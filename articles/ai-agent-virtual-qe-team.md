## QAチームが1人しかいない問題

自分はビットキーでソフトウェア品質戦略を担当している。やることは多い。テスト設計のレビュー、品質データの分析、Qaseの運用設計、ダッシュボードの構築、ベンダー管理、レポート作成。

人を増やせればいいが、品質戦略の専門人材はそう簡単に採れない。

で、考えた。**AIエージェントに専門職を割り当てて「仮想QEチーム」を作れないか？**

Claude Codeには「カスタムエージェント」の仕組みがある。`~/.claude/agents/` にMarkdownファイルを配置すると、専門知識とツール権限を持った専用AIが立ち上がる。これを使って10体のQEエージェントを設計・配置した。

きっかけはチューリング社・阿部氏のアプローチ。41ファイルの仮想PRチームを構築して開発プロセスを回している事例を見て、「QE版をやれるんじゃないか」と思った。

## なぜ「1体の万能AI」ではダメだったか

最初は1つのプロンプトに全部詰め込もうとした。テスト設計もデータ分析もレポートも、全部1体でやらせる案。

3秒で破綻が見えた。

- **コンテキストが溢れる。** Qase APIの仕様、テスト設計の7観点、KPIの計算式、ダッシュボードのCSS。1つのプロンプトに全部入れたら、どれも中途半端になる
- **ツール権限が合わない。** データ分析にはBashとAPIアクセスが要るが、レポート作成にはWriteとEditがあれば十分。全ツールを渡すと余計なことをする
- **モデルの使い分けができない。** テスト戦略の設計はOpus（高推論）が必要だが、データ集計にOpusは過剰。コスト的にも無駄

人間のチームでも「全部できる人」を1人雇うより、専門家を組み合わせるほうが強い。AIも同じだった。

### 実際に起きた「万能AI」の失敗

汎用AIにQaseのテストケースを一括更新させたとき、APIのカスタムフィールド更新で `custom_fields`（複数形）を使い続けた。APIはstatus: trueを返すのに、データが一切反映されない。原因は **`custom_field`（単数形）が正解** だったこと。

73プロジェクト、217,948件のテストケースを処理するバッチで、この手のミスが起きると致命的になる。汎用AIは「Qase APIの癖」を知らない。専門エージェントに閉じ込めて、この知識をプロンプトに焼いておくことで、二度と起きなくなった。

## 10体の構成

実際に作ったエージェントの構成がこれ。

### 司令塔

| エージェント | モデル | 役割 |
|---|---|---|
| **qe-orchestrator** | Opus | 指示を受けて最適なエージェントを選定・起動する司令塔 |

「テスト戦略をレビューして」と言うと、orchestratorがtest-design-architectとquality-analystを並列で起動する、という動き方をする。

エージェント定義の冒頭はこう書いてある：

```markdown
---
name: qe-orchestrator
description: QE戦略リードの司令塔。ユーザーの指示を解析し、
  最適なエージェントを選定・起動・統合する。
model: opus
---

あなたはbitkey品質戦略チームの司令塔です。
ユーザー（QE戦略リード）の指示を受け、
最適なエージェントを選定・起動し、結果を統合します。
```

定義ファイルにはワークフローも書いてある。「テスト戦略レビュー」「テスト設計レビュー」「週次品質レポート」など、よくある指示パターンと、それに対してどのエージェントをどの順で起動するかを定義している。

```markdown
## ワークフロー定義

**テスト戦略レビュー**
1. quality-strategist → 方針確認・現状分析
2. test-design-architect → テスト設計構造の評価
3. quality-analyst → 定量分析・RCA
4. insight-reporter → 統合レポート生成

**週次品質レポート**
1. data-analyst → Qase/Jiraからデータ収集
2. dashboard-designer → ダッシュボードHTML更新
3. insight-reporter → エグゼクティブサマリー生成
```

これがあることで、「品質レポート作って」の1行から、3体のエージェントが連鎖的に動く。

### 設計・分析レイヤー

| エージェント | モデル | 役割 |
|---|---|---|
| **test-design-architect** | Opus | テスト計画・テスト設計の上位設計。品質評価 |
| **quality-analyst** | Sonnet | バグデータ・テスト結果の多角的分析。RCA |
| **ai-reverse-engineer** | Sonnet | ソースコードから仕様・テスト観点を自動抽出 |

test-design-architectはOpusを使っている。テスト設計の品質評価にはS/A/B/C/Dの5段階グレードを定義していて、これを正しく判定するには推論の深さが必要になる。

quality-analystの定義はこう：

```markdown
---
name: quality-analyst
description: 品質分析専門家。テスト結果・バグデータ・
  プロセスメトリクスを多角的に分析し、品質の「なぜ」を
  深掘りして改善の根拠を提供する。
tools: Read, Glob, Grep, Bash
model: sonnet
---

あなたは「品質データを掘り下げる探偵」です。
「バグが多い」「テストが通らない」という現象の背後にある
根本原因を、データと論理で解き明かします。
```

注目してほしいのは **toolsがRead, Glob, Grep, Bashだけ** という点。WriteもEditもない。分析エージェントはファイルを「読む」だけで「書く」ことはしない。これが重要。

### データ・インフラレイヤー

| エージェント | モデル | 役割 |
|---|---|---|
| **data-analyst** | Sonnet | 品質データの収集・クレンジング・KPI計算 |
| **qase-specialist** | Sonnet | Qase APIの操作、テストケース管理、廃止管理 |
| **dashboard-designer** | Sonnet | HTMLダッシュボード・品質レポートの構築 |

qase-specialistの定義には、APIの癖やbitkey固有の運用ルールを焼き込んでいる：

```markdown
あなたは「Qaseを知り尽くした使い倒しのプロ」です。
bitkeyの品質プラットフォームとしてQaseを最大活用し、
テスト管理業務を効率化します。
```

「知り尽くした」というフレーズをわざと入れている。汎用AIだと「Qaseとは何ですか」レベルから始まることがあるが、専門エージェントは「Qaseの全機能を前提として」動く。APIの単数形/複数形問題も、カスタムフィールドの設計パターンも、このエージェントに閉じ込めてある。

### アウトプット・対外レイヤー

| エージェント | モデル | 役割 |
|---|---|---|
| **insight-reporter** | Sonnet | 経営層向けレポート変換。月次・四半期 |
| **vendor-manager** | Sonnet | 外部パートナーの選定・契約・品質管理 |

### 独立型

| エージェント | モデル | 役割 |
|---|---|---|
| **extension-engineer** | Opus | VS Code拡張・macOSツールの開発保守 |

extension-engineerだけは品質業務と直接関係ない。Claude Code自体の開発環境を改善するツール（VS Code拡張やmacOSユーティリティ）を作るエージェント。他のエージェントとの依存関係がないので、独立型として配置している。

## 設計で意識した3つのこと

### 1. モデルの使い分け

10体中、Opusは3体だけ。残り7体はSonnet。

```
Opus（高推論・高コスト）:
  qe-orchestrator     — チーム全体の判断
  test-design-architect — テスト設計の品質評価
  extension-engineer   — コード生成の品質

Sonnet（高速・低コスト）:
  それ以外の7体      — データ処理、API操作、レポート生成
```

判断基準はシンプルで、**「推論の深さが必要か」** だけ。テスト戦略の設計やテストケースの品質評価は「正解がない判断」を求められるのでOpus。一方、Qase APIを叩いてデータを集める、CSVを加工する、HTMLを生成するといった作業は「手順が明確」なのでSonnetで十分。

体感だが、Sonnetで回せる作業にOpusを使っても精度はほぼ変わらない。コストだけが上がる。

### 2. ツール権限の制限

全エージェントに全ツールを渡さない。

```
quality-analyst:    Read, Glob, Grep, Bash
                    （読むだけ。書き込まない）

dashboard-designer: Read, Glob, Grep, Bash, Write, Edit
                    （ファイル生成あり）

vendor-manager:     Read, Glob, Grep, Bash, WebSearch
                    （外部調査あり）

qase-specialist:    Read, Glob, Grep, Bash, WebFetch, WebSearch, Write, Edit
                    （API操作＋設定ファイル更新あり）
```

**「できることを絞る」とエージェントの出力が安定する。** 何でもできる状態だと、分析を頼んだのにファイルを書き始めたり、レポートを頼んだのにコードを修正し始めたりする。

実際にquality-analystからWriteを外したのは、分析結果をファイルに書き出すときにフォーマットが安定しなかったから。「分析して」と頼むと、分析結果を勝手にMarkdownファイルに書き出す → そのフォーマットが毎回違う → 後続のダッシュボード生成で読み込めない、という問題が起きた。

WriteをなくしてBashだけにしたら、標準出力にテキストで返すようになった。それをdashboard-designerが受け取る形のほうが、結果的にパイプラインが安定した。

### 3. 依存関係の明示

各エージェント定義の末尾に「連携エージェント」セクションを入れた。

```markdown
## 連携エージェント
- data-analyst: 生データ提供
- insight-reporter: 経営向け変換
- qase-specialist: 詳細データ抽出
```

これはAIへの指示というより、自分用の設計ドキュメント。どのエージェントがどこに依存しているかを見える化しておかないと、構成変更時に壊れる。

たとえばqase-specialistのAPIの呼び方を変えたら、data-analystのデータ取得ロジックにも影響する。依存関係が明示されていれば「ここを変えたらここも変える」が追える。

## データの流れ

エージェント間のデータの流れはこうなっている。

```
qe-orchestrator（指示の振り分け）
    ├── test-design-architect ←→ ai-reverse-engineer
    │       ↓
    ├── qase-specialist（テストケース管理）
    │       ↓
    ├── data-analyst（データ収集・加工）
    │       ↓
    ├── quality-analyst（分析・RCA）
    │       ↓
    ├── dashboard-designer（可視化）
    │       ↓
    └── insight-reporter（レポート化）
```

上から下に流れるパイプライン型が基本。ただし、test-design-architectとai-reverse-engineerは双方向でやり取りする。コードから観点を抽出して、それをテスト設計に反映する、というループがあるため。

### 具体的なパイプライン例：週次品質レポート

「週次レポートを作って」と入力したとき、実際に起きることはこう：

```
1. qe-orchestrator が「週次品質レポート」ワークフローを選択

2. data-analyst が起動
   → Qase APIから今週のテスト実行結果を取得
   → Pass/Fail/Blocked の集計、前週比の計算
   → CSV形式で標準出力に返す

3. dashboard-designer が起動
   → data-analystの出力を受け取る
   → HTMLダッシュボード（チャート・テーブル）を生成
   → ファイルに書き出す

4. insight-reporter が起動
   → ダッシュボードのデータを読み取る
   → 経営層向けの3行サマリーを生成
   → 「今週のリスク」「来週のアクション」を付加
```

自分がやることは最初の1行だけ。あとは3体が順に動いて、最終成果物が出てくる。

## 構築プロセス：0から10体ができるまで

2026年5月に一気に構築した。プロセスはこう：

### Step 1：業務の棚卸し（1日目）

まず自分の品質業務を全部書き出した。

```
テスト設計のレビュー
品質データの収集・分析
Qaseの設定・運用
ダッシュボード/レポート構築
ベンダーとのやり取り
VS Code拡張の保守
テスト戦略の策定
コードからの仕様抽出
KPI計算
経営向けレポート作成
```

この時点で「10個くらいの専門領域に分かれるな」と見えた。

### Step 2：ロール定義（1日目）

棚卸しした業務を専門領域でグルーピングして、各ロールの責務を定義した。

ここで重要だったのは **「このロールは何をしないか」を決めること** 。quality-analystは分析をするが、その結果をレポートにまとめるのはinsight-reporterの仕事。ダッシュボードに可視化するのはdashboard-designerの仕事。境界を引かないと、全エージェントが同じことをやり始める。

### Step 3：エージェント定義ファイルの作成（2日目）

Markdownファイルを10個書いた。各ファイルの構成は統一している：

```markdown
---
name: エージェント名
description: 1行の役割説明
tools: 使えるツールのリスト
model: opus or sonnet
---

# ロール名

あなたは「○○」です。（擬人化した一行の役割定義）

## 主要責務
- 責務1
- 責務2
- ...

## 判断基準やフレームワーク
（そのロール固有の知識）

## 連携エージェント
- agent-a: 何を受け取るか
- agent-b: 何を渡すか
```

**擬人化がポイント。** qase-specialistは「Qaseを知り尽くした使い倒しのプロ」、quality-analystは「品質データを掘り下げる探偵」。こう書くと、AIの出力トーンが変わる。「プロ」と言われたエージェントは、基本的なことを聞き返さずに自信を持って動く。

### Step 4：共通リファレンスの作成（2日目）

全エージェントが参照する共通ファイル `qe-reference.md` を作った。Qase APIの仕様、KPIの計算式、品質スコアの定義など、チーム共通の知識をまとめたもの。

各エージェントの定義に同じ情報を重複して書くと、更新時に10ファイル全部を直す羽目になる。共通リファレンスに切り出すことで、メンテナンスポイントを1箇所に集約した。

### Step 5：試運転と調整（3日目〜）

最初の1週間は、意図通りに動かないケースを片っ端から潰した。

- quality-analystがファイルを書き出す問題 → toolsからWriteを除去
- orchestratorが不要なエージェントまで起動する問題 → ワークフロー定義を具体化
- エージェント間でデータの受け渡し形式がバラバラ → 出力フォーマットを統一

正直、定義ファイルの初版は半分くらい書き直した。「設計→試運転→修正」のサイクルを3周くらい回して、ようやく安定した。

| 品質 | 毎回フォーマットが微妙に違う | テンプレート化で統一 |

### Qaseテストケース棚卸し

| | Before | After |
|---|---|---|
| 対象 | 73プロジェクト、217,948件 | 同じ |
| 作業時間 | やる気が起きない規模感 | 自動バッチで3分類 |

## 実際に使ってみてわかったこと

### うまくいっていること

**司令塔パターンは正解だった。** 「品質レポートを作って」と1行言えば、orchestratorがdata-analyst → quality-analyst → dashboard-designer → insight-reporterを順に起動する。自分で4体を手動で呼ぶ必要がない。

**専門特化で精度が上がった。** Qaseの操作をqase-specialistに閉じたことで、APIの呼び方やフィールド名の間違いが激減した。汎用AIにQase操作をさせていたときは、custom_fieldの単数/複数形でよくミスっていた。

**並列実行で時間が縮む。** 独立したタスクなら複数エージェントを同時に走らせられる。テスト設計のレビューとデータ分析を並列で回すと、体感で半分くらいの時間で終わる。

**定義ファイルが設計ドキュメントになった。** エージェント定義を書く過程で「この業務の責務範囲はどこまでか」「どのツールが必要か」を明文化した。これは人間のチームを作るときのジョブディスクリプションと同じ。AIのためだけでなく、自分の業務整理としても価値があった。

### 課題として残っていること

**エージェント間の引き継ぎが雑になりがち。** orchestratorが各エージェントに指示を出すとき、コンテキストの受け渡しが「プロンプトのテキスト」に依存する。構造化されたインターフェースがないので、伝言ゲームになることがある。

たとえば、data-analystが出力した数値をquality-analystに渡すとき、orchestratorが要約して渡す。その要約で情報が落ちることがある。「前週比15%増」が「増加傾向」に丸められたり。

**10体全部が常に必要なわけではない。** 日常的に使うのはqase-specialist、data-analyst、dashboard-designerの3体がほとんど。vendor-managerやinsight-reporterは月に数回。存在を忘れて手作業してしまうこともある。

**定義ファイルのメンテナンスが地味に必要。** Qase APIの仕様が変わったらqase-specialistの定義を更新する。共通リファレンス（qe-reference.md）との整合も保つ必要がある。10体分となると、それなりに手間。ただし、これは人間のチームでもオンボーディング資料を更新するのと同じコスト感。

**コスト管理が見えにくい。** Opus3体を同時に動かすとAPI利用量が跳ねる。今のところ業務上の問題にはなっていないが、利用量のモニタリングは組み込めていない。

## この設計が向いているケース

万人におすすめするつもりはない。向き不向きがある。

**向いている:**
- 品質業務を1人または少人数で回している
- 定型作業（データ収集→分析→レポート）のパイプラインがある
- Qaseなど特定ツールのAPI操作を頻繁にやる
- 業務の責務境界を明確にしたい

**向いていない:**
- チームに十分な人数がいて、AIに委任する動機がない
- 業務がアドホックで、パイプライン化しにくい
- エージェント定義のメンテナンスコストを許容できない
- Claude Codeのカスタムエージェント機能を使える環境にない

## まとめ

「AIに仕事を任せる」の第一歩は、**仕事を分解して名前をつけること** だと思う。

10体のエージェントを作る過程で、自分の品質業務がどういう専門性の組み合わせで成り立っているのか、初めて整理できた。テスト設計、データ分析、可視化、レポーティング。それぞれに必要なスキルセット、ツール、推論の深さが違う。

この分解ができれば、AIに任せるかどうかは二の次で、チーム設計そのものが変わる。人間のチームを作るときにも使える考え方のはず。

:::
