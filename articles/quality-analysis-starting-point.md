## 「品質分析やらなきゃ」の罠

「品質分析を始めたい」——そう思ったとき、最初に調べるのは分析手法だと思います。

パレート分析、なぜなぜ分析、ODC分析、フォールトツリー……。手法はいくらでも出てきます。でも、いざ自分の現場でやろうとすると手が止まる。

止まる理由は、手法を知らないからではありません。**分析できるデータがないから**です。

## 実際にやってみた

私のチームでは、不具合データ10,691件を対象にLevel 1の分析（偏りを見る）を試みました。最初に目に飛び込んできたのは、手法以前の問題でした。

### Severityの半分が空欄

不具合の**51.2%にSeverityが設定されていない**。最も件数の多い領域では63.5%が未設定でした。

Severityがなければ「重大なバグが増えているのか」すら判断できません。分析の前提が崩れている状態です。

### 5つのソースに定義がバラバラ

不具合データの出所が5つに分散し、同じ「重大度」でもCritical/Emergency/blocker/Majorと名前が混在していました。

分析するには、まず名寄せが必要です。でもその名寄せに正解がない。定義が統一されていないからです。

### 未着手の山にCriticalが埋もれている

43.5%が未着手または待ち状態。そのうちCritical以上が623件。Severity未設定の1,492件の中にも重大バグが潜在している可能性があります。

分析する前に、トリアージすべきバグがあるという事実に気づく——これも「分析」の一つです。

## 勉強のたとえでいうと

以前の記事で、テスト・QC・QAを「勉強」にたとえました。品質分析を同じ構造で見ると：

```
テスト  → 問題を解く       → 点数が出る
分析    → 答え合わせする    → 何を間違えたかわかる
改善    → 勉強法を変える    → 次の点数が上がる
```

ここで大事なのは、答え合わせには**「正解が書いてある解答用紙」が必要**だということです。

解答用紙に正解が書いてなかったら？ 問題番号がバラバラだったら？ そもそも自分の答案がどれかわからなかったら？

答え合わせ（＝分析）は始められません。

**品質データの「Severity未設定51%」は、正解が書いていない解答用紙です。**

## 分析できるデータの3条件

分析手法を選ぶ前に、データがこの3つを満たしているか確認してください。

| 条件 | 問い | NG例 |
|---|---|---|
| **①分類されている** | Severityやカテゴリは埋まっているか？ | 51%が未設定 |
| **②定義が統一されている** | 同じ言葉が同じ意味で使われているか？ | Critical/Emergency/blockerが混在 |
| **③時間軸がある** | いつ作り込まれ、いつ見つかったかわかるか？ | created_atしかなくdetection_phaseが空 |

3つすべて揃っていなくても、①だけ整えるだけで「偏りを見る」分析は始められます。

## Level 1：偏りを見るだけで十分

高度な手法は要りません。**クロス集計だけ**で、現場に十分なインパクトを与えられます。

### やること

```
Severity × 領域  → どこに重大バグが集中しているか
月別 × 領域     → いつ増えているか、減っているか
ステータス × Severity → 放置されている重大バグはないか
```

### これだけで見えること

- 「workhubのバグが多い」ではなく「workhubのMajor以上が前月比30%増」
- 「バグが溜まっている」ではなく「Critical以上が623件未着手」
- 「テスト足りてない」ではなく「この領域のバグ密度が他の3倍」

**件数を報告するだけの「集計」と、偏りから問いを立てる「分析」は違います。**

## 分析を回すために必要なこと

### ①データの入り口を整える

分析は「後工程」です。入り口（バグ登録時）でデータが汚れていたら、どんな手法も機能しません。

- Severity必須にする（空欄で保存できないようにする）
- 選択肢を統一する（Critical/Major/Normal/Minorの4段階）
- 登録テンプレートを用意する

### ②「集計」と「分析」を分ける

集計は自動化できます。分析は人がやります。

- 集計：ダッシュボードで自動表示（毎日）
- 分析：集計結果を見て「なぜ？」を問う（週次/月次）

### ③ So What? を必ずつける

数字を出して終わりではなく、「だから何をすべきか」まで言い切る。

- ✕「今月のバグは234件でした」
- ○「今月のバグは前月比+20%。増加はXX領域に集中。原因はYYの可能性」

## おわりに

品質分析が回らない現場に、新しい分析手法を導入しても意味がありません。

まずやるべきは、**バグデータのSeverityを埋めること**。たったそれだけで、クロス集計という最もシンプルな手法で「偏り」が見えるようになります。

偏りが見えれば、問いが立つ。問いが立てば、改善が始まる。

分析の第一歩は、手法を学ぶことではなく、データを整えることです。
