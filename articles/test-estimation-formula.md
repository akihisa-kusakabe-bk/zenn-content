## 「だいたい○○ケースくらいですかね」の正体

テスト計画でスケジュールを立てるとき、テストケース数の見積もりはどうやっているだろうか。

正直なところ、多くの現場では「前回と同じくらいの規模感だから○○ケースくらい」「経験的にこの手の機能なら△△ケース」という見積もりが主流だと思う。自分もそうだった。

これで困るのは3つの場面。

- **初めての領域。** 過去実績がないから「だいたい」が通用しない
- **説明責任。** 上席に「なぜその工数なのか」と聞かれたとき、根拠を示せない
- **精度のばらつき。** 見積もる人によって2〜3倍の差が出る

結局、見積もりの「勘と経験」の中身を分解してみたら、ちゃんと数式にできた。さらにAIで支援できるポイントも見えてきた。

## テスト見積もりの基本公式

機能テスト・シナリオテストの見積もりは、突き詰めると2つの掛け算。（非機能テストは構造が異なるため本記事では扱わない）

```
テスト工数 = テストボリューム × 生産性⁻¹
```

- **テストボリューム** = どれだけのテストケース/ステップがあるか
- **生産性** = 1人時あたり何ケース設計/実行できるか

## テストボリュームの分解

テストボリュームの出し方は、テストの種類で構造が変わる。

### 機能テスト（結合テスト）の場合

#### テストケース数 = テストオブジェクト × テスト観点

機能単位のテストでは、ケース数は「何をテストするか（オブジェクト）」と「どう確認するか（観点）」の掛け算で出る。

| テストオブジェクトの例 | テスト観点の例 |
|---|---|
| 画面（ログイン画面、設定画面…） | 正常系（期待通りの入力） |
| 入力項目（テキストボックス、プルダウン…） | 異常系（不正入力、空欄） |
| ボタン/アクション（送信、キャンセル…） | 境界値（最大桁数、0件、上限） |
| API（エンドポイント単位） | 状態遷移（ステータス変化） |
| バッチ/ジョブ | 組合せ（複数条件の掛け合わせ） |
| 外部連携（決済、通知…） | 権限（ロール別アクセス） |

**全オブジェクト × 全観点ではない。** オブジェクトの種類によって適用すべき観点は決まる。

| オブジェクト種別 | 適用する観点 | 適用しない観点 |
|---|---|---|
| テキストボックス | 同値分割、境界値、文字種、桁数 | 状態遷移（普通は不要） |
| ステータス遷移 | 状態遷移、無効遷移 | 境界値（数値がない） |
| API | 正常/異常レスポンス、認証、レート制限 | UI操作系の観点 |
| 一覧画面 | ページング、ソート、0件/大量データ | 文字種（入力がない） |

このマッピングが「経験者の頭の中」にしかなかったものの正体。

#### 機能テストのステップ数

ケース数だけでは実行工数は出ない。1ケースあたりのステップ数が必要。

| ケースタイプ | 平均ステップ数の目安 |
|---|---|
| 単項目の入力チェック | 3〜5ステップ |
| 画面遷移の確認 | 5〜8ステップ |
| 複合条件の組合せテスト | 5〜10ステップ |

### シナリオテスト（総合テスト）の場合

シナリオテストでは、「オブジェクト×観点」ではなく、「業務フロー×ステップ」でボリュームを出す。

```
テストボリューム = シナリオ数 × 平均ステップ数
```

#### シナリオの洗い出し方

シナリオは「誰が、何のために、どうつかうか」を軸に分解する。

| 分解軸 | 例（通知設定機能） |
|---|---|
| 正常系業務フロー | 通知設定を有効化 → 通知受信 → 内容確認 |
| 代替フロー | 通知を一時停止 → 停止中にイベント発生 → 再開後にまとめて通知 |
| 異常系フロー | 通知送信先が無効 → エラーハンドリング → リトライ |
| 権限別フロー | 管理者が他ユーザーの通知を強制設定 |
| データ状態別 | 初回設定（デフォルト） / 変更 / 移行データあり |

#### シナリオのステップ数

| シナリオタイプ | 平均ステップ数の目安 |
|---|---|
| 単機能の正常系フロー | 5〜8ステップ |
| 複数機能をまたぐE2Eフロー | 10〜20ステップ |
| 異常系・エッジケース | 8〜15ステップ |
| 業務フロー全体（申込→審査→承認→完了） | 15〜30ステップ |

### 機能テストとシナリオテストの使い分け

| | 機能テスト（結合） | シナリオテスト（総合） |
|---|---|---|
| 見積もりの単位 | ケース数 | シナリオ数 × ステップ数 |
| ボリュームの出し方 | オブジェクト × 観点 | 業務フローの分解 |
| 向いている場面 | 機能追加・改修のテスト | リリース前の総合確認 |

## 生産性の算出

ボリュームが出たら、次は「どのくらいのスピードでできるか」。

### 生産性を左右する変数

「1時間に何ケース」は以下の変数で大きく変わる。

| 変数 | 設計への影響 | 実行への影響 |
|---|---|---|
| 新規 vs 改修 | 新規は仕様理解から。2〜3倍の差 | 新規は環境構築も含む |
| 仕様の明確さ | 曖昧 → 確認コストで生産性半減 | ー |
| ドメイン知識 | 初回は調査込み。2回目以降1.5〜2倍速 | ー |
| テスト技法 | DTは手間だが網羅性が高い | ー |
| 手動 vs 自動 | ー | 自動化済みなら実行時間≈ゼロ |
| 環境・データ準備 | ー | 準備が重いと実行より準備が長い |
| 障害発生率 | ー | バグ多い → 報告・再テストで低下 |
| エビデンス取得 | ー | 有無で「3〜4倍変わる」（湯本氏） |

### 標準値：どのくらいが目安か

業界標準ベンチマークは存在しない。ISTQB・Capers Jonesのような権威も、件/時間の基準値は公表していない。テストケースの粒度・ドメイン複雑度・エビデンス取得の有無で生産性が数倍変わるからだ。

ただし、「このあたりが目安」と言える参考データはある。

#### 機能テスト（結合）の生産性目安

| 工程 | 参考値（人日） | 参考値（人時） | 根拠 |
|---|---|---|---|
| テスト設計 | 約50件/人日 | 約6件/人時 | ⚠️ 著者推定（IPA工数比率 設計20%:実行50%から逆算） |
| レビュー | 約100件/人日 | 約13件/人時 | ⚠️ 著者推定（設計の2倍速と仮定） |
| テスト実行 | **20件/人日** | **2.5件/人時** | IPA白書統計（結合テスト・中央値） |

:::message
**「設計より実行が遅い」のは直感に反するかもしれない。** 記事内のSHIFT社データと比較するとその正体が見える。

| 条件 | 件/人時 | 備考 |
|---|---|---|
| **テスト設計（著者推定）** | **約6** | IPA工数比率から逆算 |
| 実行（エビデンスなし・画面操作あり） | 12 | SHIFT社データ（例示値） |
| 実行（エビデンスなし・複数画面遷移） | 6 | SHIFT社データ（例示値） |
| **実行（IPA実績=エビデンス＋バグ込み）** | **2.5** | IPA白書 |

つまり:
- エビデンス・バグなし → 実行は設計と**同等か2倍速い**（直感通り）
- エビデンス・バグあり → 実行が設計の**半分以下に落ちる**（逆転する）

**エビデンス取得や障害報告が速度を大きく落としている可能性が高い。** ただしIPA白書は多組織の統計データであり、SHIFT社は単一企業のデータなので、差の原因はエビデンスだけとは限らない（組織差・計測方法の違いも含まれる）。それでも、エビデンス取得の自動化が投資対効果の高い改善ポイントであることは間違いない。
:::

#### シナリオテスト（総合）の生産性目安

| 工程 | 参考値（人日） | 参考値（人時） | 根拠 |
|---|---|---|---|
| シナリオ設計 | 16〜24シナリオ/人日 | 2〜3シナリオ/人時 | ⚠️ 著者推定（機能テスト設計の1/2〜1/3） |
| レビュー | 40〜64シナリオ/人日 | 5〜8シナリオ/人時 | ⚠️ 著者推定（設計の2〜3倍速と仮定） |
| シナリオ実行 | **10シナリオ/人日** | **1.25シナリオ/人時** | IPA白書統計（総合テスト・中央値） |

> 出典: IPA「ソフトウェア開発データ白書 2016-2017」の統計データを湯本剛氏が分析（[参考記事](https://note.com/yumotsuyo/n/nb6b89762c060)）
> 湯本氏の指摘: 「結合テストなら60〜80件いけると思ったが、実データは20件/日」。エビデンス取得・障害報告の時間が体感と実績の差を生む。

**テスト実行の複雑度別目安（SHIFT社の実務知見）:**

| 複雑度 | 1件あたり所要時間 | 人時換算 |
|---|---|---|
| 表示確認のみ | 3分 | 約20件/人時 |
| 画面操作あり | 5分 | 約12件/人時 |
| 複数画面遷移 | 10分 | 約6件/人時 |
| 応答待ちあり | 15分 | 約4件/人時 |

> 出典: SHIFT社「[テスト実施(実行)ですべきこと](https://service.shiftinc.jp/column/7991/)」

:::message
**テスト設計が終わった時点で、実行工数が見積もれる。** テスト設計の成果物（テストケース一覧）を上記の4分類に振り分けるだけで、実行時間の推定ができる。

```
推定実行時間 = Σ（各複雑度のケース数 × 1件あたり所要時間）
```

例: 表示確認20件(×3分) + 画面操作15件(×5分) + 画面遷移8件(×10分) = 60+75+80 = **215分（約3.6時間）**

テストレベル（結合 or 総合）とケースの複雑度分類、この2つの変数があれば実行工数は算出できる。「設計が終わるまで実行工数が読めない」のではなく、**設計が終わった瞬間に実行工数が確定する**という関係にある。
:::

### 標準以下なら→改善必須

自社の生産性が上記の目安を下回っている場合、何かがおかしい。プロセスに問題がある可能性が高い。

| 症状 | よくある原因 | 打ち手 |
|---|---|---|
| 設計が極端に遅い（<3件/人時） | 仕様が曖昧で確認待ちが多発 | 仕様レビューをテスト設計前に入れる |
| 設計が極端に遅い（<3件/人時） | 観点カタログがなく、毎回ゼロから考えている | 観点テンプレートを整備する |
| 実行が極端に遅い（<10件/人日） | テスト環境の構築・データ準備に時間を食われている | テストデータの自動生成・リセットの仕組み化 |
| 実行が極端に遅い（<10件/人日） | 障害発生率が高く、報告・再テストに工数が流れている | 開発側の品質を上流で押さえる（コードレビュー強化等） |

### 標準を超えるには→テストのやり方を変える

上記の目安は「従来の手動プロセス」の相場観。これを超えるには、テストのやり方自体を研究して変える必要がある。

| アプローチ | 具体策 | 期待効果 |
|---|---|---|
| 設計のAI支援 | 仕様書からテスト観点を自動マッピング（本記事のAIポイント2） | 設計速度2〜3倍 |
| 実行の自動化 | 回帰テストを自動化し、手動は探索的テストに集中 | 実行工数そのものが消える |
| テストケースの再利用 | 過去資産から類似ケースを検索・派生 | 設計工数の削減（特に改修プロジェクト） |
| リスクベースの絞り込み | 全観点をやるのではなく、リスクの高い観点に集中 | ケース数自体を減らして全体工数を圧縮 |
| エビデンス取得の改善 | スクリーンショット自動取得・ログ自動添付 | 実行1件あたりの時間が半減（湯本氏も「3〜4倍変わる」と指摘） |
| テスト技法の研究 | JSTQBシラバスやテスト設計コンテスト等で技法を磨く | 同じ観点でも少ないケースで網羅できる |

つまり、目安は「現在地」を測るためのもの。下回ったらプロセスの問題、超えたいならテストのやり方の研究が必要。

### 自社データの計測方法

最終的に見積もりにつかうべきは自社の実績データ。

QaseやTestRailなどのテスト管理ツールを使っていれば、以下のデータが取れる。

```
設計生産性 = 作成ケース数 ÷ 設計に使った時間
実行生産性 = 実行ケース数 ÷ 実行に使った時間
```

過去3〜5スプリント分のデータがあれば、かなり安定した係数が出る。自社データがない初回は、上記の目安を使いつつ、1スプリント後に実績で補正する。

## スケジュールの算出

ここまでの要素を組み合わせると、スケジュールが出る。

```
テスト設計工数 = テストケース数 ÷ 設計生産性（件/人時）
テスト実行工数 = テストケース数 ÷ 実行生産性（件/人時）
レビュー工数  = テストケース数 ÷ レビュー生産性（件/人時）

合計工数 = 設計 + レビュー + 実行 + バッファ（通常20〜30%）

スケジュール = 合計工数 ÷ 投入人数
```

## AIが効く3つのポイント

この見積もりプロセスの中で、AIで楽になるのは3箇所。

### 1. テストオブジェクトの自動抽出

仕様書や画面設計書からテストオブジェクトを抜き出す作業。人がやると読み落としが起きるし、時間がかかる。

AIに仕様書を渡して「テスト対象となるオブジェクトを種別ごとに抽出して」と指示すれば、画面・入力項目・ボタン・API・バッチを構造化して返してくれる。

```
入力: 仕様書（テキスト or 画面キャプチャ）

プロンプト: この仕様書からテスト対象となるオブジェクトを以下の分類で抽出してください。
- 画面名
- 入力項目（種別: テキスト/プルダウン/チェックボックス/ラジオ等）
- ボタン/アクション
- API（推測含む）
- 状態遷移（ステータスが変わるもの）

出力: 構造化されたオブジェクト一覧（JSON or テーブル）
```

**精度の実感:** 自分が試した範囲では、画面キャプチャからの抽出で概ね拾える印象。ただし使用モデルや仕様書の書き方で精度は大きく変わる。抜けるのは「画面に表示されない内部処理」や「暗黙の仕様」。ここは人がレビューして補完する。

### 2. テスト観点の自動マッピング

オブジェクト種別ごとに適切なテスト観点を割り当てる作業。これが「経験者の頭の中」の本体。

AIにオブジェクト種別ごとの観点カタログを持たせておけば、自動でマッピングできる。

```
入力: テストオブジェクト一覧 + 観点カタログ

プロンプト: 各テストオブジェクトに対して、種別に応じた適切なテスト観点を
マッピングしてください。マッピング根拠も付記してください。

出力:
| オブジェクト | 種別 | 適用観点 | 推定ケース数 |
|---|---|---|---|
| ユーザー名 | テキストボックス | 同値分割(3), 境界値(2), 文字種(4) | 9 |
| ステータス | 状態遷移 | 有効遷移(5), 無効遷移(3) | 8 |
```

**ポイント:** 観点カタログはJSTQBシラバスのテストタイプ分類やISO 25010の品質特性をベースにすると網羅性が上がる。

### 3. 生産性係数の算出

Qase等のテスト管理ツールからデータを引っ張ってきて、自社の生産性係数を計算する部分。

```
入力: Qaseのテスト実行履歴（過去5スプリント分）

プロンプト: 以下の実行履歴から、テスト種別ごとの
設計生産性（件/人時）と実行生産性（ステップ/人時）を算出してください。
外れ値は除外し、中央値ベースで出してください。

出力:
| テスト種別 | 設計生産性 | 実行生産性 | サンプル数 |
|---|---|---|---|
| 機能テスト（新規） | 4.2件/人時 | 12ステップ/人時 | n=45 |
| 機能テスト（改修） | 7.8件/人時 | 15ステップ/人時 | n=62 |
| E2Eテスト | 2.1件/人時 | 8ステップ/人時 | n=18 |
```

## 実践例：ある機能追加の見積もり

実際にこの方法で見積もるとどうなるか。架空の例で示す。

**お題：** ユーザー設定画面に「通知設定」機能を追加

### Step 1: テストオブジェクト抽出（AI実行）

| # | オブジェクト | 種別 |
|---|---|---|
| 1 | 通知設定画面 | 画面 |
| 2 | メール通知トグル | チェックボックス |
| 3 | プッシュ通知トグル | チェックボックス |
| 4 | 通知頻度 | プルダウン（即時/日次/週次） |
| 5 | 通知時間帯 | 時刻入力（開始・終了） |
| 6 | 保存ボタン | ボタン |
| 7 | 通知設定API | API（PUT /settings/notification） |
| 8 | 通知ステータス | 状態（有効/無効/一時停止） |

### Step 2: テスト観点マッピング（AI実行）

| オブジェクト | 適用観点 | 推定ケース数 |
|---|---|---|
| メール通知トグル | ON/OFF(2), 初期値(1), 保存確認(1) | 4 |
| プッシュ通知トグル | ON/OFF(2), 初期値(1), 保存確認(1) | 4 |
| 通知頻度 | 各選択肢(3), 初期値(1), 変更保存(1) | 5 |
| 通知時間帯 | 正常範囲(2), 境界値(4), 不正値(3), 開始>終了(1) | 10 |
| 保存ボタン | 正常保存(1), 未変更保存(1), 二重クリック(1) | 3 |
| 通知設定API | 正常(1), バリデーション(3), 認証(2), 競合(1) | 7 |
| 通知ステータス | 有効遷移(3), 無効遷移(2) | 5 |
| 画面表示 | 初期表示(1), 権限別(2), レスポンシブ(2) | 5 |
| **合計** | | **43ケース** |

### Step 3: 生産性係数の適用

ここでは参考値の中央あたりを使って試算する。自社データがあればそちらに置きかえる。

| 工程 | 使用係数 | 根拠 | 計算 | 工数（人時） | 工数（人日） |
|---|---|---|---|---|---|
| テスト設計 | 約6件/人時 | 著者推定（IPA工数比率から） | 43 ÷ 6 | 7.2h | 0.9日 |
| レビュー | 約13件/人時 | 著者推定（設計の2倍速） | 43 ÷ 13 | 3.3h | 0.4日 |
| テスト実行 | 2.5件/人時 | IPA白書（結合テスト中央値） | 43 ÷ 2.5 | 17.2h | 2.2日 |
| バッファ（25%） | | | | 6.9h | 0.9日 |
| **合計** | | | | **34.6h** | **4.3人日** |

※ テスト実行の2.5件/人時はIPA白書の実測統計。設計・レビューは著者がIPA工数比率から推定した参考値。詳細は「標準値：どのくらいが目安か」セクション参照。

### 「勘」との比較

- **勘ベース:** 「通知設定くらいなら2〜3人日かな」
- **数式ベース:** 4.3人日
  - **差分の正体:** 時刻入力の境界値テスト（10ケース）と状態遷移テスト（5ケース）が勘では抜けていた。「43ケース」という数字が出ると、なぜその工数なのかをケース単位で説明できる

## この方法の限界と対策

万能ではない。限界を知っておく。

| 限界 | 対策 |
|---|---|
| **非機能テストは別計算。** 性能・セキュリティは観点マッピングの構造が違う | 非機能テスト用の観点カタログを別途用意 |
| **暗黙の仕様は抽出できない。** AIは書かれていないことは拾えない | ドメインエキスパートのレビューを必ず挟む |
| **生産性係数は環境依存。** チーム・ツール・ドメインで全然違う | 必ず自社データをつかう。業界平均は参考程度 |
| **初回は係数がない。** 過去データがないプロジェクトでは使えない | 類似プロジェクトの係数を借りて、1スプリント後に補正 |

## アジャイル開発での応用：ストーリーポイントからテスト工数を出す

ここまでの公式は「仕様書がある」前提だった。ではスプリントごとに要件が変わり、詳細な仕様書がないアジャイル開発ではどうするか。

入力を「テストオブジェクト×観点」から「ストーリーポイント」に置きかえる。

```javascript
// ウォーターフォール版
テスト工数 = (テストオブジェクト × テスト観点) × 生産性⁻¹
//            ↑ 仕様書が必要

// アジャイル版
推定テストケース数 = ストーリーポイント × テスト密度(件/SP)
推定実行時間 = 推定テストケース数 × 複雑度別所要時間
//              ↑ スプリント計画時に分かる
```

### テスト密度の算出

鍵は**テスト密度（1ストーリーポイントあたり何テストケース出るか）**。過去スプリントの実績から出す。

```javascript
テスト密度 = 過去Nスプリントの総テストケース数 ÷ 総消化SP
```

| Sprint | 消化SP | テストケース数 | テスト密度 |
|---|---|---|---|
| Sprint 1 | 13 | 52 | 4.0件/SP |
| Sprint 2 | 8 | 28 | 3.5件/SP |
| Sprint 3 | 21 | 73 | 3.5件/SP |
| **加重平均** | **42** | **153** | **3.6件/SP** |

加重平均（総ケース数÷総SP = 153÷42）をつかう。スプリントごとの単純平均だとSP数の少ないスプリントに引っ張られる。3〜5スプリント分のデータがあれば安定した係数になる。

### 計算例

今スプリント: 15SP を計画

```javascript
推定ケース数 = 15SP × 3.6件/SP ≒ 54ケース

推定実行時間（複雑度別に分類）:
  表示確認 20件 × 3分  =  60分
  画面操作 25件 × 5分  = 125分
  画面遷移 10件 × 10分 = 100分
  合計                 = 285分 ≒ 4.8時間
```

おおよそのケース数が出ていれば、先述の複雑度別所要時間を掛けるだけで実行工数も概算で算出できる。

### 精度を上げるコツ

| アプローチ | やり方 |
|---|---|
| **ストーリー種別で分ける** | 新機能(5件/SP) vs バグ修正(2件/SP) vs リファクタ(1件/SP) で密度が違う |
| **スプリント回顧で補正** | 見積もりと実績の差分を毎スプリント記録し、係数を更新する |
| **プランニング時に複雑度も見積もる** | 「このストーリーは画面遷移系が多い」→ 実行時間の精度が上がる |

仕様書がなくても、**ストーリーポイント＋過去のテスト密度＋複雑度分類**の3つがあれば、スプリント計画時にテスト工数を数字で出せる。

## まとめ

テスト見積もりの「勘と経験」を分解すると、3つの部品になる。

1. **テストオブジェクト** -- 何をテストするか
2. **テスト観点** -- どう確認するか
3. **生産性係数** -- どのくらいの速さでできるか

この3つを構造化すれば、見積もりプロセスの大部分をAIで支援できる。ただし「仕様に書かれていない暗黙知」と「現場固有の調整」は人間の仕事として残る。

見積もりの精度が上がると、スケジュールの信頼性が上がる。信頼性が上がると、「なぜこの工数なのか」を数字で説明できる。説明できると、品質活動への投資判断がしやすくなる。
