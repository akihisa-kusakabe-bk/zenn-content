## 26冊のシラバス、全部読んだ人いる？

JSTQBのシラバスは2026年7月時点で26種類ある。Foundation Level、Advanced Level（テストアナリスト、テストマネージャー）、Specialist（性能テスト、セキュリティテスト、AIテスト、モバイルアプリテスト、自動車ソフトウェアテスト……）。

正直、全部読んでる人は少数派だと思う。自分もそう。FL・CTAL-TAあたりは読んだけど、CT-GaMe（ゲームテスト）やCT-AuT（自動車ソフトウェア）は「へー、あるんだ」止まり。

でもこの26冊、テスト設計の知識体系としてはめちゃくちゃ整理されている。K1〜K4の学習目標で粒度が揃っているし、概念間の関連も明示されている。

**これ、AIに食わせたら最強のテスト設計ナレッジベースになるんじゃない？**

## 個別スキル26本は3秒で却下した

最初に考えたのは「シラバスごとにAIスキルを1本ずつ作る」案。即却下。

- **管理が破綻する。** シラバスが改訂されたら26ファイル更新するのか？
- **横断参照ができない。** FLとCTAL-TAの知識を組み合わせたいとき、2つのスキルを手動で呼び分けるのか？
- **ユーザーが迷う。** 「どのスキルを使えばいいか」で悩む時点で、ツールとして失敗している

## 1本のオーケストレーションも安直にやると失敗する

逆に「全シラバスの内容を1本のプロンプトに詰め込む」のも試した。コンテキストウィンドウに入りきらないし、入ったとしても回答が浅くなる。

「性能テストの観点を出して」と聞いたとき、FLレベルの一般論しか出ない。CT-PTの専門知識が埋もれてしまう。

## 3つのアプローチを比較する

ここまでの2案と、最終的にたどり着いた案を並べてみる。

| | 案1: 個別スキル26本 | 案2: 全部入り1本 | 案3: プロファイル標準化 |
|---|---|---|---|
| **構造** | シラバス1冊 = スキル1本 | 26冊を1プロンプトに結合 | 1スキル + 統一フォーマットのプロファイル26枚 |
| **管理コスト** | 改訂時26ファイル更新 | 1ファイルだが巨大で編集困難 | プロファイル1枚だけ差し替え |
| **横断参照** | 手動で複数スキル呼び分け | 全部入りだが深掘りできない | related_syllabiで自動横断 |
| **回答精度** | 専門性は高いが孤立 | 浅く広い | applicable_whenでルーティング → 専門知識を深く引ける |
| **ユーザー体験** | 「どれ使う？」で迷う | 1本で楽だが回答が物足りない | 1本で楽、かつ専門性が出る |
| **判定** | ✕ | ✕ | ○ |

```
案1: 個別26本             案2: 全部入り1本          案3: プロファイル標準化
┌──┐┌──┐┌──┐ ×26     ┌────────────────┐      ┌────────────────┐
│FL││TA││PT│ ...     │FL+TA+PT+AI+… │      │   1スキル       │
└──┘└──┘└──┘         │  (コンテキスト │      │  ┌──────────┐  │
                      │   溢れる)      │      │  │ Router   │  │

 × 横断参照不可         × 回答が浅い             │       ↓        │

## 「型」の力で解決する：プロファイルフォーマット標準化

解決策はシンプルで、2つの部品を掛け合わせる。

1. **シラバスプロファイル** — 各シラバスの知識を統一フォーマットで記述した「ナレッジカード」
2. **ユースケーステンプレート** — どのシラバスにも適用できる共通の思考フレーム

全シラバスを同じ構造で記述することで、1つのスキルが状況に応じて必要なプロファイルを引っ張ってこれる。

## プロファイルの5フィールド構造

各シラバスを以下の5フィールドで構造化する。

| # | フィールド | 役割 | 例（CT-AI） |
|---|---|---|---|
| ① | **core_concepts** | シラバスの「顔」。主要概念のリスト | AIテストの特異性、MLモデルの品質特性、テストデータの考慮事項 |
| ② | **learning_objectives** | K段階別の目標 | K1: AIシステムの特徴を想起できる、K3: MLモデルのテスト手法を適用できる |
| ③ | **applicable_when** | ルーティング判定キーワード | 「機械学習」「推論精度」「学習データ」「AI品質」が文脈に出たとき |
| ④ | **test_design_hooks** | テスト設計への接続点（一番大事） | viewpoints: データ品質観点、モデル精度観点、公平性観点 |
| ⑤ | **related_syllabi** | 横断参照用 | FL（基礎）、CT-PT（性能側面）、CTAL-TA（分析手法） |

**④ test_design_hooks が最重要。** ここがないと「知識としては出せるけどテスト設計に使えない」になる。

## ユースケーステンプレート4パターン

どのシラバスにも共通で使える「思考のフレーム」を4つ用意した。

| ユースケース | テンプレートがやること |
|---|---|
| **学習** | core_concepts + learning_objectivesからK段階に応じた説明を生成 |
| **テスト観点抽出** | test_design_hooks.viewpointsから観点を列挙、カタログ形式で出力 |
| **設計レビュー** | learning_objectivesに照らして設計書の充足度を評価 |
| **横断比較** | 複数シラバスのcore_conceptsを対比表で整理 |

### テスト観点抽出の例

```
入力: 「IoTデバイスのファームウェアアップデート機能のテスト観点を出して」

ルーティング:
  applicable_when に「IoT」→ CT-IoT がヒット
  「ファームウェア」→ CT-ET（組込み）も関連
  基礎として FL を常に参照

出力: 3シラバスの test_design_hooks.viewpoints を統合した観点リスト
```

## 権利・ライセンスの3ライン

JSTQBのシラバスを使う以上、越えてはいけないラインがある。

| リスク | 越えてはいけないライン | 対策 |
|---|---|---|
| **著作権** | シラバス本文の丸ごと複製 | プロファイル化（概念抽出）に留める。原文は含めない |
| **権威性の誤認** | AIの出力を公式見解と混同 | 出典明示 + 「JSTQBの公式見解ではない」を出力に必ず組み込む |
| **資格制度との衝突** | 試験対策ツール化 | 用途をテスト設計支援に限定。試験問題の生成はしない |

プロファイルに含めるのは「概念の構造化」であって「シラバス本文の引用」ではない。この線を守る。

# /jstqb — JSTQBシラバスオーケストレーター

あなたはJSTQB/ISTQBシラバスの体系的知識をベースに、テスト設計を支援するエキスパートです。

## 動作フロー

1. **入力解析**: ユーザーの質問からユースケースとキーワードを特定する
2. **シラバス選択**: 下記プロファイル一覧の `applicable_when` を照合し、関連シラバスを1〜3冊選択する
3. **テンプレート適用**: ユースケースに応じたテンプレートで回答を生成する
4. **横断統合**: 複数シラバスが選択された場合、観点を統合して出力する

## ユースケース判定

ユーザーの入力を以下4パターンに分類する：

| パターン | 判定キーワード | 出力形式 |
|---|---|---|
| **learn** | 「教えて」「とは」「違いは」「概要」 | K段階に応じた説明。K2なら概念説明、K3なら手順付き、K4なら判断基準付き |
| **extract** | 「テスト観点」「テスト条件」「何をテストする」「観点を出して」 | テスト観点カタログ形式（#/レベル/分類/大項目/中項目/小項目/観点） |
| **review** | 「レビュー」「評価」「足りてる？」「抜け漏れ」 | 充足度マトリクス＋不足観点リスト |
| **compare** | 「違い」「比較」「どっち」「使い分け」 | 対比表 |

判定に迷う場合は **extract**（テスト観点抽出）をデフォルトとする。

### extract（テスト観点抽出）の場合
```
入力された仕様・要件に対して、選択されたシラバスの
test_design_hooks.viewpoints を軸にテスト観点を抽出する。

出力形式：テスト観点カタログ
| # | レベル | 分類 | 大項目 | 中項目 | 小項目 | 観点 |

- 各観点にはどのシラバスのどの概念に基づくかを付記する
- 複数シラバスが選択された場合、観点を統合して重複を排除する
- 仕様に明示されていない暗黙の品質特性も、シラバスの知識から補完する
```

## 制約事項

- シラバスの内容を「正解」として断定しない。「JSTQBシラバスでは〜と定義されている」と出典を明示する
- プロファイルに記載のない詳細は、PDFを参照するか「シラバス本文の確認を推奨」と案内する
- ユーザーの実務コンテキスト（プロダクト特性、チーム規模、開発プロセス）に合わせてカスタマイズする
- テスト観点抽出の出力はカタログ形式を遵守する
````

## 付録B：使い方プロンプト例（コピペで使える）

スキルを構築したら、以下のように使う。`/jstqb` に続けてそのまま入力するだけ。

### テスト観点の抽出

一番使う場面。仕様書やPRDを渡して、シラバスの知識から観点を引き出す。

```
/jstqb このPRDからテスト観点を抽出して。
スマートロックのBluetooth接続→解錠→施錠のフローが対象。
モバイルアプリからの操作で、iOS/Android両対応。
```

→ CTFL（基本技法）+ CT-MAT（モバイル固有）+ CT-PT（BLE通信性能）が自動選択され、統合されたテスト観点カタログが出力される。

### 特定シラバスを指定して学習

自動選択に頼らず、シラバスを指定することもできる。

```
/jstqb CT-ATLaSの「品質アシスタンス」について教えて。
品質コーチングとファシリテーションの違いが分からない。
```

→ CT-ATLaSの learning_objectives K2レベルで、2つの概念を対比表で説明。

### テスト設計のレビュー

既存のテスト設計に対して、シラバスの知識でギャップ分析。

```
/jstqb 以下のテスト設計をレビューして。
決済APIの結合テスト設計書を添付する。
リスクベースで優先度付けしてるけど、抜け漏れがないか見てほしい。
```

→ CTAL-TA（テスト技法の網羅性）+ CTAL-TM（リスク分析の妥当性）で評価。充足度マトリクスと不足観点を出力。

### シラバス間の横断比較

勉強会やチーム内共有用。違いを整理したいときに。

```
/jstqb CTAL-TAとCTAL-TTAの守備範囲の違いを整理して。
うちのチームはどっちを先に学ぶべきか判断したい。
チームの現状：Webアプリ中心、E2Eテスト自動化済み、セキュリティテストは未着手。
```

→ 2シラバスの core_concepts 対比表 + チームの状況に合わせた学習優先度の提案。

### 実務シナリオから逆引き

シラバス名を知らなくても、やりたいことから引ける。

```
/jstqb AIを使った画像認識機能のテストってどうやればいい？
精度の評価基準とか、テストデータの作り方が分からない。
```

→ CT-AIが自動選択。学習データ品質・メタモルフィックテスト・評価指標（精度/再現率/F値）の実務適用を説明。

### 既存のテスト設計スキルとの連携

`/jstqb` の出力を後続スキルに渡すチェーン。

```
/jstqb このユーザーストーリーのテスト観点をCTFL + CTAL-TAベースで出して。

（出力されたテスト観点カタログを確認した後）

/test-analyze この観点をベースにテスト条件を構造化して。

（テスト条件を確認した後）

/test-design テストケースに展開して。
```

→ シラバスの知識 → テスト分析 → テスト設計の3段階パイプライン。各段階で人間が確認・調整できる。

## まとめ

- JSTQBシラバス26冊を個別スキル化すると管理が破綻する
- 1本の汎用スキルに全部詰め込むと回答が浅くなる
- **プロファイルフォーマットの標準化**（5フィールド構造）で、1スキルが全シラバスを高精度に扱える
- `test_design_hooks` でテスト設計の実務フローに直接接続するのがポイント
- 26冊を全部読まなくても、構造化すればAIが横断的に参照してくれる
- 権利面は「概念の構造化」に留め、原文複製と試験対策利用を避ける
