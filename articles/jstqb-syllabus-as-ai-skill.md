## 26冊のシラバス、全部読んだ人いる？

JSTQBのシラバスは2026年7月時点で26種類ある。Foundation、Advanced、Expert、さらにSpecialistが大量に。

正直、全部読んでる人は少数派だと思う。自分もそう。FL・CTAL-TAあたりは読んだけど、CT-GaMe（ゲームテスト）とかCT-AuT（自動車ソフトウェア）は「へー、あるんだ」止まり。

でもこの26冊、テスト設計の知識体系としてはめちゃくちゃ整理されてる。K1〜K4の学習目標で粒度が揃ってるし、概念間の関連も明示されてる。

**これ、AIに食わせたら最強のテスト設計ナレッジベースになるんじゃない？**

という発想から、「JSTQBシラバスをAIスキルとして使えるようにする」設計を考えた話。

## 個別スキル26本は3秒で却下した

最初に思いつくのは「シラバスごとにAIスキルを作る」案。

```
/jstqb-fl     ← Foundation Level
/jstqb-ta     ← テストアナリスト
/jstqb-ai     ← AIテスティング
/jstqb-atlas  ← 大規模アジャイル
... ×26本
```

**管理が破綻する。** シラバスが改訂されたら26ファイル更新するのか？ ユーザーが「どのスキルを使えばいいか」迷う時点で、ツールとして失敗してる。

しかもシラバス間の横断参照ができない。モバイルアプリの非機能テストを考えたいとき、CT-MAT（モバイル）とCT-PT（性能）を跨いで引ける設計じゃないとダメ。

## じゃあ1本のオーケストレーションスキルにまとめる？

「`/jstqb` 一発で全シラバスをカバーするスキルにしよう」——これも安直にやると失敗する。

汎用プロンプトで26シラバスを扱おうとすると、どのシラバスに対しても浅い回答しか出ない。LLMに「関連するシラバスを参照して答えて」と丸投げしても、的外れなルーティングや表面的な要約が返ってくるだけ。

個別だと深いけど保守が地獄。汎用だと楽だけど浅い。

## 「型」の力で解決する：プロファイルフォーマット標準化

ここで考えたのが **プロンプトテンプレートの標準化** という手法。

仕組みはシンプルで、2つの部品を掛け合わせる：

1. **シラバスプロファイル** — 各シラバスの知識を統一フォーマットで記述した「ナレッジカード」
2. **ユースケーステンプレート** — どのシラバスにも適用できる共通の思考フレーム

```
入力（ユーザーの質問）
  ↓
ルーティング（プロファイルのキーワードでマッチ）
  ↓
シラバスプロファイル × ユースケーステンプレート
  ↓
高精度な出力
```

**個別に作り込まなくても、フォーマットの力で精度が出る。** これが狙い。

## シラバスプロファイルの設計

各シラバスをこの形式で構造化する。CT-ATLaS（大規模アジャイルテストのリーダーシップ、2026年7月に日本語版が出たばかり）を例にすると：

```yaml
id: CT-ATLaS
name: 大規模アジャイルテストのリーダーシップ
level: Advanced
version: V2.0.J01

# ① 中核概念 ― このシラバスが扱う固有の知識領域
core_concepts:
  - 品質アシスタンス
  - バリューストリームマッピング
  - 組織的テスト戦略

# ② 学習目標 ― K1〜K4で何を求めているか
learning_objectives:
  K2: [品質コーチングの説明, チェンジリーダーシップの説明]
  K3: [バリューストリームマップの作成, ボトルネック特定]
  K4: [組織的テスト戦略の策定]

# ③ ルーティング判定 ― いつこのシラバスを選ぶか
applicable_when:
  keywords: [大規模, スケール, 複数チーム, SAFe, LeSS]
  scenarios: [組織横断テスト戦略, アジャイルスケーリング]

# ④ テスト設計への接続点 ― 実務で使うフック
test_design_hooks:
  viewpoints: [チーム間連携, フロー効率, 品質ゲート配置]
  techniques: [VSM分析, 品質メトリクス設計]

# ⑤ 横断参照
related_syllabi: [CTFL, CTFL-AT, CTAL-TM]
```

この5つのフィールドが肝。

**① core_concepts** はシラバスの「顔」。何を学べるかの一覧。

**② learning_objectives** はK段階別の目標。K2（説明できる）とK4（策定できる）では出力の深さを変える必要があるから、ここが精度の鍵になる。

**③ applicable_when** はルーティングの精度を決める。ユーザーの入力にこのキーワードが含まれたら、このシラバスを選ぶ。

**④ test_design_hooks** が一番大事かもしれない。シラバスの知識を「テスト設計のインプット」に変換するための接続点。ここがないと「教科書botが1つ増えた」だけで終わる。

**⑤ related_syllabi** は横断参照用。1つの質問に複数シラバスが関連するとき、ここを辿って統合する。

## ユースケーステンプレート

プロファイルの上に被せる「共通テンプレート」を4パターン用意する：

| ユースケース | テンプレートがやること |
|---|---|
| **学習**（「○○について教えて」） | `core_concepts` + `learning_objectives` からK段階に応じた説明を生成 |
| **テスト観点抽出**（「この仕様のテスト観点を」） | `test_design_hooks.viewpoints` で観点を列挙、カタログ形式で出力 |
| **設計レビュー**（「このテスト設計をレビューして」） | `learning_objectives` に照らして充足度を評価、不足観点を指摘 |
| **横断比較**（「AとBの違いは？」） | 複数シラバスの `core_concepts` を対比表で整理 |

たとえば「モバイルアプリの非機能テストを考えたい」と入力すると：

1. `applicable_when` を走査 → **CT-MAT**（モバイル）+ **CT-PT**（性能）が選択される
2. 「テスト観点抽出」テンプレート × 2シラバスのプロファイルを適用
3. CT-MATの「デバイス多様性・ネットワーク・UX」観点 + CT-PTの「負荷・ストレス・スケーラビリティ」観点が**統合されたカタログ**として出力される

個別スキルでは実現できない横断参照が、フォーマット標準化によって自然に機能する。

## なぜJSTQBシラバスとこの手法は相性がいいのか

普通のドキュメントでこれをやろうとすると「何を抽出すればいいか分からない」問題が起きる。でもJSTQBシラバスには3つの特性がある。

**K1〜K4の学習目標が構造化されている。** 「記憶する」「説明できる」「適用できる」「分析できる」のレベル分けが最初から入ってるので、`learning_objectives` にそのまま落とし込める。

**概念間の関連が明示されている。** 各シラバスが前提とする知識（FL合格が前提、等）と、関連する他のシラバスが明記されてるので、`related_syllabi` が機械的に定義できる。

**26冊すべてが同じ体系に属している。** ISTQBのスキームに沿って作られてるから、同一フォーマットで構造化しても無理が出ない。

つまり、ISTQBの体系設計がそのままAIナレッジベースの構造設計として使える。

## 実務への接続がゴール

シラバスの知識をAIスキルにしても、「テスト設計の教科書botが1つ増えた」だけでは意味がない。

`test_design_hooks` の設計次第で、既存のテスト設計ワークフローに直接接続できる：

```
PRD → /jstqb（観点抽出）→ /test-analyze（テスト条件）→ /test-design（テストケース）
```

自分のチームでは、テスト設計の前段でClaude Codeのスキル（`/test-analyze`、`/test-design`）を使ってる。そこに`/jstqb`が加わると、シラバスの知識が「読み物」ではなく「テスト設計のインプット」として機能する状態を作れる。

テストアナリストが全シラバスを暗記してなくても、プロファイルが知識を構造化して保持してくれる。チームの知識基盤として、シラバスの価値が変わる。

## まとめ

- JSTQBシラバス26冊を個別スキル化すると管理が破綻する
- 1本の汎用スキルだと浅い回答しか出ない
- **プロファイルフォーマットの標準化**（5フィールド構造）で、1スキルで全シラバスを高精度に扱える
- ISTQBの体系設計（K段階・概念構造）がそのままAIナレッジの構造として使える
- `test_design_hooks` で実務のテスト設計フローに直接接続するのがゴール

26冊を全部読まなくても、構造化すればAIが横断的に参照してくれる。テスト設計の知識基盤として、シラバスの使い方が変わるかもしれない。
