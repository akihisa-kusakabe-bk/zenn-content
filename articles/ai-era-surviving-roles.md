**AIが「実行する側」を飲み込む時代に、あなたはどこに立つか**

AIがコードを書く。AIがテストケースを生成する。AIがバグを見つける。

この流れを見て、テストエンジニアとして不安を感じたことはないでしょうか。「自分の仕事、なくなるんじゃないか」と。

結論から言います。**なくなる仕事はあります。でも、なくならない仕事もあります。**そして、テストエンジニアが持っているスキルは、実はAI時代に最も「活きる」ポジションにある——この記事では、その理由を整理します。

ソフトウェア開発の現場には、3つの主要ロールがあります。PdM（プロダクトマネージャー）、Dev（開発者）、QA（品質保証）。いわゆる「3アミーゴ」です。AI時代に、この3者のうち誰が生き残るのか。誰の仕事が最も変わるのか。

:::message
**この記事を読んでほしい人**
- 「AIに仕事を奪われるかも」と漠然と不安を感じているテストエンジニア
- リスキリングの方向性を具体的に知りたい人
- PdM・Dev・QAの役割の変化を俯瞰したい人
:::

## AIが代替するもの、しないもの

まず、AIが得意なことと苦手なことを整理します。

| AIが得意（代替が進む） | AIが苦手（人間が残る） |
|---|---|
| パターンに基づく生成・変換 | 文脈を踏まえた判断 |
| 大量データの処理・分析 | 「何が重要か」の優先順位づけ |
| 定型的な作業の自動化 | ステークホルダーとの合意形成 |
| 既知のルールに基づく検証 | 未知のリスクの察知 |

一言でまとめると、**「やる」はAIに移り、「決める」は人間に残る**。

この軸で3アミーゴを分解すると、面白いことが見えてきます。

## 3アミーゴを分解する

各ロールの業務を「AIが代替する領域」と「人間が残る領域」に分けます。

### PdM：「何を作るか」を決める人

| AIが代替する（下流） | 人間が残る（上流） |
|---|---|
| 市場調査・競合分析 | ビジョンの策定 |
| ユーザーデータの分析 | 優先順位の判断 |
| 仕様書・PRDの下書き | ステークホルダーとの調整 |
| ユーザーストーリーの生成 | 「作らない」という意思決定 |

PdMの下流作業——データを集めて整理し、文書に落とす——はAIが得意な領域です。しかし、「このプロダクトで何を守り、何を捨てるか」という判断は、ビジネス文脈と人間関係の中でしか決められません。

### Dev：「どう作るか」を実現する人

| AIが代替する（下流） | 人間が残る（上流） |
|---|---|
| コーディング | アーキテクチャ設計 |
| コードレビュー（静的解析） | 技術選定・トレードオフ判断 |
| リファクタリング | 非機能要件の設計 |
| ユニットテストの生成 | 障害対応の判断 |

Devへのインパクトは最も大きいかもしれません。AIコーディングの進化は速く、「コードを書く」行為そのものの価値が急速に下がっています。残るのは、「どういう構造で作るか」「何を選び、何を諦めるか」というアーキテクチャレベルの判断です。

### QA：「それで正しいか」を問う人

| AIが代替する（下流） | 人間が残る（上流） |
|---|---|
| テストケースの生成 | リスク判断 |
| テスト実行（自動化） | 品質戦略の策定 |
| バグレポートの作成 | 「何をテストしないか」の決定 |
| リグレッションテスト | 開発プロセスへの品質組み込み |

テスト実行やテストケース生成はAIの得意領域です。しかし、「このリリースで最もリスクが高い箇所はどこか」「このバグは出荷を止めるレベルか」という判断は、プロダクトの文脈を理解した人間にしかできません。

## 生き残るのは「ロール」ではなく「レイヤー」

ここまで見ると、答えが見えてきます。

**3者とも、「実行する側」は淘汰され、「決める側」が残る。**

```
淘汰される層：  実行する   → AIがやる
残る層：       判断する   → 人間がやる
価値が上がる層： 戦略を立てる → 人間にしかできない
```

これはロール間の生存競争ではありません。各ロールの中で、**「下流から上流へ」のシフトが起きている**という話です。

PdMもDevもQAも、下流にとどまれば淘汰される。上流にシフトすれば活きる。問われているのは「どのロールか」ではなく「どのレイヤーにいるか」です。

## それでも、QAが最も有利な理由

3者とも上流シフトが必要——それは事実です。しかし、**実はQAが最も有利なポジションにいる**と考えています。理由は4つあります。

### 1. AIが作るものを「評価する側」にいる

AIが書いたコードは、誰かが検証しなければなりません。AIが生成したテストケースは、誰かが妥当性を判断しなければなりません。

**AIが「作る側」を代替するほど、「評価する側」の需要は増える。**QAはもともと「評価する側」にいるロールです。

### 2. 横断的な視点を持っている

| ロール | 見ているスコープ |
|---|---|
| PdM | 機能単位・ビジネス価値 |
| Dev | コード単位・技術的整合性 |
| **QA** | **プロダクト全体・ユーザー体験** |

QAだけが、プロダクトを「使う人の目線」で横断的に見ています。この俯瞰力は、AIが部分的に生成したコードや機能を統合的に評価する場面で、最も必要とされます。

### 3. 「壊れる場所」を嗅ぎ分ける能力がある

経験を積んだQAには、仕様やコードの変更を見ただけで「ここ壊れそう」と感じる嗅覚があります。このリスク感覚は、明文化されたルールではなく経験に基づく直感であり、AIが再現しにくい能力の一つです。

### 4. プロセス設計の素養がある

[前回の記事](https://zenn.dev/93ch/articles/test-equals-qa)で「QA＝仕組みをつくる行為」と定義しました。この「仕組みづくり」のスキルは、AI時代にそのまま活きます。

AIが生成したコードの品質を、人手のレビューだけで担保するのは無理です。**仕組みで担保する**必要がある。CI/CDパイプラインに品質ゲートを組み込み、AIの出力を自動で検証し、リスクの高い変更を検知するフローを設計する——これはまさにQAの本領です。

## 「でも、自分はテスト実行しかやっていない」

ここまで読んで、こう思った人もいるかもしれません。

「QAが有利だと言われても、自分がやっているのはテスト実行だけ。AIに代替される側じゃないか」

その不安はもっともです。しかし、テスト実行の経験は、上流にシフトするための**最高の土台**です。

テストを実行してきた人は、「ここが壊れやすい」「この仕様は曖昧で危ない」「このパターンは見落としやすい」という感覚を既に持っています。それは上流で「リスク判断」や「品質戦略」を考えるときの、最も重要なインプットです。

足りないのは経験ではなく、**経験を言語化して上流の意思決定に使う方法**です。

実は、このシリーズで書いてきた記事は、すべてこの「言語化」を支援するために書いたものです。[テスト観点の書き方](https://zenn.dev/bitkey_dev/articles/test-viewpoint-howto)、[テスト戦略と計画の違い](https://zenn.dev/bitkey_dev/articles/test-plan-vs-strategy)、[テスト≠QAの整理](https://zenn.dev/bitkey_dev/articles/test-equals-qa)——どれも「経験はあるけど言葉にできない」を「言葉にできる」に変えるための道具です。

## リスキリングの3ステップ

テスト実行から上流へシフトするために、具体的に何をすればいいのか。3段階で整理します。

### Level 1：テスト観点を言語化する

テスト実行 → **テスト設計**へのシフト。

「なんとなくテストしている」を「なぜこの観点でテストするのか」に変える。テストケースを消化するだけの作業から、テスト観点を自分で設計する仕事へ。

具体的には：
- 画面要素から観点を抽出する
- 仕様書から名詞と動詞を分解する
- 「どうなったらまずい？」を構造化する

→ 詳しくは：[「テスト観点が書けない」を解決する——3つの壁と乗り越え方](https://zenn.dev/93ch/articles/test-viewpoint-howto)

### Level 2：リスクベースで優先順位をつける

テスト設計 → **テスト戦略**へのシフト。

「全部テストする」から「何を厚くテストし、何を薄くするか」を判断する。リスクに基づいてテストの濃淡をつけ、限られたリソースで最大の効果を出す。

具体的には：
- 「壊れたら最も困る機能」を特定する
- 過去のバグ傾向からリスクの高い領域を分析する
- テスト戦略としてチームに共有する

→ 詳しくは：[今さら聞けない「テスト計画」と「テスト戦略」の違い](https://zenn.dev/93ch/articles/test-plan-vs-strategy)

### Level 3：開発プロセスに品質を組み込む

テスト戦略 → **QA（品質保証）**へのシフト。

テストフェーズだけで品質に関与するのではなく、要件定義・設計・実装の段階から品質を組み込む。「テストする人」から「品質の仕組みをつくる人」へ。

具体的には：
- 設計レビューに「テストしやすさ」の観点で参加する
- 品質メトリクスを定義し、可視化する
- 開発チームとの品質フィードバックループを設計する

→ 詳しくは：[「テスト＝QA」を卒業する日](https://zenn.dev/93ch/articles/test-equals-qa)

### 3ステップの全体像

| Level | シフト | キーワード | 身につける力 |
|---|---|---|---|
| 1 | テスト実行 → テスト設計 | 観点の言語化 | 「何をテストするか」を自分で決められる |
| 2 | テスト設計 → テスト戦略 | リスクベース思考 | 「何を優先するか」を判断できる |
| 3 | テスト戦略 → QA | プロセス設計 | 「品質の仕組み」をつくれる |

Level 1は今日から始められます。Level 3はキャリアの方向性です。大事なのは、**今いるレベルの次を意識すること**。一気にLevel 3を目指す必要はありません。

## AI時代のQA——敵ではなく道具

最後に、一つ補足します。

この記事では「AIに代替される」という表現を使いましたが、AIはQAの敵ではありません。**最強の道具**です。

| 従来のQA | AI時代のQA |
|---|---|
| テストケースを手で書く | AIに叩き台を生成させ、人間が観点を補完する |
| 過去バグを手動で分析する | AIに傾向分析させ、人間がリスク判断する |
| テスト実行に時間を取られる | AIが実行を担い、人間は戦略と設計に集中する |

AIを「仕事を奪うもの」と見るか、「仕事を変えるもの」と見るか。その違いが、これからのキャリアを分けます。

## おわりに

「品質エンジニアが最後に残る」——この言葉が、単なる願望ではなく納得感を持って伝わっていれば嬉しいです。

AIが「作る側」を加速させるほど、「それで正しいか？」を問う側の価値は上がります。テストエンジニアとして培ってきた「壊れる場所を知っている」「ユーザー目線で見られる」「仕様の曖昧さに気づける」というスキルは、AI時代にこそ活きる力です。

ただし、活かすには上流へのシフトが必要です。テスト実行にとどまれば、それはAIに代替されます。でも、テスト観点を言語化し、リスクベースで判断し、品質の仕組みをつくる——そこに向かえば、AIはあなたの仕事を奪うのではなく、あなたの力を何倍にも増幅してくれます。

まずはLevel 1から。テスト観点を、自分の言葉で書いてみてください。
