## 3-5. どこから始めるか


| 活動 | 所要時間 |
|---|---|
| バグ分析（RCA）1件 | 30分 |
| テスト観点を3つ書き出す | 15分 |
| PRテンプレに品質項目1つ追加 | 10分 |
| ふりかえりに品質トピック1つ追加 | 5分 |


どれか1つ選んで、今週やってみる。1つだけでいい。


### 明日からできること


| 活動 | やり方 |
|---|---|
| バグパターンTOP5の作成 | 週1回30分×4週 |
| テスト観点カタログ初版 | 既存テストケースから観点を逆抽出 |
| 品質チェックリストv1 | チームで2時間のワークショップ |
| リリース後バグ率の記録開始 | リリースごとに5分の記録 |


### 1ヶ月で始められること


| 活動 | 前提 |
|---|---|
| CI/CDへの品質ゲート組み込み | ツール選定と運用ルールの合意 |
| 品質ダッシュボード構築 | メトリクスの定義とデータ収集基盤 |
| 品質定義ワークショップ | ステークホルダーの巻き込み（→[第4章](/books/testing-not-equals-qa/chapter4)） |
| テスト戦略の策定 | 品質定義とリスク分析が前提（→[第5章](/books/testing-not-equals-qa/chapter5_1)） |


カタログを見て「やりたい」と思った活動を1つ選んでほしい。来週それを試してみてほしい。


### 組織的に取り組むこと


[第2章](/books/testing-not-equals-qa/chapter2)のワークで自分のチームの負債を診断した結果を使おう。負債の種類によって、効く活動が違う。

**負債1（門番化）が重い場合 → 知識を分散させる活動から**

品質の判断が特定の人に集中しているなら、まずナレッジ共有とテスト観点カタログから始める。品質ナレッジを言語化して共有するだけで、判断の属人化が薄まる。次にCI/CDへの品質ゲート組み込みで、判断基準をコード化する。

```
1ヶ月目: ナレッジ共有（週1回のバグ共有会）
2ヶ月目: テスト観点カタログ初版
3ヶ月目: PRテンプレートに品質ゲート追加
```


**負債2（上流空白）が重い場合 → 上流に足場をつくる活動から**

上流の品質保証活動がゼロなら、まず要件レビューへの参加から始める。いきなり「品質定義ワークショップをやりましょう」と言っても通らない。小さな実績を積んでから大きな活動に進む。

```
1ヶ月目: 要件レビューに「テストできるか？」の観点で参加
2ヶ月目: 設計レビューにテスタビリティ確認を追加
3ヶ月目: リスク分析を導入（リリース前の30分ミーティング）
```


**負債3（テスト工数誤認）が重い場合 → 測り方を変える活動から**

テストケース件数だけが品質指標になっているなら、まずメトリクスの見直しから始める。リスク分析で「何を重点的にテストするか」を決め、探索的テストで「手順書の外側」を探る。

```
1ヶ月目: リリース後バグ率の記録開始
2ヶ月目: リスク分析を導入（テスト工数の配分に根拠をつける）
3ヶ月目: 探索的テストを導入（スプリント最終日の30分）
```


### 負債別の処方箋


新しい活動を始めるとき、2つの落とし穴がある。

**落とし穴1: 一度にたくさん始める**。3ヶ月のロードマップは「3つを同時に始める」のではなく「1つずつ順番に始める」。1つが定着してから次に進む。定着の目安は「意識しなくても自然にやっている状態」。

**落とし穴2: 効果を急ぎすぎる**。品質保証活動の効果は即座には見えない。要件レビューの効果が数字に出るまで2〜4スプリントかかる。メトリクスは3回分のデータが溜まって初めて傾向が読める。「1ヶ月やったけど効果がない」で止めると、効果が出る前にやめていることになる。最低3ヶ月は続けてから判断する。


### 共通する注意点


チームの品質成熟度によって、効果的な活動が違う。

**Stage 1: テスト実行だけやっている（0〜3個）**

まず「テスト以外にも品質保証活動がある」ことを知ることが第一歩だ。RCA1件、バグ共有5分から始める。成果が見えたら次の活動に進む。

| おすすめの活動 | 理由 |
|---|---|
| バグ分析（RCA） | 1件30分。すぐにできて効果が見える |
| ナレッジ共有 | 5分で始められて、チーム全体の底上げに効く |
| ふりかえりの品質トピック | 既存のふりかえりに1問追加するだけ |


**Stage 2: いくつかの活動が定着している（4〜8個）**

活動のバランスを見る。上流が空白ならリスク分析を追加。横断が弱ければテスト観点カタログを始める。

**Stage 3: 多くの活動をやっている（9個以上）**

活動の「数」から「質」にシフトする。形骸化した活動がないかチェックする。テスト戦略（[第5章](/books/testing-not-equals-qa/chapter5_1)）で全体を最適化する段階。


### チームの成長段階と活動の選び方


このカタログの14の活動は、本書の他の章で詳しく扱われる。

| 活動 | 詳細を扱う章 |

カタログで概要を掴んだら、興味のある活動の章を読んで深掘りしてほしい。

QA活動を始める前に、やるべきことがもう1つある。「うちのプロダクトにとって品質とは何か？」の定義だ。品質の定義がないまま品質保証活動を始めると、何を目指しているかわからないまま走ることになる。[第4章](/books/testing-not-equals-qa/chapter4)では、チームで品質を定義するワークショップを実践する。


### 14の活動と本書の構成の関係


:::message
**品質ゲート（Quality Gate）**
次の工程に進んでよいかどうかを判定するチェックポイント。多くの組織では「テストに通ること」だけが品質ゲートになっている。しかし本来は、要件レビュー完了、設計レビュー完了、セキュリティチェック完了なども品質ゲートになりうる。テスト以外にも品質を確認するポイントは複数あっていい。
:::


:::message
**CI/CD（Continuous Integration / Continuous Delivery）**
コードの統合とデリバリーを自動化する仕組み。開発者がコードを書き終わると、自動でテストが走り、問題がなければそのままデプロイできる状態にする。CIが統合、CDがデリバリー。手動で「テストして」「デプロイして」とやる必要がなくなる。
:::


:::message
**品質メトリクス**
品質を数値で測定・評価する指標の総称。テストケース件数やパス率もメトリクスの一種だが、それだけでは品質の全体像は見えない。バグ密度、リリース後バグ率、手戻り率など、複数の指標を組み合わせて判断するのが基本。
:::


:::message
**リスクベーステスト**
リスクの高い領域にテストリソースを集中させるアプローチ。「全部均等にテストする」のではなく「壊れたら困る場所を重点的にテストする」。テストの量ではなく、テストの配分を最適化する考え方。
:::


:::message
**RCA（Root Cause Analysis：根本原因分析）**
問題の表面的な原因ではなく、根本的な原因を特定する手法。5 Whys（なぜなぜ分析）が代表的。「なぜ？」を繰り返すことで「バグを直す」から「バグが生まれる構造を直す」へと視点が変わる。
:::


:::message
**テスタビリティ（Testability）**
ソフトウェアがテストしやすい設計になっているかの度合い。テスタビリティが高ければテストが書きやすく、バグも見つけやすい。低ければテストを書くこと自体にコストがかかる。設計段階でテスタビリティを意識することは、立派な上流のQA活動だ。
:::


:::message
**手戻り率**
開発工程で「前の工程に差し戻される」割合。要件定義の不備で設計をやり直す、設計の不備で実装をやり直す、テストで見つかったバグで実装をやり直す。手戻り率が高いほど、上流の品質が低いことを示す。30%を超えていたら、上流の品質保証活動を強化するシグナルだ。
:::


:::message
**バグ密度（Bug Density）**
コードの規模あたりのバグ件数。一般的にはKLOC（1,000行）あたりのバグ数で表す。バグ密度が高い領域は、設計の見直しやリファクタリングの候補になる。ただし、バグ密度は「テストの質」にも影響される。テストが薄い領域はバグが見つからないから密度が低い、という場合もある。
:::


:::message
**探索的テスト（Exploratory Testing）**
テスト手順書に従わず、テスターの経験と直感に基づいてソフトウェアを自由に操作しながらバグを探すテスト手法。「適当に触る」こととは異なり、テーマ（チャーター）と時間を決めて集中的に探索する。手順書では発見できないバグを見つけるのに有効。
:::


:::message
**チャーター（Charter）**
探索的テストで使うガイド。「何を」「どんな観点で」「何分間」探索するかを1〜2文で記述する。チャーターがあることで探索に方向性が生まれ、「適当に触っただけ」との差が出る。テンプレートは「[対象]の[リスク観点]を[時間]で探索する」。良いチャーターは対象を絞り、リスク観点を明確にし、30分程度の時間制約を設ける。
:::


:::message
**フレーキーテスト（Flaky Test）**
実行するたびに結果が変わる不安定な自動テスト。コードを変えていないのに、通ったり落ちたりする。原因はタイミング依存、テスト間の順序依存、環境差異など。放置するとテスト結果への信頼が崩れ、「また落ちてるけど無視していいやつ」という扱いが常態化する。CI/CDの品質ゲートを形骸化させる原因にもなる。信頼を維持するには早期の修正か隔離が必要。
:::

テスト実行は「中流×プロダクト」に位置する。1つのセルだ。このマップを見ると、テスト以外にどれだけの活動があるかが一目でわかる。


### タイミング × 対象


3つの負債それぞれに効く活動を矢印でつなぐと、こうなる。

```
負債1: 門番化 ← 設計レビュー / 品質ゲート / CI/CD / ナレッジ共有
 テスト観点カタログ / メトリクス / プロセス改善

負債2: 上流空白 ← 要件レビュー / 設計レビュー / リスク分析
 品質定義WS / バグ分析(RCA) / プロセス改善

負債3: テスト工数誤認 ← リスク分析 / テスト設計 / 探索的テスト
 テスト戦略 / メトリクス / CI/CD / プロセス改善
```


自分のチームの負債がどこにあるか（[第2章](/books/testing-not-equals-qa/chapter2)のワークで診断した結果）を見て、対応する活動から始めると効果的だ。


### 負債別マップ


2つのマップから、自分のチームの「偏り」が見える。

**タイミング×対象マップ**で空白になっているセルがあれば、そこが品質保証活動の空白地帯だ。多くのチームでは「上流×プロセス」と「上流×人」が空白になっている。テストフェーズでの品質チェック（中流×プロダクト）だけに集中している状態。

**負債別マップ**で、自分のチームの負債に対応する活動のうち「やっていないもの」を見つける。それが「次に始めるべき活動」の候補だ。

たとえば「門番化」が重いのに、ナレッジ共有もテスト観点カタログもやっていない。ならば、まずナレッジ共有から始めるのが手っ取り早い。5分で始められて、門番化の根本原因（知識の偏在）に直接効く。

マップは「全部埋める」ためにあるのではない。自分のチームの現在地と、次に進む方向を見つけるためにある。


### このマップの読み方


あるあるな話。

QAチームは、テストフェーズが始まるまで暇だ。正確には暇ではない。前のリリースのバグ修正確認をしたり、テストケースを整備したりしている。しかし、次のリリースで何がつくられるのか、どんな設計になるのかは知らない。

要件定義はプロダクトマネージャーと開発リードが進める。設計レビューは開発チーム内で閉じている。QAに情報が来るのは「開発完了」のタイミングだ。「できました。テストお願いします」。

仕様書を読む。わからないところがある。「この場合どうなりますか？」と開発者に聞く。「うーん、決めてなかったかも」。テストフェーズで仕様が決まっていく。

あるQAエンジニアが、思い切って設計レビューへの参加を申し出た。「テスト観点から見た意見を出したいので、設計レビューに参加させてもらえませんか」。開発チームの反応は意外だった。「えっ、QAの人が設計レビューに来るんですか？」。驚かれた。

参加してみると、開発チームは歓迎した。「この設計だと、こういうパターンでバグが出やすいです」「この仕様、テストするとき困りそうです」。開発者にとっては新しい視点だった。「その観点は気づかなかった。設計を直します」。

たった1回の設計レビュー参加で、テストフェーズでのリスクを3件つぶせた。3件分のバグ報告、修正、確認テストの工数が丸ごと浮いた。

QAが上流に参加するのは、QAの仕事を増やすことではない。後工程の仕事を減らすことだ。「レビューに呼ばれない」のは、QAの能力の問題ではなく、組織の慣習の問題だ。声を上げれば、扉は意外と簡単に開く。


## コラム：「レビューに呼ばれないQA」


これも、よく聞く話だ。

あるQAチームがバグ密度の計測を始めた。機能ごとにバグの件数をコード量で割って、「バグ密度が高い機能TOP5」をダッシュボードに表示した。

翌週の全体ミーティングで、その数字を共有した。「決済モジュールのバグ密度が他の3倍です」。

開発チームの空気が凍った。

決済モジュールの担当者が不機嫌な顔をしている。「自分の担当モジュールが名指しで叩かれた」と受け取ったのだ。他の開発者も気まずそうだ。「次は自分のモジュールが晒されるかも」。

ミーティングの後、開発リードからQAリードに連絡が来た。「あのダッシュボード、やめてもらえませんか。開発チームの士気が下がるので」。

メトリクスの中身は正しかった。決済モジュールのバグ密度は確かに高かった。しかし、伝え方が間違っていた。

メトリクスは「誰かを責めるため」に使うものではない。「どこに手を打つべきか」を判断するために使う。バグ密度が高い＝その領域の設計やレビュープロセスに改善の余地がある、ということだ。人の問題ではなく、プロセスの問題として扱う。

改善後のQAチームは、ダッシュボードの見せ方を変えた。「バグ密度TOP5」ではなく「品質改善の機会がある領域」として提示し、担当者名は出さず機能名だけにした。「ここを一緒に改善しませんか？」という姿勢に変えたら、開発チームの反応もまるで変わった。

メトリクスは武器にも凶器にもなる。どう使うかが問われる。


## コラム：「メトリクスを入れたら開発に嫌がられた話」


あるあるな話。

あるチームは、リリース後に同じパターンのバグが繰り返し出ていた。「金額の端数処理ミス」が半年で3回。消費税の丸め、ポイント計算の切り捨て、割引率の少数。パターンは違うが、根っこは同じ「数値計算の端数処理」だった。

3回目が出たとき、QAエンジニアがRCAをやってみた。30分、「なぜ？」を3回繰り返しただけ。

- 直接原因: 割引率の小数を切り捨てる処理が間違っていた
- なぜ？: 小数の丸め方が仕様に明記されていなかった
- なぜ？: 金額計算の端数処理ルールが組織にない
- 根本原因: 金額を扱う機能の「丸め方」を必ず仕様に書くルールがなかった

RCAの結果を開発チームに共有した。「金額計算を含む機能の要件には、丸め方（切り捨て/切り上げ/四捨五入/銀行丸め）を必ず明記する」というルールをつくった。

以降、金額の端数処理バグは0件になった。

たった30分のバグ分析で、半年間繰り返したバグパターンが消えた。バグを個別に直すだけではなく、バグが生まれない仕組みをつくること（QA）。この差が、30分の投資で生まれた。

### 棚卸しシート


**「やっている」が3個以下**: テスト実行に集中している状態。まずは★☆☆の活動（RCA、ナレッジ共有、ふりかえりの品質トピック追加）から始めよう。

**「やっている」が4〜8個**: 基盤はある。「やっていない」の中で「やりたい」がついた活動に着手すると、品質保証活動の幅が広がる。

**「やっている」が9個以上**: かなり充実している。各活動の「質」を見直すフェーズだ。[第5章](/books/testing-not-equals-qa/chapter5_1)のテスト戦略で、活動全体の最適化を考えよう。

このワークは、1人でやっても効果がある。しかし、チームメンバー全員でやると「自分たちは何をやっていて、何をやっていないか」の認識が揃う。認識のずれが見えること自体に価値がある。

「やっている」と答えた活動が、本当に機能しているかも確認してほしい。「要件レビューはやっている」と答えても、レビューの場で品質観点のコメントが出たことがないなら、やっているとは言えない。形式的にやっているのと、品質に効いているのは別の話だ。


### 振り返り


「やっている」に○をつけた活動について、以下の3問で「本当に効いているか」を確認する。

| 質問 | YES=1点 / NO=0点 |
|---|---|
| その活動の結果、実際に何かが変わったか？（バグが減った、手戻りが減った等） |  |
| その活動の成果物が、次のアクションに使われているか？ |  |
| その活動がなくなったら、チームは困るか？ |  |


3問とも YES なら、その活動は品質に効いている。1〜2問なら形骸化の兆候がある。0問なら「やっているつもり」の状態だ。

形骸化した活動は2つの選択肢がある。やり方を変えて活性化させるか、思い切ってやめるか。形だけ続けている活動は工数の無駄だ。やめた分のリソースを「やりたい」に○がついた新しい活動に振り向ける方が生産的だ。


### 深掘り：機能度チェック


**Q：テスト以外のQA活動って、開発者の仕事じゃないですか？**

設計レビューもコードレビューも開発者がやる。しかし、QAの視点で参加することと、開発者として参加することは違う。開発者は「これで作れるか」を見る。QAは「これでテストできるか」「この設計はバグを生みやすくないか」を見る。同じ会議でも、持ち込む観点が違う。開発者の仕事を奪うのではなく、開発者だけでは出てこない視点を追加する。

**Q：14個全部やらないといけないんですか？**

全部やる必要はない。3-5のロードマップで書いた通り、まず1つだけ始める。1つが定着したら次を足す。14個を同時に始めたら、どれも中途半端になる。

**Q：上司に「テスト以外のことに時間を使うな」と言われたらどうすれば？**

「テスト以外の品質保証活動でバグの作り込みを減らす」と説明する。上流で30分のレビューをすれば、後工程で3時間のバグ修正と確認テストが不要になる。投資対効果で話すと、テスト実行だけに閉じるよりも総コストが下がることを示せる。[第2章](/books/testing-not-equals-qa/chapter2)のバリー・ボームのコスト比のデータも使える。

**Q：外部のQAベンダーにもできる活動はありますか？**

テスト実行とテスト設計は委託しやすい。探索的テストも、プロダクトの知識をある程度共有できれば委託可能だ。一方、要件レビュー・品質定義・テスト戦略といった上流活動は、プロダクトの文脈を深く理解している必要がある。外部に丸投げは難しい。内製チームが上流と戦略を担い、実行を外部と分担するのが現実的な形だ。

**Q：QAチームがない小さいチームでも使えますか？**

むしろ小さいチームの方が始めやすい。合意形成に必要な人数が少ないし、プロセスの変更もすぐに試せる。QAチームという専門組織がなくても、開発者が「テスト以外の品質保証活動を1つだけ足す」だけで効果がある。RCA1件、ナレッジ共有5分。チームの規模は関係ない。

**Q：カタログにある活動を始めたけど、効果が見えません。**

効果が見えるまでには時間がかかる。要件レビューは2〜4スプリントで「テストフェーズでの手戻り減少」として効果が出始める。メトリクスは3回分のデータが溜まらないと傾向が読めない。「始めたけど効果がない」と1ヶ月で判断するのは早い。3ヶ月は続けてほしい。効果を測る指標を先に決めておくと、振り返りがしやすい。

**Q：メトリクスを導入したら開発チームに嫌がられました。どうすれば？**

メトリクスは「誰かを責めるため」ではなく「どこに手を打つか判断するため」に使う。バグ密度が高い領域を個人名ではなく機能名で表示する。「問題がある」ではなく「改善の機会がある」というフレーミングにする。開発チームと一緒にメトリクスを見て「どうすればこの数字が良くなるか」を議論する。メトリクスの導入初期に開発チームと「このデータをどう使うか」を合意しておくと、摩擦が減る。

**Q：テスト以外の活動に時間を使うと、テスト実行の時間が減りませんか？**

減る。しかし、上流の品質保証活動を行うことで、テストフェーズで見つかるバグの総数が減る。結果的に、テスト実行にかかる時間（バグ報告→確認テスト→再テストのサイクル）が短くなる。短期的にはテスト実行の時間が減るが、中長期的にはテスト全体の工数が下がる。投資と同じ構造で、今使う時間が将来の時間を節約する。

**Q：リスク分析は毎スプリントやるべき？**

毎スプリント「リスク分析会議」を開く必要はない。ただし、スプリントプランニングの中で「今回の変更でリスクが高い箇所はどこか」を5分確認する習慣は持つべきだ。本格的なリスク分析はリリース単位や四半期で十分。日常的にはリスクを「意識する」だけでも、テストの優先順位づけが変わる。

**Q：探索的テストのスキルをチームに広げるには？**

ペア探索テストが効果的。ベテランと新人がペアになり、30分の探索テストを一緒に行う。ベテランの「ここが怪しい」という勘所を、新人がリアルタイムで体験できる。言語化が難しい暗黙知を「見て学ぶ」形で伝えられる。月に1回、30分のペア探索テストを3ヶ月続ければ、チーム全体の探索テスト力が底上げされる。

**Q：活動の優先順位がつけられない。全部重要に見える**

3-5の「負債別の処方箋」を使う。[第2章](/books/testing-not-equals-qa/chapter2)のワークで診断した負債の種類によって、効く活動が違う。自分のチームの負債が門番化なら知識共有から。上流空白なら要件レビューから。テスト工数誤認ならメトリクスから。負債の種類が優先順位を決めてくれる。

**Q：テスト以外のQA活動を、スプリントにどう組み込めばいい？**

スプリントのキャパシティに「品質保証活動枠」を最初から確保する。全体の10〜15%が目安だ。2週間スプリントなら、1人あたり1日分。この枠で要件レビューへの参加、RCA、テスト観点カタログの更新などを行う。「空いた時間でやる」と決めると永遠にやらない。タスクボードに「QA活動」カラムを追加して、他のタスクと同じように可視化するのが定着のコツだ。

**Q：すでに「やっているつもり」の活動が、形骸化しているかどうか判断するには？**

3つの質問で判断する。「その活動の成果物は誰かが読んでいるか？」「その活動の結果、何かが変わったか？」「その活動がなくなったらチームは困るか？」。3つともNOなら形骸化している。ワークの「機能度チェック」シートをチームで記入してみると、メンバー間で認識がずれていることも見える。「やっている」のに成果が出ていない活動は、やめるか、やり方を変えるかの二択だ。

**Q：品質保証活動の成果をチームや上司にどう伝えればいい？**

数字で見せるのが一番早い。「要件レビューを始めて2スプリント後、テストフェーズでの仕様起因の差し戻しが5件→1件に減った」。こういう具体的なBefore/Afterがあれば、品質保証活動の投資対効果を説明できる。最初の報告は「始めました」ではなく「始めた結果、こう変わりました」のタイミングで出すと説得力がある。数字がまだないうちは「仕様の曖昧さを2件事前に潰せた」のような定性的な事実でもいい。大事なのは「やった」ではなく「やった結果、何が変わったか」を語ることだ。

**Q：このカタログの14の活動以外にもQA活動はあるの？**

ある。セキュリティテスト、パフォーマンステスト、アクセシビリティテスト、ユーザビリティテストなど、テスト種別としてのQA活動は他にも多い。このカタログは「テスト実行以外で品質に貢献する活動」に絞っている。テスト種別の話は[第5章](/books/testing-not-equals-qa/chapter5_1)のテスト戦略で扱う。また、組織によってはコンプライアンス対応やセキュリティ監査もQAの守備範囲に入る。14個は出発点であって、ゴールではない。自分のチームに必要な活動があれば、このカタログに足してほしい。

**Q：開発者がQA活動に協力的じゃない場合、どうすれば？**

いきなり「品質保証活動をやりましょう」と言っても動かない。開発者は「それをやると自分の仕事がどう楽になるか」に反応する。まずは小さな実績をつくるのがいい。たとえば、要件レビューに1回参加して「この仕様、テストフェーズで絶対聞かれますよ」と指摘する。その指摘が実際にテストフェーズの手戻りを防いだとき、開発者は「QAが上流にいると助かる」と感じる。説得より実績。1回の成功体験が、次の協力を引き出す。「品質のために」ではなく「あなたの手戻りを減らすために」という言い方に変えるだけで、反応が変わることも多い。
