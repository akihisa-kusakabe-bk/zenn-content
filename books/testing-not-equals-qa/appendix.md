## D. 本書チートシート


見開き1枚で本書の全体像がつかめる。切り取って壁に貼ってもいい。


### ① テスト / QC / QA の3層定義


```
テスト = 測る（今の状態を確認する）
QC = 診る（品質の状態を把握し制御する）
QA = 仕込む（良いものが生まれる仕組みをつくる）
```


### ② 品質サイクル


```
テストループ（測る） QCループ（診る）
 ↓ ↓
テスト設計 → 実行 バグ報告 → 原因分析
 ↑ ↓ ↑ ↓
 観点更新 ← 記録 再テスト ← 修正
 ↘ ↙
 テスト観点カタログ（ハブ）
 ↑
 QA活動（仕込む）
```


### ③ 3段階シフト


```
Step 1（今日から）: テスト実行 → テスト設計
Step 2（3ヶ月後）: テスト設計 → テスト戦略
Step 3（1年後）: テスト戦略 → QA
```


### ④ 各章の1行サマリ


```
Ch1 テストは測る、QCは診る、QAは仕込む
Ch2 混同は雪だるま式に膨らむ負債
Ch3 テスト以外のQA活動は14種類ある
Ch4 品質を定義しないと守れない
Ch5 戦略が先、計画が後
Ch6 AIが飲み込むのはレイヤー
Ch7 品質組織は「測る」から始まり「測る」に戻る
Ch8 各章ワークの精度を上げて自己コンサルする
```


### ⑤ 明日からできる3つ


```
1. 「テスト」と「QA」を使い分ける
2. バグ1件の根本原因を分析する
3. A4一枚のテスト戦略を書く
```

## F. AIでテスト設計・実行する実践ガイド


[第6章](/books/testing-not-equals-qa/chapter6)で「AIが飲み込むのはロールではなくレイヤーだ」と書いた。ここではその実践編として、AIをテスト設計・実行に活用するための考え方とプロンプト例を紹介する。


### F-1. AIに任せること・任せないことの判断基準


| レイヤー | AIに任せる | 人間がやる |
|---|---|---|
| 実行 | テストケースの実行（自動化）、テスト結果の集計、レポートの定型部分の生成 | 探索的テストの実施、ユーザビリティの主観判断 |
| 設計 | テスト観点の候補出し、テストケースのドラフト生成、テストデータの生成 | テスト観点の取捨選択、テスト戦略の策定、リスク判断 |
| 判断 | データの可視化、傾向の提示 | リリース判定、品質方針の策定、テスト戦略の意思決定 |


AIは「候補を出す」のが得意で、「選ぶ」のは人間の仕事だ。テスト観点を100個出させて35個に絞る（[第5章](/books/testing-not-equals-qa/chapter5_3)の「削る力」）。その「100個出す」をAIに任せ、「35個に絞る」を人間がやる。


### F-2. テスト設計にAIを使う


#### 仕様からテスト観点を抽出する


**プロンプト例:**

```
以下の仕様書から、テスト観点を網羅的に抽出してください。

【仕様】
{仕様書の内容をここに貼る}

【出力形式】
- カテゴリ（機能/非機能/セキュリティ/エラー処理）ごとに分類
- 各観点に「なぜこの観点が必要か」の理由を1行で

【注意事項】
- 正常系だけでなく異常系・境界値も含めること
- ユーザーの利用シナリオに沿った観点も含めること
- 「テストできそうか」は気にせず、思いつく限り出すこと
```


ポイントは最後の「テストできそうかは気にせず」だ。AIに制約を外して広く出させ、人間が実現可能性とリスクで絞る。


#### テスト観点に優先順位をつける


**プロンプト例:**

```
以下のテスト観点リストに優先順位をつけてください。

【テスト観点リスト】
{前のステップで出た観点リスト}

【品質方針】
{[第4章](/books/testing-not-equals-qa/chapter4)で策定した品質方針}

【優先順位の基準】
1. 品質方針に直結する観点を最優先
2. バグが出たときの影響が大きい観点を高優先
3. 過去に不具合が出た領域の観点を高優先
4. 重複している観点は統合

【出力形式】
- 高/中/低の3段階で分類
- 「高」は全テストサイクルで必ず実行
- 「中」はリスクに応じて実行
- 「低」はリグレッションテストから除外候補
```


品質方針を入力に含めるのがコツだ。品質方針がないと、AIは一般的な優先順位しかつけられない。[第4章](/books/testing-not-equals-qa/chapter4)で策定した品質方針が、AI活用の精度を決める。


#### テストケースを生成する


**プロンプト例:**

```
以下のテスト観点からテストケースを生成してください。

【テスト観点】
{優先順位「高」の観点リスト}

【テストケースの書き方ルール】
- 1ケースにつき1つの確認事項
- 前提条件、手順、期待結果を明記
- 手順は具体的に（「適切な値を入力する」ではなく「メールアドレス欄に test@example.com を入力する」）
- 期待結果は検証可能な形で（「正しく動作する」ではなく「ログイン後のダッシュボード画面が表示される」）

【注意事項】
- 同値分割と境界値分析を意識すること
- エラーメッセージの内容も期待結果に含めること
```


生成されたテストケースは必ず人間がレビューする。AIが生成したテストケースをそのまま実行するのは危険だ。「なぜこのテストケースが必要か」を説明できないテストケースは削除する。


### F-3. テスト実行にAIを使う


#### テスト自動化コードの生成


**プロンプト例（Playwright）:**

```
以下のテストケースをPlaywrightのE2Eテストコードに変換してください。

【テストケース】
前提条件: ユーザーがログイン画面にアクセスしている
手順1: メールアドレス欄に test@example.com を入力する
手順2: パスワード欄に ValidPass123! を入力する
手順3: ログインボタンをクリックする
期待結果: ダッシュボード画面が表示される

【技術要件】
- 言語: TypeScript
- フレームワーク: Playwright
- ページオブジェクトパターンを使用
- テストデータはfixture経由で渡す
- 待機はauto-waitingに頼り、明示的なwaitは最小限に
```


自動化コードもAIが「ドラフト」を書いて、人間が「レビュー・修正」する。ページオブジェクトの構造やテストデータの管理方法はプロジェクト固有なので、AIの出力をそのまま使えることは少ない。しかし骨格を書いてもらうだけで工数は大幅に減る。


#### 探索的テストの候補提案


**プロンプト例:**

```
以下の機能について、探索的テストのチャーターを5つ提案してください。

【機能概要】
{機能の説明}

【既知のバグパターン】
{過去に出たバグの傾向}

【チャーターの形式】
「{対象}を{操作}したとき、{確認すること}を探索する」
各チャーターに推定時間（15分/30分/60分）を付記

【重点領域】
- 通常の利用シナリオでは通らないパス
- 複数機能の組み合わせで発生する問題
- パフォーマンスやタイミングに依存する問題
```


探索的テスト自体はAIには実行できない。しかし「どこを探索すべきか」のヒントを出させることで、テスターの思考を補完できる。


### F-4. 品質分析にAIを使う


#### バグの根本原因分析


**プロンプト例:**

```
以下のバグについて根本原因分析（RCA）を支援してください。

【バグの概要】
{バグの説明}

【再現手順】
{手順}

【影響範囲】
{影響を受けるユーザー・機能}

【分析してほしいこと】
1. 「なぜ？」を5回繰り返して根本原因候補を3つ挙げる
2. 各候補について、再発防止策を提案する
3. 類似のバグが他の箇所でも起きる可能性を指摘する

【注意】
- プロセスの問題として分析すること（個人の責任追及はしない）
- 技術的な根本原因とプロセス的な根本原因の両方を検討すること
```


AIの分析はあくまで「候補」だ。実際のコードやログを見ないと確定できない。しかし「なぜ？」の深掘りを壁打ちするには便利だ。


#### 品質レポートの生成


**プロンプト例:**

```
以下のデータから品質レポートを生成してください。

【データ】
- テスト結果: {Pass/Fail/Blocked の件数}
- バグ密度: {数値}
- リリース後バグ: {件数と内訳}
- テスト観点カバレッジ: {数値}

【レポートの構成】
1. サマリ（3行以内）
2. 今週のトレンド（先週比）
3. リスク（今週見つかった懸念事項）
4. 推奨アクション（具体的に何をすべきか）

【宛先】
- サマリ: 全員
- トレンド〜リスク: QA、Dev
- 推奨アクション: PdM、マネジメント
```


定型的な集計と文面の生成はAIに任せて、人間は「数値の解釈」と「アクションの判断」に集中する。


### F-5. AIツール別の使い分け


| ツール | 得意なこと | テスト設計での活用場面 |
|---|---|---|
| ChatGPT（GPT-4o） | 自然言語での対話、長文の要約・生成 | 仕様の読み解き、テスト観点の壁打ち、レポート生成 |
| Claude | 長文のコンテキスト理解、構造的な分析 | 仕様書全体からのテスト観点抽出、RCAの深掘り |
| GitHub Copilot | コード補完、テストコード生成 | 単体テストの自動生成、E2Eテストコードのドラフト |
| Cursor / Windsurf | コードベース全体の理解、複数ファイルの修正 | テスト自動化コードの大規模リファクタリング |


どのツールを使っても基本は同じだ。**AIが「候補」を出し、人間が「判断」する**。ツールの選定よりも、「何をAIに聞くか」のプロンプト設計の方が品質に効く。


### F-6. AIスキル設計の考え方


テスト設計で繰り返す作業は、3段階で自動化できる。

| 段階 | 内容 | 例 |
|---|---|---|
| ルール | 「こう聞いたらこう返す」を文書化 | プロンプトテンプレートをチームで共有 |
| スキル | ルールをツールに組み込む | AIツールにカスタム指示を設定 |
| エージェント | スキルを自律実行させる | テスト結果を自動収集→レポート自動生成 |


いきなりエージェント化を目指さない。まずプロンプトテンプレートを3つ作って、チームで使い回す。それが安定したらスキル化する。スキルが安定したらエージェント化する。

**プロンプトテンプレート管理のコツ:**
- チームの共有ドキュメントにテンプレート集を作る
- テンプレートには「いつ使うか」「入力に何を渡すか」「出力をどう使うか」を明記
- 月1回、テンプレートの効果をチームで振り返る（使われていないテンプレートは削除）


### F-7. AIテスト設計の落とし穴


AIを品質活動に使うとき、注意すべき点がある。

| 落とし穴 | 症状 | 対策 |
|---|---|---|
| AIの出力をそのまま使う | テストケースの目的が説明できない | 「なぜこのテストが必要か」を人間が言語化してから採用 |
| 品質方針なしにAIを使う | 一般的なテスト観点しか出ない | [第4章](/books/testing-not-equals-qa/chapter4)の品質方針を入力に含める |
| AIで量を稼ごうとする | テストケースが膨大になり管理不能 | [第5章](/books/testing-not-equals-qa/chapter5_3)の「削る力」を適用。量より質 |
| AIの分析を鵜呑みにする | RCAが表面的な原因で止まる | AIの候補をたたき台に、人間がコード・ログで裏取り |
| ツール選定に時間をかける | 活動が始まらない | どのツールでもいいから今日プロンプトを1回試す |


AIは品質活動の「実行レイヤー」を加速する道具だ。品質を「仕込む」のは人間の仕事。[第1章](/books/testing-not-equals-qa/chapter1)の定義で言えば、AIはテスト（測る）の効率化に強く、QA（仕込む）は人間にしかできない。


## G. 品質活動の導入ロードマップ


本書の内容を実際に導入するための3段階ロードマップ。


### Phase 1: 今週やること（1〜7日目）


| アクション | 所要時間 | 参照章 |
|---|---|---|
| 「テスト」「QC」「QA」を意識的に使い分ける | 0分（意識するだけ） | [第1章](/books/testing-not-equals-qa/chapter1) |
| 直近のバグ1件でRCAを実施する | 30分 | [第3章](/books/testing-not-equals-qa/chapter3_2) |
| 本書のチートシート（付録D）を印刷して壁に貼る | 5分 | 付録D |


Phase 1のゴール: QA≠テストを自分の言葉で説明できる状態。


### Phase 2: 今月やること（2〜4週目）


| アクション | 所要時間 | 参照章 |
|---|---|---|
| QA活動棚卸しワークを実施する | 30分 | [第3章](/books/testing-not-equals-qa/chapter3_1) |
| 品質方針ドラフトを1人で書く | 15分 | [第4章](/books/testing-not-equals-qa/chapter4) |
| 品質定義ワークショップをチームで実施する | 90分 | [第4章](/books/testing-not-equals-qa/chapter4) |
| テスト観点を10個書き出してカタログの種を作る | 60分 | [第5章](/books/testing-not-equals-qa/chapter5_1) |
| リリース後バグ率の記録を開始する | 5分/リリース | [第3章](/books/testing-not-equals-qa/chapter3_1) |


Phase 2のゴール: 品質方針が合意され、社内チャットツールに固定されている状態。


### Phase 3: 3ヶ月後の目標


| アクション | 所要時間 | 参照章 |
|---|---|---|
| A4一枚のテスト戦略を書く | 60分 | [第5章](/books/testing-not-equals-qa/chapter5_1) |
| テスト観点カタログを50行以上に育てる | 継続 | [第5章](/books/testing-not-equals-qa/chapter5_1) |
| 品質メトリクスを3回以上記録する | 継続 | [第3章](/books/testing-not-equals-qa/chapter3_1) |
| 品質方針に基づくリリース判定を3回以上実施する | 継続 | [第4章](/books/testing-not-equals-qa/chapter4) |
| 自分の業務のレイヤー比率を確認する | 15分 | [第6章](/books/testing-not-equals-qa/chapter6) |


Phase 3のゴール: 品質サイクルが回り始めている状態。あとがきの「3ヶ月後チェックリスト」が判定基準になる。


### ロードマップの使い方


このロードマップは「上から順にやる」リストではない。自分のチームの現在地に合わせて、できるところから始める。Phase 1の3つだけでも、品質への意識が変わる。全部を完璧にやろうとして何も始められないより、1つだけ始める方がはるかに効果がある。

迷ったら、まず[第1章](/books/testing-not-equals-qa/chapter1)を読み返して「テスト/QC/QA」を使い分ける習慣をつけることだ。言葉の使い分けはコストゼロで始められる。次に[第4章](/books/testing-not-equals-qa/chapter4)の品質定義ワークショップ。チームで品質方針を1つ決めるだけで、リリース判定の景色が変わる。Phase 2まで進めば、品質活動が「属人的な頑張り」から「チームの仕組み」に変わり始める。
