:::message
この章のポイント: 各章で学んだ内容を自分のチームに当てはめるセルフコンサル・ワーク集。1人でも、チームでもできる。
:::

各章の末尾にクイック版のワークを置いた。15〜30分で「自分の現場、今どうなってる？」を可視化する内容だ。

この章では、同じテーマをもっと深くやる。各ワークにスコアリングとギャップ分析を加え、最後にアクションプランを作るところまで持っていく。自分自身の品質コンサルタントになるための道具だ。

1人でやるなら各ワーク60分。チームでやるなら90分を見てほしい。


## 8-1. 業務レイヤー分析（Ch1 + Ch6 連動）


[第1章](/books/testing-not-equals-qa/chapter1)のワーク「活動の仕分け」と、[第6章](/books/testing-not-equals-qa/chapter6)のワーク「レイヤー仕分け」を統合して深掘りする。


### Step 1: 業務の棚卸し（15分）


先週1週間の業務をすべて書き出す。ミーティングも含める。粒度は「30分以上使ったもの」で十分。

| # | 業務内容 | 所要時間 |
|---|---|---|
| 1 |  |  |
| 2 |  |  |
| 3 |  |  |
| … |  |  |
| 15 |  |  |


15個書けなくても構わない。書けるだけ書く。


### Step 2: 二軸で分類する（15分）


書き出した業務を、2つの軸で分類する。

**軸1: テスト / QC / QA（[第1章](/books/testing-not-equals-qa/chapter1)）**

| 分類 | 定義 | 例 |
|---|---|---|
| テスト（測る） | ソフトウェアの状態を観察して記録する | テスト実行、バグ報告、テスト結果の記録 |
| QC（診る） | 品質の状態を評価し、基準に照らして制御する | バグの傾向分析、影響度判定、リリース判定 |
| QA（仕込む） | 品質が生まれ続ける仕組みをつくる | テスト戦略策定、品質メトリクス設計、プロセス改善 |


**軸2: 実行 / 設計 / 判断（[第6章](/books/testing-not-equals-qa/chapter6)）**

| 分類 | 定義 | 例 |
|---|---|---|
| 実行レイヤー | 手順に従って処理する | テストケースの実行、データの入力、レポートの転記 |
| 設計レイヤー | 方法を考えて組み立てる | テスト設計、メトリクスの選定、プロセスの設計 |
| 判断レイヤー | 状況を読んで意思決定する | リリース判定、品質方針の策定、リソース配分 |


### Step 3: マトリクスに配置する（10分）


棚卸しした業務を、3×3のマトリクスに配置する。各セルに業務番号と所要時間を記入。

|  | テスト（測る） | QC（診る） | QA（仕込む） |
|---|---|---|---|
| **実行** |  |  |  |
| **設計** |  |  |  |
| **判断** |  |  |  |


### Step 4: スコアリング（10分）


各セルの合計時間を算出し、全体に占める割合を計算する。

**現状の比率**

|  | テスト | QC | QA | 合計 |
|---|---|---|---|---|
| 実行 | ___% | ___% | ___% | ___% |
| 設計 | ___% | ___% | ___% | ___% |
| 判断 | ___% | ___% | ___% | ___% |
| 合計 | ___% | ___% | ___% | 100% |


**診断基準**

| パターン | 読み方 | 次のアクション |
|---|---|---|
| テスト×実行が50%超 | テスト実行に時間を取られすぎ | 自動化 or 外部委託で実行を減らす |
| QA列がほぼ0% | 「仕込む」活動ができていない | [第3章](/books/testing-not-equals-qa/chapter3_1)の活動カタログから1つ始める |
| 実行行が70%超 | 実行に偏りすぎ。AI時代に脆い | [第6章](/books/testing-not-equals-qa/chapter6)の3段階シフトで設計・判断へ移行 |
| 判断行が30%超 | バランスが良い。次は質を上げる | [第7章](/books/testing-not-equals-qa/chapter7)の品質戦略キャンバスで精度を上げる |
| QC列が最大 | 火消しモード。負債が溜まっている | [第2章](/books/testing-not-equals-qa/chapter2)の負債診断→根本原因に手を打つ |


### Step 5: 理想比率を設定する（10分）


3ヶ月後の理想比率を書く。いきなり大幅に変えるのは現実的ではない。現状から10-15%の移動を目安にする。

**3ヶ月後の理想比率**

|  | テスト | QC | QA | 合計 |
|---|---|---|---|---|
| 実行 | ___% | ___% | ___% | ___% |
| 設計 | ___% | ___% | ___% | ___% |
| 判断 | ___% | ___% | ___% | ___% |
| 合計 | ___% | ___% | ___% | 100% |


**ギャップ = 理想 − 現状**

ギャップが最も大きいセルが、最優先で取り組むべき領域だ。

## 8-4. テスト戦略セルフレビュー（Ch5 連動）


[第5章](/books/testing-not-equals-qa/chapter5_1)のワーク「A4テスト戦略」を書いた後に、自分でレビューするためのチェックシート。


### 戦略文書の品質チェック（20分）


自分が書いたテスト戦略を以下の観点で採点する。各項目1-3点。

| # | チェック項目 | 1点（不足） | 2点（部分的） | 3点（十分） | 点数 |
|---|---|---|---|---|---|
| 1 | 品質方針との整合性 | 品質方針に言及していない | 品質方針を参照しているが具体的な対応がない | 品質方針の各項目にテスト観点が紐づいている |  |
| 2 | リスクベース | リスク分析がない | リスクの列挙はあるが優先順位がない | リスクに基づいてテストの濃淡が決まっている |  |
| 3 | 「テストしない」の明記 | テストしない範囲が書かれていない | テストしない範囲はあるが理由がない | テストしない範囲と、その判断根拠が書かれている |  |
| 4 | レイヤー分離 | テスト実行計画しかない | テスト設計とテスト実行が分かれている | 戦略→設計→実行→分析のサイクルが書かれている |  |
| 5 | 測定可能性 | 成功基準が「バグがなくなる」等の曖昧表現 | 数値目標はあるが計測方法がない | 数値目標と計測方法がセットで書かれている |  |
| 6 | 更新ルール | 更新タイミングが書かれていない | 「定期的に見直す」程度の記述 | 更新トリガーと更新プロセスが明記されている |  |


**採点基準**

| 合計 | 評価 | 次のアクション |
|---|---|---|
| 15-18 | 実用レベル。チームで運用を始められる | 1ヶ月後にこのチェックで再評価 |
| 10-14 | 骨格はある。弱い項目を補強する | 1-2点の項目を1つずつ改善 |
| 6-9 | 方向は見えている。[第5章](/books/testing-not-equals-qa/chapter5_1)を再読して書き直す | 品質方針の確認（[第4章](/books/testing-not-equals-qa/chapter4)）から再スタート |
| 6未満 | テスト計画であってテスト戦略ではない可能性 | [第5章](/books/testing-not-equals-qa/chapter5_1)の5-1「戦略と計画は違う」を読み直す |


### テスト観点の網羅性チェック（20分）


テスト観点カタログの健全性を自己診断する。

| # | チェック項目 | YES/NO |
|---|---|---|
| 1 | テスト観点が言語化されている（「何をテストするか」が文章になっている） |  |
| 2 | 各テストケースにテスト観点が紐づいている |  |
| 3 | 品質方針の各項目に対応するテスト観点がある |  |
| 4 | リスクが高い領域のテスト観点が厚くなっている |  |
| 5 | リスクが低い領域のテスト観点が意図的に薄くなっている |  |
| 6 | テスト観点の追加・削除ルールが決まっている |  |
| 7 | 最後にテスト観点を見直したのが1ヶ月以内だ |  |
| 8 | テスト観点カタログをチーム全員が参照できる |  |


YESが6個以上ならカタログは機能している。4-5個なら運用の見直しが必要。3個以下ならカタログの再構築を検討する。

### 3ヶ月後の再診断


このワークを3ヶ月後にもう一度やる。同じテンプレートで、同じ採点基準で。数値の変化が、自分の品質保証活動の成果だ。

変化がなくても落ち込む必要はない。「変化がない」こと自体が情報だ。アクションの選び方が間違っていたのか、実行が足りなかったのか、環境が変わったのか。原因を分析して次の3ヶ月の計画を立てる。

品質サイクルは、品質保証活動そのものにも適用できる。測る→直す→仕込む。自分自身の品質保証活動を、自分で品質管理する。それがセルフコンサルだ。
