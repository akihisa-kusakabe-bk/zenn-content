## 5-3. AI時代のテスト設計: 「削る力」


AIに「テスト観点を出して」と頼めば、100個出てくる。

出すのは簡単だ。対象の機能を入力して「テスト観点を網羅的にリストアップして」と指示すれば、AIはもれなく出してくれる。正常系、異常系、境界値、セキュリティ、パフォーマンス、ユーザビリティ。あらゆる角度から観点が生成される。

問題は「出す」ことではない。「削る」ことだ。

100個の観点のうち、本当に必要なのは35個かもしれない。残りの65個は、今回のテストでは不要な観点だ。不要な理由はさまざまだ。別のテストレベルでカバー済み、スコープ外、低リスク、過去に問題なし。

AIが100個出せる時代。価値があるのは「何を削るか」の判断だ。これがテスト設計力だ。


### 4ステップのプロセス


AI時代のテスト設計を4つのステップで進める。

**Step 1: AIに出させる（足し算）**

対象機能の仕様やUIを入力し、テスト観点を網羅的に生成させる。

プロンプト例:
```
以下のログイン画面のテスト観点を網羅的にリストアップしてください。
- メールアドレスとパスワードで認証
- ソーシャルログイン（Google, Apple）対応
- パスワードリセット機能あり
- 5回連続失敗でアカウントロック
```


AIは100個前後の観点を出してくる。正常系のログイン成功から、SQLインジェクション、ブルートフォース攻撃まで。この時点では「出しすぎ」でいい。漏れがある方が怖い。

AIに観点を出させるコツが3つある。

**1. 仕様を具体的に渡す**。「ログイン画面のテスト観点」だけだとAIは一般的な観点しか出せない。仕様の詳細（認証方式、入力制約、エラー処理）を渡すと、プロダクト固有の観点が出る。

**2. 過去のバグデータを渡す**。「過去にこんなバグが出ました」と伝えると、AIはそのパターンに類似した観点を追加してくれる。テスト観点カタログの「最終バグ」情報が役立つ。

**3. 複数回やる**。1回の指示で完璧な観点は出ない。最初の結果を見て「セキュリティ面がもっと欲しい」「境界値が足りない」と追加指示する。対話で磨くイメージだ。

**AIプロンプトの実践Tips**

より精度の高い観点を出すためのプロンプトテクニック。

```
あなたはシニアQAエンジニアです。
以下のECサイトの商品検索機能について、
テスト観点を以下の軸で網羅的にリストアップしてください。

【機能仕様】
- キーワード検索（部分一致）
- カテゴリ絞り込み（複数選択可）
- 価格帯フィルタ（min-max）
- 並び替え（価格順、新着順、人気順）
- ページネーション（20件/ページ）

【観点の軸】
1. 正常系（ハッピーパス）
2. 異常系（エラーケース）
3. 境界値
4. 組み合わせ（フィルタの複合条件）
5. パフォーマンス
6. セキュリティ
7. ユーザビリティ

【過去のバグ傾向】
- 全角スペースの検索でエラー
- 価格帯フィルタで0円指定時に全件表示
- 3ページ目以降のソート順が崩れる

過去のバグ傾向に類似した観点も含めてください。
```


ポイントは「過去のバグ傾向」をプロンプトに含めること。AIはパターン認識が得意なので、過去のバグに類似した観点を追加してくれる。テスト観点カタログの「最終バグ」情報がここで活きる。

**Step 2: テストレベルで分類する（整理）**

出てきた観点を、どのテストレベルで確認するかに分類する。

| テストレベル | 確認する観点の例 |
|---|---|
| 単体テスト（UT） | バリデーションロジック、パスワードハッシュ |
| 結合テスト（IT） | API認証フロー、DB参照 |
| E2Eテスト | ログイン→ダッシュボード表示の一連の流れ |
| 手動テスト | UI表示、ソーシャルログインの実機確認 |


分類することで「単体テストで確認済みの内容を結合テストでもう一度確認する」重複が見える。

**Step 3: 35個に削る（引き算）**

4つの判断基準で不要な観点を除外する。

| # | 判断基準 | 削る例 |
|---|---|---|
| 1 | 別テストレベルでカバー済み | UTで確認済みのバリデーションをE2Eで再確認 |
| 2 | スコープ外 | 今回の変更に関係ない機能のテスト |
| 3 | 低リスク | 過去3回のリリースで問題なし＋変更なし |
| 4 | 過去に問題なし | 安定している領域の網羅的テスト |


削る判断は「安全か危険か」ではなく「リスクに対してリソースが適切か」で考える。高リスク領域に薄いテストは危険。低リスク領域に厚いテストは無駄。リスクとテスト密度を対応させるのがテスト戦略の本質であり、「削る力」の使いどころだ。


### 削る判断のフローチャート


```
この観点は安全性・法規制に関わるか？
 → YES → 残す（削れない）
 → NO ↓

別のテストレベルでカバー済みか？
 → YES → 削る（UTでカバーならE2Eから削除）
 → NO ↓

今回のスコープ（変更範囲）に含まれるか？
 → NO → 削る（スコープ外）
 → YES ↓

過去3リリースでバグが出ているか？
 → YES → 残す（リスクが高い）
 → NO ↓

品質方針の上位項目に関わるか？
 → YES → 残す（戦略的に重要）
 → NO → 削る候補（優先度下げ）
```


このフローチャートを使えば、AIが出した100個の観点を機械的に仕分けできる。判断に迷う観点だけ人間が考えればいい。

削れない3条件がある。これらは残す。

- **安全性に関わるもの**: 認証・認可、個人情報の取り扱い
- **法規制に関わるもの**: コンプライアンス要件
- **過去に重大バグがあったもの**: 再発リスクが高い

**Step 4: 削った理由を残す（説明責任）**

削った観点と理由を記録する。「削った」と「忘れた」は全然違う。

| 観点 | 削った理由 | 再追加条件 |
|---|---|---|
| パスワード文字種バリデーション | UTでカバー済み | UTが廃止された場合 |
| IE11対応 | スコープ外（サポート終了済み） | ブラウザサポートポリシー変更時 |
| 負荷テスト | 低リスク（前回問題なし＋変更なし） | ログイン処理のアーキテクチャ変更時 |


削った理由を残すことで、次のスプリントで「なぜこの観点がないのか」と聞かれたときに説明できる。再追加条件を書いておけば、状況が変わったときに復活させる判断も素早くできる。

削ることは手を抜くことではない。限られたリソースを最も効果的に配分する判断だ。AIが100個出してくれるから、人間は「削る」に集中できる。出す力がAI、削る力が人間。この分業が、AI時代のテスト設計の形だ。


### 判断に迷うケースの対処法


「削るべきか残すべきか」の判断に迷うケースがある。よくある3パターンと対処法。

**迷い1: 過去にバグが1回だけ出た観点**

1回だけなら偶発的かもしれない。しかし重大なバグだった場合は残すべき。判断基準は「そのバグが再発したとき、ユーザーへの影響は大きいか」。影響が大きければ残す。小さければ削る候補にする。

**迷い2: 別チームがテストしているかもしれない観点**

「かもしれない」は危険だ。確認する。確認できないなら残す。「誰かがテストしているだろう」は品質負債の温床だ。カタログの「テストレベル」列に「別チーム確認済み」と明記できるなら、削れる。

**迷い3: 頻度は低いがリスクが高い観点**

年に1回しか実行されない機能でも、失敗したときの影響が大きければテストする。頻度×影響度のマトリクスで判断する。

|  | 影響度: 大 | 影響度: 小 |
|---|---|---|
| **頻度: 高** | 必ず残す | 残す |
| **頻度: 低** | 残す（ここが迷う） | 削る候補 |


「頻度が低くて影響度が大きい」ケースは残す。決済の障害対応フローのテストがこれに当たる。滅多に起きないが、起きたら致命的だ。


### 「削る力」のレベル


削る力にもレベルがある。

| レベル | 判断基準 | 必要な知識 |
|---|---|---|
| Lv.1 | 重複を削る | テストケースの内容を理解できる |
| Lv.2 | 別テストレベルでカバー済みを削る | テストレベル（UT/IT/E2E）の特性を理解 |
| Lv.3 | 低リスクを削る | プロダクトのリスク構造を理解 |
| Lv.4 | 「テストしない」を戦略的に決める | 品質方針・テスト戦略を理解 |
| Lv.5 | テスト戦略自体を見直す | プロダクトの成長フェーズを判断できる |


Lv.1-2はAIの支援で誰でもできる。Lv.3-5はプロダクトの文脈を知っている人間にしかできない。テスト設計力を鍛えるとは、Lv.3以上の判断ができるようになることだ。


### テスト自動化と「削る力」の関係


テスト自動化の文脈でも「削る力」は重要だ。

「全テストケースを自動化しよう」は危険な目標だ。テストケースの75%が不要だったとしたら、不要なテストケースの自動化は「効率的に無駄なことをやる」ことになる。

自動化すべきテストの選定基準:

| 自動化すべき | 手動のままでいい |
|---|---|
| 回帰テスト（毎回同じことを確認） | 探索的テスト（毎回違うことを探る） |
| データパターンが多い（100パターン以上） | パターンが少ない（5パターン以下） |
| 実行頻度が高い（毎日〜毎スプリント） | 実行頻度が低い（年1回） |
| 判定が明確（Pass/Fail） | 判定が主観的（UIの見た目） |
| 環境構築が容易 | 物理デバイスが必要 |


テスト自動化の投資対効果を最大化するには、まず「削る」。不要な観点を削った後に残った観点の中から、自動化に向いているものを選ぶ。順番は「削る→自動化」であって「自動化→削る」ではない。


### 削る判断のBefore/After


「削る力」がない状態と、ある状態を比較する。

**Before: 削る力がない**

```
PM「時間ないんだけど、テストケース何件？」
QA「300件です」
PM「全部やれるの？」
QA「全部やらないと品質が保証できません」
PM「じゃあ残業で」
```


**After: 削る力がある**

```
PM「時間ないんだけど、テストケース何件？」
QA「テスト観点ベースで整理したら120件です。
 前回300件だったのを、UTカバー済み80件、
 スコープ外60件、低リスク40件を削りました」
PM「品質は大丈夫？」
QA「テスト戦略で『テストしない領域』を明記しています。
 リスクの高い決済・認証は全件テスト。
 削ったのは低リスク領域だけです」
PM「なるほど、了解」
```


「300件を全部やる」より「120件に絞った理由を説明できる」方が、チームの信頼を得られる。


### チームで「削る力」を共有する


削る力が特定の人に属人化すると、その人がいないスプリントでテストの質が下がる。チームで共有する3つの方法。

**1. ペア削りレビュー**

AIが出した観点を、2人でペアになって削る。1人が「この観点は不要」と言い、もう1人が「なぜ？」と問い返す。判断の理由を言語化する訓練になる。

**2. 削り判断ログ**

テスト観点カタログの「削った観点」シートに、削った理由と判断者を記録する。判断の蓄積がチームのナレッジになる。新メンバーはこのログを見れば、チームの判断基準を学べる。

**3. 削り結果のふりかえり**

スプリントレトロスペクティブで「削った観点に関連するバグが出たか」を確認する。出なかったら判断は正しかった。出たら判断基準を見直す。この検証サイクルがチームの削る力を育てる。


### テスト設計力の鍛え方


「削る力」は一朝一夕には身につかない。3つの方法で鍛える。

**方法1: バグ分析の習慣**。リリース後にバグが出たら「なぜテストで見つけられなかったか」を分析する。観点が不足していたのか、テストレベルが違ったのか、そもそもリスク判断が間違っていたのか。この分析の積み重ねがリスク判断力を鍛える。

**方法2: ペアテスト設計**。テスト設計を2人でやる。1人が「この観点は必要」と主張し、もう1人が「本当に？」と問い返す。この対話が「なぜこの観点が必要なのか」を言語化する訓練になる。

**方法3: 削った結果の検証**。削った観点に関連するバグがリリース後に出たか出なかったかを追跡する。出なかったら削る判断は正しかった。出たなら、判断基準を見直す。データが蓄積されるほど、削る精度が上がる。

### この章のまとめ


[第5章](/books/testing-not-equals-qa/chapter5_1)のメッセージを3つに絞る。

**1. 戦略が先、計画が後**

テスト計画書のコピペ問題は、テスト戦略の不在が根本原因だ。A4一枚のテスト戦略を30分で書くだけで、テスト計画の質と効率が同時に上がる。

**2. テスト観点カタログが品質サイクルのハブ**

テストケースの量ではなく、テスト観点の質で品質を守る。カタログを中心にテストループとQCループを回すことで、テストが「やっつけ仕事」から「資産の蓄積」に変わる。

**3. AI時代のテスト設計力は「削る力」**

AIが100個出す時代。35個に削る判断が人間の価値だ。出す力がAI、削る力が人間。この分業がテスト設計の新しい形。

[第6章](/books/testing-not-equals-qa/chapter6)では、この分業構造をテスト設計以外の品質活動全体に広げる。「AIが飲み込むのはロールではなくレイヤーだ」。


## 用語解説


:::message
**テストレベル（Test Level）**
テストの粒度を表す分類。下から順に、UT（Unit Test / 単体テスト）→ IT（Integration Test / 結合テスト）→ ST（System Test / システムテスト）→ UAT（User Acceptance Test / 受入テスト）。上に行くほどテスト対象が大きくなり、実行コストも上がる。下のレベルで見つけられるバグを上のレベルで見つけるのは非効率。だから「どのレベルで何を確認するか」の分類が重要。
:::


:::message
**テストタイプ（Test Type）**
テストの目的別の分類。機能テスト（仕様通りに動くか）、非機能テスト（速さ・使いやすさ・セキュリティ）、回帰テスト（変更が既存機能を壊していないか）などがある。テストレベルが「どの粒度でテストするか」なら、テストタイプは「何の目的でテストするか」。
:::


:::message
**リグレッションテスト（Regression Test / 回帰テスト）**
変更が既存の機能を壊していないかを確認するテスト。新しい機能を追加したときに、既存の機能が動かなくなっていないかを確認する。自動化の効果が最も高い領域。毎回同じテストを実行するので、手動でやるよりも自動で回した方が効率的。
:::


:::message
**テストチャーター（Test Charter）**
探索的テストの目的・範囲・焦点を1〜2文で記述したガイド。「ログイン画面の異常系を30分で探索する」のように、テーマと時間を決めて探索する。手順書のように「何を確認するか」を細かく指定するのではなく、「どの方向を探るか」を示す。テスターの自由度を保ちつつ、方向性を揃えるバランスが肝。
:::


:::message
**探索的テスト（Exploratory Testing）**
テスト設計と実行を同時に行うテスト手法。手順書に従うのではなく、テスターの経験と知識に基づいて自由にソフトウェアを操作しながらバグを探す。ただし「適当に触る」こととは違い、チャーターで方向性を決め、時間を区切って集中的に行う。手順書ベースのテストでは見つけられない「想定外のバグ」を発見するのに有効。
:::


:::message
**テストピラミッド（Test Pyramid）**
テスト自動化の投資配分を示すモデル。ピラミッドの下層（単体テスト）を多く、上層（E2Eテスト）を少なくするのが理想。下層ほど実行速度が速く、メンテナンスコストが低い。逆にE2Eが大量で単体が少ない構造は「アイスクリームコーン」と呼ばれ、テスト実行が遅く壊れやすいアンチパターン。
:::


:::message
**テスト観点カタログ**
テストで確認すべき視点を一覧化したもの。テストケースより抽象度が高く、長寿命。1つの観点から複数のテストケースを導出できる粒度が適切。品質サイクルのハブとして、テストループとQCループの成果を蓄積し、次のサイクルに引き継ぐ。
:::


:::message
**テスト戦略（Test Strategy）**
テストの方針を定める文書。「何を重点的にテストするか」「何をテストしないか」「品質の判断基準は何か」を決める。テスト計画（How/When/Who）の前提となるWhy/Whatの文書。寿命が長く、四半期に1回程度の見直しで十分。
:::


:::message
**テスト終了条件（Exit Criteria）**
テストを終了してよい条件を事前に定めたもの。「全テストケースPass」だけでなく、「重大バグ0件」「カバレッジ80%以上」「探索的テストで新規バグなし」など複数の条件を組み合わせることが多い。テスト戦略の「品質の判断基準」に直接紐づく。明確な終了条件がないと、「まだテストした方がいいんじゃないか」という不安でテストが終わらない。
:::


:::message
**同値分割（Equivalence Partitioning）**
入力値を「同じ振る舞いをするグループ」に分類し、各グループから1つずつ代表値をテストする技法。例えば年齢入力なら、0〜17（未成年）、18〜64（成人）、65以上（高齢者）の3グループに分けて、各グループから1値をテストする。全値をテストする代わりに代表値だけテストすることで、テストケース数を大幅に削減できる。
:::


:::message
**境界値分析（Boundary Value Analysis）**
同値分割の境界付近の値をテストする技法。同値分割で分けたグループの境目（17と18、64と65）にバグが潜みやすいため、境界値を重点的にテストする。同値分割と組み合わせて使うことが多い。「削る力」の基礎。境界値を押さえておけば、中間値のテストは省略できる根拠になる。
:::

## AI×人間の分業マトリクス


テスト設計の各工程で、AIと人間の得意領域を整理した。


![AI×人間の分業マトリクス](/images/books/testing-not-equals-qa/diag_05_ai_human_bar.png)


パターンがある。生成（足し算）はAIが強い。判断（引き算）は人間が強い。

AIに任せすぎると、100個の観点を全部テストして工数が爆発する。人間だけでやると、観点の抜け漏れが起きる。AIが広く出して、人間が深く絞る。この分業が、テスト設計の生産性と品質を同時に上げる。


## コラム：「3年使い回しのコピペ計画書」


あるあるな話。

あるプロジェクトで、テスト計画書のレビュー依頼が来た。開いてみると、見覚えのある文面。去年のプロジェクトと同じだ。

日付と担当者名が変わっている。テスト対象のシステム名も変わっている。しかし、テストの方針、テストの範囲、テスト終了条件、つまり本質的な部分が一字一句同じだった。

よく見ると、ドキュメントの更新履歴に3年分の記録が残っていた。3年間、この計画書がコピペで使い回されていた。

なぜコピペになるのか。テスト戦略がないからだ。

テスト戦略が存在しないと、テスト計画書は毎回ゼロから書くことになる。しかし毎回ゼロから書く余裕はない。だからコピペする。コピペしても問題が起きないのは、計画書が形式的なもので、実際のテストは担当者の経験に依存しているからだ。

テスト戦略があれば、テスト計画書はスプリントごとに「今回の変更点」だけ書けばいい。方針は戦略で決まっているから、繰り返し書く必要がない。コピペの原因は怠慢ではなく、戦略の不在だ。

あるチームはこの問題に気づいた後、A4一枚のテスト戦略を30分で作った。次のスプリントから、テスト計画書は「前回の戦略に変更なし。今スプリントの変更点は以下」の1ページで済むようになった。テスト計画書の作成に2日かかっていたのが2時間になった。浮いた時間をテスト設計に使えるようになった。


## コラム：「AI観点100個で破綻した話」


あるあるな話。

あるチームがAIを導入した。テスト観点の洗い出しをAIに任せた。「ログイン機能のテスト観点を出して」と入力したら、100個出てきた。

チームは驚いた。「すごい、こんなに網羅的に出してくれるのか」。全部テストすることにした。

1週間後、テスト実行が終わらなかった。100個の観点からテストケースを作ったら300件を超えた。通常のスプリントで実行できる量ではなかった。

しかも、300件のうち本当に重要な観点が埋もれた。セキュリティに関わるテストと、UIのフォントサイズ確認が同じ優先度で並んでいた。全部やろうとしたから、優先順位がつかなかった。

結局、時間切れで未実行のテストケースが80件残った。その80件の中に、リリース後に発覚したバグの観点が含まれていた。

AIの問題ではない。削らなかった人間の問題だ。AIが出した100個を「全部やる」と決めた判断が間違いだった。

100個出せるのはAIの強みだ。しかし、100個から35個に削る判断は人間にしかできない。「出す」と「削る」を分業しないと、AIの強みが仇になる。


## コラム：「テスト観点カタログ、誰も見ない問題」


あるあるな話。

あるチームが品質改善の取り組みとして、テスト観点カタログを作った。QAリードが2週間かけて、全機能の観点を洗い出し、300行のスプレッドシートにまとめた。

完成したとき、チームは拍手した。「これで属人化がなくなる」「品質が上がる」。

3ヶ月後、カタログの最終更新日はリリース日のままだった。誰も更新していなかった。新しいバグが出ても、カタログには反映されていなかった。新機能のテストでも、カタログは参照されていなかった。

QAリードが聞いた。「なんでカタログ使ってないの？」。返ってきた答えは3つ。

「見方がわからない」。300行のシートは圧倒的で、どこから見ればいいかわからなかった。

「更新の仕方がわからない」。観点の粒度やフォーマットのルールが属人化していて、QAリード以外が書きにくかった。

「使わなくてもテストできるから」。今まで通りの方法で問題なくテストできていた。

QAリードは反省した。作り方に問題があった。1人で2週間かけて完璧なカタログを作るのではなく、チームで10分かけて50行のカタログを作るべきだった。50行なら全員が見れる。全員が書いたものなら、全員が使う。

完璧なカタログは使われない。不完全でもチームが使うカタログに価値がある。

| # | 観点 | 判断 | 理由 |

| 6 | パスワード空欄エラー | 削る | UTでバリデーションをカバー済み |
| 7 | メールアドレス形式不正 | 削る | UTでバリデーションをカバー済み |
| 14 | SQLインジェクション | **残す** | セキュリティ。削れない |
| 18 | フォントサイズ確認 | 削る | 低リスク。デザインレビューでカバー |
| 19 | ダークモード対応 | 削る | スコープ外（今回変更なし） |


### 削った結果の分析


20個の代表的な観点から、削る判断を適用するとこうなる。

| 判定 | 件数 | 内訳 |
|---|---|---|
| 残す | 12個 | 正常系3、異常系4、セキュリティ2、機能2、性能1 |
| 削る | 8個 | UTカバー済み3、スコープ外2、低リスク2、重複1 |
| 削る率 | 40% |  |


100個の全観点に同じ判断を適用すると、35〜40個に絞れることが多い。


### 削った後に確認すべき3つの問い


1. **安全性・法規制の観点が残っているか**: セキュリティ、個人情報、コンプライアンス関連は削れない
1. **品質方針の上位項目がカバーされているか**: [第4章](/books/testing-not-equals-qa/chapter4)で定義した品質方針の最重要項目に対するテストが残っているか
1. **リスクの高い変更箇所がカバーされているか**: 今回の変更でリスクが高い箇所のテストが残っているか

3つの問いすべてにYESなら、削った判断は妥当だ。


### 振り返り


削った後に残った観点が「このリリースで確認すべきこと」のリストになる。削った観点は「確認しなくていいと判断したこと」のリストになる。

どちらも意味がある。残した理由も、削った理由も、明文化されている。これがテスト設計力だ。「全部やる」では身につかない。「何を削るか」を判断する経験の積み重ねが、テスト設計力を鍛える。


## ワーク：品質サイクルの初回運用（50分）


品質サイクルを1回だけ試しに回してみるワーク。チームでやると効果的。


### 手順


**Phase 1: カタログの種をつくる（15分）**

1. 直近のスプリントで実行したテストケースを10件選ぶ
1. 各テストケースから「観点」を抽出する（1行1観点）
1. スプレッドシートに「観点ID/観点名/カテゴリ/優先度」の4列で書く

| 観点ID | 観点名 | カテゴリ | 優先度 |
|---|---|---|---|
| TP-001 | ユーザー登録の正常フロー | 認証 | 高 |
| TP-002 | パスワードの文字種バリデーション | 認証 | 中 |
| TP-003 | ... | ... | ... |


10件書けたら、カタログの種ができた。

**Phase 2: バグから観点を追加する（15分）**

1. 直近3ヶ月のバグを5件選ぶ
1. 各バグの根本原因を1行で書く
1. 「このバグを防ぐテスト観点」をカタログに追加する

| バグ | 根本原因 | 追加する観点 |
|---|---|---|
| 決済金額の不一致 | 消費税の端数処理 | 消費税計算の端数処理パターン |
| ログイン後に白画面 | セッション切れのハンドリング漏れ | セッションタイムアウト後の画面遷移 |


**Phase 3: 棚卸しシミュレーション（10分）**

Phase 1で作った10観点 + Phase 2で追加した5観点 = 15観点。この中から「削る候補」を3つ選ぶ。削る理由を書く。

**Phase 4: ふりかえり（10分）**

- カタログを作るのにかかった時間は？
- テストケースから観点を抽出するのは簡単だったか？
- バグから観点を追加するのは自然な流れだったか？
- 削る判断は迷ったか？迷ったポイントは？

このワークを1回やるだけで、品質サイクルの感覚がつかめる。次のスプリントからPhase 1〜4を正式に組み込むかどうかは、ワークの結果を見て判断する。


## FAQ


**Q：テスト戦略って誰が書くもの？**

QAリードまたはテストマネージャーが書くのが一般的。しかし、1人で書くより、PM・開発・QAで30分のミーティングをして合意するのが効果的だ。戦略は方針だから、チームで合意している方が実行に移しやすい。QA専任がいないチームでは、開発リードがテスト戦略を兼任してもいい。

**Q：探索的テストとアドホックテストの違いは？**

探索的テストはチャーター（目的と方向性）がある。「ログインの異常系を30分で探索する」。目的があり、時間が区切られ、結果を記録する。アドホックテストは「なんとなく触ってみる」。目的がなく、記録も残さない。探索的テストはスキルが要る。アドホックテストは誰でもできる。見つかるバグの質が違う。

**Q：AIに任せていい範囲はどこまで？**

生成（足し算）はAI向き。判断（引き算）は人間向き。テスト観点の列挙、テストケースの生成、テストデータの生成はAIに任せていい。リスク判断、テスト戦略の策定、品質の最終判断は人間がやる。[第6章](/books/testing-not-equals-qa/chapter6)でこの分業をもっと詳しく扱う。

**Q：テスト観点カタログはどうやって始める？**

ゼロから作る必要はない。既存のテストケースから観点を逆抽出する。テストケースを1件ずつ見て「このテストケースは何の観点で書かれたか」をラベル付けする。50件もやれば、主要な観点が見えてくる。それがカタログの種になる。

**Q：75%削減って本当に大丈夫？**

一度に75%削るわけではない。品質サイクルを回しながら、段階的に削っていく。最初は10%削ってみる。テスト結果に変化がなければ、もう10%削る。品質に影響が出たら戻す。サイクルで回すから安全に削れる。削った結果を毎スプリント検証するから、問題があればすぐに気づける。

**Q：テスト戦略はどのくらいの頻度で見直す？**

品質方針と同じタイミングで見直す。四半期に1回が目安。ただし、大きな技術変更（アーキテクチャの刷新、新しいプラットフォームへの対応）があった場合はその都度見直す。テスト計画は毎スプリント更新するが、テスト戦略は方針なので頻繁に変える必要はない。

**Q：テスト観点カタログとテストケースの違いは？**

テスト観点は「何を確認するか」。テストケースは「どう確認するか」。テスト観点「ログイン認証の正常系」から、テストケースは「メールアドレスadmin@example.comとパスワードP@ssw0rdでログインし、ダッシュボードが表示されること」になる。観点は抽象度が高いので長寿命。テストケースは具体的なので、UIが変われば書き直しになる。カタログは観点を管理する。テストケースは観点から導出する。

**Q：テスト観点カタログが大きくなりすぎたらどうする？**

四半期ごとの棚卸しで古い観点を削除する。削除基準は「6ヶ月以上バグが出ていない＋変更なし＋低リスク」。ただし安全性・法規制に関わる観点は対象外。観点の数は機能の規模に依存するが、1プロダクトあたり100〜300観点が目安。それ以上になったら粒度が細かすぎる可能性がある。

**Q：品質サイクルをスクラムのどこに組み込めばいい？**

計画・設計はスプリントプランニングの中で。テスト観点の選択に10分を使う。実行・記録はスプリント中のテスト作業そのもの。分析・評価はスプリントレトロスペクティブの品質パートとして10分。改善・更新はレトロ直後に5分。既存のスクラムイベントの中に品質サイクルを埋め込むことで、追加の会議を増やさずに回せる。

**Q：テスト設計にAIを使うと、テスト設計者のスキルが育たないのでは？**

逆だ。AIが100個出してくれるから、「出す」スキルではなく「削る」スキルを集中的に鍛えられる。100個を眺めて「これは不要」「これは必要」を判断する経験が、テスト設計力を最速で育てる。AIがなかった時代は、観点を出すことに時間を使いすぎて、「削る」判断の練習機会が少なかった。

**Q：テスト戦略とテスト計画を1つの文書にまとめてもいい？**

分けた方がいい。理由は寿命が違うからだ。テスト戦略は四半期単位、テスト計画は毎スプリント。1つの文書にすると、計画を更新するたびに戦略部分も含めた大きな文書を管理することになる。A4一枚のテスト戦略と、スプリントごとの差分テスト計画。この2本立てが軽くて回しやすい。

**Q：テスト終了条件が決まっていない場合、テスト戦略はどうする？**

テスト終了条件はテスト戦略の「③品質の判断基準」に相当する。決まっていないなら、テスト戦略を作ることが終了条件を決める契機になる。「全テストケースPass」だけでは終了条件として不十分だ。「重大バグ0件」「回帰テストPass率100%」「探索的テストで新規バグなし」など、複数の観点で終了条件を設定する。

**Q：テスト観点カタログを複数プロダクトで共有できる？**

共通の観点（セキュリティ、アクセシビリティなど）は共有できる。プロダクト固有の観点（業務ロジック、特定のAPI仕様）は共有できない。おすすめは「共通カタログ」と「プロダクト固有カタログ」の2階建て構造。共通カタログは組織全体で管理し、プロダクト固有カタログは各チームが管理する。

**Q：テスト戦略を作ったのに、チームメンバーがテスト計画書と混同してしまう**

戦略と計画の違いを「寿命」で説明するとわかりやすい。テスト戦略の更新は四半期に1回。テスト計画の更新は毎スプリント。「この文書、次のスプリントでも使える？」と聞いて、使えるなら戦略、使えないなら計画だ。物理的にもファイルを分けることを推奨する。同じフォルダに入れると、いつの間にか1つの文書にマージされがちだ。

**Q：テスト観点カタログの運用を始めたが、カテゴリの分け方で議論が紛糾する**

カテゴリは「機能領域」で分けるのが最もシンプル。認証、決済、検索、通知、管理画面のように、プロダクトの機能単位で分ける。「正常系/異常系」はカテゴリではなくテストケースの属性だ。テスト観点は「何をテストするか」の切り口なので、機能領域で分けるのが自然。最初は5カテゴリ程度で始めて、カタログが育った段階で見直せばいい。

**Q：テストケースの棚卸しを上司が許可してくれない**

「テストケースを削る」と言うと不安がられる。「テストケースの効率を上げる」と言い換えてみよう。具体的には「同じ品質を、少ないテストケースで担保する」と説明する。21.5万件→5万件に削減しても品質が変わらなかった事例を見せると、説得力がある。まずは10%の削減から始めて、結果を見せるのが効果的だ。
