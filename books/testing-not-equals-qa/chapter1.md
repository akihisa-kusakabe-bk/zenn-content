## 1-1. 第三者検証時代の違和感


第三者検証会社で働いていた頃、不思議なことに気づいた。

案件Aでは「テスター」と呼ばれ、案件Bでは「QAエンジニア」と呼ばれる。名刺の肩書は変わった。ミーティングでの紹介のされ方も変わった。でも、やっていることは1ミリも変わっていない。仕様書を受け取り、テスト設計書を書いて、テストを実行し、バグを報告する。それだけだ。

アジャイル案件では「QA」。ウォーターフォール案件では「テスト」。開発手法が変わると呼び名が変わるのに、自分たちの仕事内容はどちらも同じだった。最初はそんなものかと思っていた。むしろ「QAエンジニア」という肩書の方がかっこいいし、単価も高い。呼び名が違うだけならまあいいか、と。

ただ、アジャイルの現場は勝手が違った。開発はアジャイルでも、QAはいつも通りテスト設計から実行までやる。問題は、仕様書がないことだった。ウォーターフォールなら要件定義書や画面設計書がある。アジャイルにはそれがない。だからシステムの画面、テストオブジェクトを直接見て、テスト観点を当てて、「これでよいか？」と確認する。画面設計の概要を自分たちで書いて、そこからテスト設計をする。開発の代わりに要件定義と画面設計を書いて、ようやくテストができる状態をつくっていた。

この繰り返しを、ある案件では「テスト」と呼び、別の案件では「QA」と呼んでいた。

不思議だったのは、社内でも誰もこの矛盾を指摘しなかったことだ。ベテランのテストリーダーも、マネージャーも、営業も。「QAやってます」という言葉がクライアントへの提案資料に書いてあって、中身はテスト実行の見積もりだった。でも誰も何も言わない。自分も含めて、「そういうものだ」と受け入れていた。

転機は、第三者検証の現場に製造業の品質保証部門出身の方が増えてきた時期だった。IT業界が人手不足で、異業種からの転職者が増えていた頃のことだ。

ある日、その方に聞いてみた。「品証って、具体的に何をする組織なんですか？」

返ってきたのは、自分がやっていることとはまったく違う世界の話だった。

「前の会社の品証は、検査なんてしないよ。工程の設計をするんだ。この工程でこういう不具合が出やすいから、ここにチェックポイントを入れる。不具合の傾向を分析して、製造工程そのものを改善する。品質保証の本体は、良いモノが生まれる仕組みをつくることなんだよ」

「じゃあ、検査は誰がやるんですか？」

「検査は検査部門がやる。品証とは別だよ」

検査と品質保証が別。そんな発想は、自分の中になかった。ソフトウェアの世界では「テスト（検査）をやること＝品質保証」だと、みんなが思い込んでいたから。

検査をしない品質保証。その言葉が、頭の中でずっと引っかかった。

自分が率いる組織は「QA」を名乗っていた。でもやっていたのはテスト実行だ。名前だけが「QA」で、中身はテスト。言われてみれば当たり前のことに、何年も気づかなかった。それだけ「QA＝テスト」という等式が、自分の中にも業界全体にも浸透していたということだ。

あなたの職場ではどうだろう。テストをしている人が「QA」と呼ばれていないだろうか。テスト実行だけをしているチームが「QAチーム」を名乗っていないだろうか。求人票に「QAエンジニア募集」と書いてあって、業務内容を読むとテスト実行だけだったりしないだろうか。

もしそうだとしても、責められる話ではない。ソフトウェア業界全体がそうなっているのだから。この等式は個人の問題ではなく、業界構造の問題だ。大事なのは、その等式が本当に正しいのかを、一度立ち止まって考えてみることだ。

この本は、その「立ち止まり」を手伝うために書いた。

この違和感を解きほぐすために、誰でもわかる「たとえ」で整理してみよう。


## 1-2. 勉強のたとえで整理する


テスト、QC、QAの違いを一発で理解するために、「勉強」にたとえてみる。登壇でも一番反応がよかったたとえだ。


### テスト＝問題を解くこと


数学のテストを思い出してほしい。

問題用紙が配られる。制限時間内に解く。答案を提出する。先生が採点する。点数が返ってくる。

「あなたの今の数学の実力は、100点中65点です」

テストでわかるのは、「今の自分の状態」だ。得意なところと苦手なところ。解けた問題と解けなかった問題。テストは現在地を教えてくれる。

ソフトウェアのテストも同じ構造をしている。

| 勉強でいうと | ソフトウェアでいうと |
|---|---|
| 問題を解く | テストケースを実行する |
| 正解か不正解かわかる | Pass（成功）/ Fail（失敗）がわかる |
| 点数が出る | バグの件数・合格率が出る |
| 「65点です」 | 「テストケース200件中、15件がFail」 |


テストは「今の状態を測定する行為」だ。体温計に近い。体温計は体温を測るが、熱を下げてはくれない。テストも同じで、品質を「測定」するが、品質を「改善」はしない。

現場でよくある光景を挙げてみる。「テストケース500件実行しました。バグ30件見つかりました」。これはテストの成果報告だ。500件のテストで品質の状態がわかった。バグ30件という数字が出た。でも、この報告が出た時点では、品質は1ミリも良くなっていない。測定しただけだ。

ここが大事なポイントだ。問題を解いただけで成績は上がらない。100問解いても、200問解いても、解くだけでは学力は伸びない。テストを実行しただけでは、品質は上がらない。

この一点だけでも覚えて帰ってほしい。「テストは品質を測定するが、改善はしない」。これが本書の出発点だ。


:::message
**テスト（Software Testing）とは**
ソフトウェアが期待どおりに動くかを確認する行為。ISTQB（国際ソフトウェアテスト資格認定委員会）では「ソフトウェアの品質を評価し、運用時の故障リスクを低減するプロセス」と定義している。難しく聞こえるかもしれないが、要するに「問題を解いて答え合わせする」のと同じ構造だ。
:::


### QC（品質管理）＝成績を分析して学力の傾向を把握すること


テストが終わったら、次にやることがある。成績表の分析だ。

マルバツをつけたら終わり、ではない。成績表を分析して、どの教科が弱いのか、どんな問題で間違えやすいのか、傾向を把握する。そのうえで「この教科は赤点ギリギリだから重点的にやろう」と判断する。

これがQC（Quality Control：品質管理）だ。

| 勉強でいうと | ソフトウェアでいうと |
|---|---|
| 成績表を分析する | バグの傾向を分析する |
| 弱点の傾向を把握する | 影響度を判定する（Critical / Minor） |
| 赤点科目を特定する | リリース可否を判断する |
| 重点科目を決める | 対処の優先順位を決める |


:::message
**QC（Quality Control：品質管理）とは**
品質の状態を評価し、基準に照らして制御する活動。ISTQBでは「コンポーネントやシステムの品質を評価するために設計された一連の活動」と定義されている。本書では「診る」と表現する。バグを直すこと自体は開発活動であり、QCではない。
:::


QCは「品質の状態を診断し、制御する行為」だ。過去と現在を見ている。

テストで65点だとわかった。成績表を分析して、どの分野が弱いか傾向を把握した。「数学は計算ミスが多い」「英語は長文読解が弱い」。傾向がわかれば対策の優先順位をつけられる。「数学は赤点ラインだから最優先」「英語は平均以上だから後回し」と判断できる。

ソフトウェアの現場ではこうなる。テストでバグが見つかった。そのバグの影響度はどうか。Criticalか、Minorか。リリースを止めるべきか、次のスプリントで対処していいか。バグの傾向を分析して「認証周りにバグが集中している」とわかれば、重点的にテストを追加する判断ができる。

ここまでがQCだ。とても大事な活動だが、多くの現場はここまで到達していない。

問題は、テストで止まってしまうことだ。多くの現場は「テスト」で止まっている。テストして、バグを見つけて、開発者が直して、確認テストをする。ここまでは回している。でも、品質の傾向を分析したり、リリース判定の基準を設けたりといったQC、つまり「診る」活動まではやっていない。「勉強法を変える」ところまではなおさら踏み込んでいない。


### QA（品質保証）＝勉強の仕方そのものを改善すること


成績を本気で上げたい人は何をするか。

問題を解くことでも、答え合わせすることでもない。**勉強の仕方そのもの**を見直す。

- 朝と夜、どっちの方が集中できるだろう？
- この教科は教科書を読むより、問題集から入った方が効率いいのでは？
- そもそも、試験範囲の重点ポイントを押さえてから勉強すべきでは？
- ノートの取り方を変えたら、復習の効率が上がるんじゃないか？
- 間違いやすい問題のパターンを先に知っておけば、ケアレスミスが減るのでは？
- 友達と教え合った方が記憶に残るかもしれない

これがQA（Quality Assurance：品質保証）だ。

| 勉強でいうと | ソフトウェアでいうと |
|---|---|
| 勉強法を見直す | 開発プロセスを改善する |
| 効率の良い順番を考える | テスト戦略を設計する |
| 苦手分野を重点的にやる | リスクベースでテストを配分する |
| 間違いやすいパターンを先に知る | 過去バグの傾向分析から予防策を立てる |
| 先生に質問しやすい環境をつくる | 開発者がバグを作り込みにくい仕組みをつくる |
| 学習計画を立てる | 品質計画を策定する |


:::message
**QA（Quality Assurance：品質保証）とは**
品質の良いものが生まれる仕組みをつくる活動。JIS Q 9000（品質マネジメントシステムの国際規格）では「品質要求事項が満たされるという確信を与えることに焦点を合わせた品質マネジメントの一部」と定義されている。ポイントは「確信を与える」という言葉。テストを実行することではなく、品質が担保される仕組みそのものを指す。
:::


QAは「良いものが生まれる仕組みをつくる行為」だ。未来を見ている。

ポイントは「仕組み」という言葉だ。QAがつくるのは、個別の問題への対処ではなく、仕組みだ。たとえば勉強なら、「毎朝6時に起きて30分復習する習慣」「間違いノートをつけて、テスト前に見返すルーティン」「わからない問題は翌日までに先生に質問するルール」。仕組みは個人の頑張りに依存しない。誰がやっても、一定の品質が保てる状態をつくることが、QAの本質だ。

テストは「今、65点だ」を知ること。QCは「間違えた問題を直して、次は解けるようにする」こと。QAは「そもそも80点が取れる勉強法に変える」こと。

見ている時間軸がまったく違う。テストとQCは「起きたこと」に反応している。QAは「これから起きること」に備えている。


### 3つの違いを一枚で


整理するとこうなる。


![テスト/QC/QAの関係](/images/books/testing-not-equals-qa/fig_01_venn.png)


```
テスト → 測る → 「今どうなっているか」を知る
QC → 診る → 「品質の状態」を把握し制御する
QA → 仕込む → 「問題が起きにくい状態」をつくる
```


テストはQAの一部だ。QCもQAの一部だ。しかし、QA＝テストではない。

テストだけをもって「QAやっています」というのは、問題を解いただけで「勉強しています」というようなものだ。答え合わせも、勉強法の改善もしていないのに。

ここで自分の現場を振り返ってみてほしい。あなたのチームは3つのうちどこまでやっているだろうか。

- テストだけ（問題を解いているだけ）
- テスト＋QC（品質の傾向を分析し、判断している）
- テスト＋QC＋QA（勉強法を見直している）

多くの現場は「テスト」で止まっている。テストして、バグを見つけて、開発者が直して、確認テストをする。ここまでは回している。でも、品質の傾向を分析したり、リリース判定の基準を設けたりといったQC、つまり「診る」活動まではやっていない。「なぜそのバグが生まれたのか」「どうすれば次は防げるのか」「そもそもテストの仕方自体を見直すべきでは」という問いは出てこない。

「テストしかしていない」ことに気づいても、落ち込む必要はない。認識することが、卒業への第一歩だ。他の業界ではこの段階をとっくに卒業しているし、ソフトウェア業界もこれから卒業できる。


### テスト以外のQA活動の例


「QA＝仕組みをつくるって、具体的に何をするの？」と思っただろう。ここでは予告だけしておく。[第3章](/books/testing-not-equals-qa/chapter3_1)で14種類のQA活動を体系的に紹介する。

| 活動 | 一言で |
|---|---|
| 要件レビュー | 仕様の曖昧さを開発前に潰す |
| リスク分析 | 壊れやすい場所を予測する |
| テスト戦略策定 | 何をテストし、何をテストしないか決める |
| プロセス改善 | バグが生まれにくい開発フローをつくる |
| 品質メトリクス | 品質の状態を数字で見える化する |


「テストの先」にはこれだけの活動がある。テストケースを増やすだけが品質保証活動ではない。


## 1-3. 他業界の品質保証との比較


「QA＝テスト」という等式は、ソフトウェア以外の業界ではとっくに否定されている。いくつか見てみよう。ソフトウェア業界だけが特殊なのだとわかるはずだ。


### 製造業：60年前に卒業している


日本の製造業は、品質管理の歴史そのものだ。

1950年、W・エドワーズ・デミングが来日し、統計的品質管理（SQC：Statistical Quality Control）の講演を行った。翌1951年にはデミング賞が創設された。ここから日本の品質管理運動が始まる。

初期のQCは「検査」だった。製品が完成したら検査員が1つずつチェックし、不良品を取り除く。学校のテストと同じ構造だ。

しかし、この方法には限界があった。検査員を増やしても、検査項目を増やしても、不良品の発生率そのものは下がらない。なぜなら、不良品が生まれる製造工程そのものは何も変わっていないからだ。出荷前に不良品を弾いているだけで、不良品は作り続けている。検査のコストばかりが膨らみ、品質は頭打ちになった。

この気づきから、品質管理は大きく進化した。QC（品質管理）からTQC（Total Quality Control：全社的品質管理）へ。さらにTQM（Total Quality Management：総合的品質マネジメント）へ。「品質は工程で作り込む」という思想が広まった。

トヨタ生産方式の「自工程完結」はまさにこの思想を体現している。後工程の検査で不良を見つけるのではなく、各工程が自分の工程で品質を確保する。品質保証は最後の検査ではなく、ものづくりのプロセス全体に組み込まれている。

製造業は60年以上前に「検査＝品質保証」を卒業した。検査を増やしても品質は上がらないと、半世紀以上前に結論が出ている。


### 医療：治療だけが医療ではない


病気になったら病院に行く。医師が診察して、診断を下して、治療する。

これが医療のすべてだろうか。もちろん違う。

予防接種、健康診断、生活習慣の指導、公衆衛生、感染症対策、医療制度設計、疫学研究。治療は医療のほんの一部だ。

WHO（World Health Organization：世界保健機関）は健康を「病気でないことだけではなく、身体的・精神的・社会的に良好な状態」と定義している。「病気を見つけて治す」のは、健康のための活動のごく一部に過ぎない。

「患者を治すことだけが医療だ」と言ったら、医療関係者は困惑するだろう。そもそも病気にならない仕組み（予防医療）の方が、よほど多くの命を救っている。

ソフトウェアに置き換えると、バグを見つけて直すのは「治療」にあたる。大事な活動だが、それだけでは品質保証とは呼べない。そもそもバグが生まれにくい環境をつくること（予防）、品質の基準を定義すること（健康の定義）、開発プロセス全体を設計すること（医療制度設計）も含めて、品質保証だ。


### 航空：仕組みで安全をつくる


航空業界は、世界で最も安全な輸送手段と言われている。100万フライトあたりの事故率はわずか0.2件ほどだ。

この安全は、どう実現されているのか。「検査を厳しくする」ことではない。

航空業界は事故が起きたとき、パイロット個人を責めない。NTSB（National Transportation Safety Board：国家運輸安全委員会）が事故調査報告書を作成し、業界全体に公開する。事故の原因を個人のミスに帰属させるのではなく、システムの問題として捉える。

この仕組みからCRM（Crew Resource Management）が生まれた。パイロット一人の判断に頼るのではなく、乗務員全員が声を上げられる環境をつくる。結果、航空事故率は数十年で劇的に下がった。

ポイントは「事故後の検査を厳しくする」のではなく、「事故が起きにくい仕組みをつくる」ことで安全を守っている点だ。フライト前のチェックリスト（テスト）は今も毎回やる。でも、それだけが安全の根拠ではない。組織全体で安全を作り込む仕組みがあるから、あれだけの安全性を維持できている。


### 飲食業：食中毒は検査では防げない


もう1つ身近な例を。

飲食店の衛生管理を考えてみよう。料理を提供する前に、すべての皿を検査して「この一品は安全です」と判定するだろうか。そんなことはしない。

やっているのは、調理工程そのものの管理だ。食材の温度管理、調理器具の洗浄手順、調理スタッフの手洗いルール、保存温度と保存期間のルール。HACCP（Hazard Analysis and Critical Control Point：危害要因分析重要管理点）という仕組みは、「どの工程にどんなリスクがあるか」を分析し、重要な管理ポイントを定めて監視する手法だ。

検査（テスト）は最終確認にすぎない。食中毒を防いでいるのは、工程管理という「仕組み」だ。

ソフトウェアに置き換えると、リリース前のテストは最終確認。バグを防いでいるのは、設計レビュー、コードレビュー、CI/CD、テスト戦略という「仕組み」のはずだ。しかし多くの現場では、仕組みがなく、最終確認のテストだけで品質を守ろうとしている。


### ソフトウェアだけが止まっている


製造業は検査から仕組みへ。医療は治療から予防へ。航空は個人の責任からシステムの改善へ。飲食業は出荷検査から工程管理へ。

どの業界も、同じ方向に進化してきた。「問題を見つけて対処する」だけでは品質は守れないことに気づき、「問題が起きにくい仕組みをつくる」方向へシフトした。気づいた時期は違うが、到達した結論は同じだ。検査（テスト）は品質保証活動の一部であり、全部ではない。

年表にすると、このシフトの遅れが目に見える。

| 年代 | 製造業 | 医療 | 航空 | ソフトウェア |
|---|---|---|---|---|
| 1950年代 | 統計的品質管理 | — | — | — |
| 1960年代 | TQCへ | 臨床治験制度 | 事故報告制度 | テスト概念登場 |
| 1980年代 | TQMへ | EBMへ | CRM導入 | 構造化テスト |
| 2000年代 | リーン生産 | 安全の仕組み化 | SMS義務化 | アジャイルテスト |
| 2020年代 | AI品質管理 | 予防医療DX | 予測保全 | QA＝テストまま |


ソフトウェア業界は「テストの技法」は進化してきた。ウォーターフォール型のテストからアジャイルテストへ、手動テストからテスト自動化へ。テストの「やり方」は確かに進歩している。

しかし「QA＝テスト」という認識は、進歩していない。テスト技法がどれだけ高度になっても、品質保証活動がテスト実行に閉じている限り、他業界が数十年前に到達した「仕組みで品質を守る」段階には追いつかない。

他の業界が60年前に卒業した段階に、ソフトウェアはまだいる。

では、「QA＝テスト」が定着した現場には、具体的にどんな症状が出ているのか。


## 1-4. 現場で見る「QA＝テスト」の4症状


「QA＝テスト」の等式が成り立ったままの現場には、共通した症状が現れる。4つ挙げる。心当たりがいくつあるか、数えながら読んでみてほしい。


### 症状1：テストケースは増えるが品質は変わらない


あるプロジェクトの話。リリースのたびにテストケースを追加している。バージョン1.0のときは500件だったテストケースが、バージョン3.0では2,000件になった。テストにかかる時間も、1週間から3週間に伸びた。

で、品質は良くなったか。

バグの傾向は変わっていない。ユーザーからの問い合わせも減っていない。むしろ「テストに時間がかかりすぎてリリースが遅れる」という新しい問題が増えた。

勉強のたとえに戻そう。問題を解く量は増えている。1日30問だったのが100問になった。でも、勉強法は変えていない。間違えた原因を分析していない。苦手分野を重点的にやっていない。100問解いても200問解いても、やり方が同じなら成績は変わらない。

テストケースの数は、品質の指標ではない。テストケースが増えているのに品質が変わらないなら、問題はテストの量ではなく、テストの質だ。何を測るか、なぜ測るか、測った結果をどう使うか。そこを考えるのがQAエンジニアの仕事であり、テストケースを増やし続けるのとは根本的に違う。


### 症状2：同じパターンのバグが繰り返される


「またこの手のバグか」

この一言が、チームの会話に頻繁に出てくる。入力値のバリデーション漏れ。画面遷移時の状態リセット忘れ。APIのエラーハンドリング不足。NULL参照。日付のタイムゾーン問題。毎回似たようなバグが出て、毎回直して、毎回確認テストをして、次のリリースでまた同じパターンが出る。

答え合わせまではしている。「このバグの原因はここだ」「修正した」「確認テストした」。QCは回っている。

でも、根本的な原因に手をつけていない。「なぜ、バリデーション漏れが繰り返されるのか？」「コードレビューのチェックリストに入っていないのか？」「そもそも、入力バリデーションの共通ライブラリを作れば防げるのでは？」「開発者にバリデーションの重要性を共有する場があるか？」

個別のバグは直している。でも、バグが生まれる構造は直していない。だから同じパターンが繰り返される。

勉強でいえば、同じタイプの問題で毎回間違えているのに、毎回「あ、また間違えた」で終わっている状態だ。「自分はこのタイプの問題が苦手だ」と認識して、そのタイプの問題を集中的に練習する。それが勉強法の改善であり、QAの発想だ。


### 「直した」と「防いだ」の違い


症状2をさらに掘り下げる。

「バグを直す」と「バグを防ぐ」は似ているようで、まったく違う活動だ。

|  | バグを直す（個別対処） | バグを防ぐ（QA） |
|---|---|---|
| 対象 | 今見つかったバグ1件 | 同じパターンのバグすべて |
| 時間軸 | 過去→現在 | 現在→未来 |
| やること | 原因を特定し修正する | 原因が生まれない仕組みをつくる |
| 例 | NULLチェック漏れを修正する | NULLチェックをlintルールに追加する |
| 効果の範囲 | この1件だけ | 今後の全コードに適用 |


バグ1件を直す作業時間は30分かもしれない。NULLチェックのlintルールを追加する作業時間も30分かもしれない。同じ30分でも、効果の範囲がまるで違う。前者は1件を直す。後者は、同種のバグが二度と生まれない状態をつくる。

「忙しいから直すだけで精一杯」という声はよく聞く。しかし、直すだけで終わると、来月また同じバグを直している。「直す30分」を繰り返すより、「防ぐ30分」を1回やる方が、トータルの時間は短くなる。


### 症状3：リリース直前にしか品質の話をしない


「テストフェーズ」が始まるまで、品質について誰も話さない。

要件定義のとき。「この要件、テストしやすい形で書けているか？」という問いは出ない。設計のとき。「この設計だと、このパターンのバグが作り込まれやすいのでは？」という指摘はない。実装のとき。「このコードは後からテストしにくい構造になっていないか？」という確認もない。

テストフェーズになって初めて、「バグが多い」「品質が低い」「リリースに間に合わない」という会話が始まる。

QA＝テストだと思っていると、テストフェーズでしか品質に関われない。品質保証活動の入口がテストしかないから、テスト以前の工程で品質を作り込む機会を逃す。

勉強のたとえでいうと、試験前日にしか勉強しない学生だ。授業中にノートを取らない。宿題もやらない。試験前日に慌てて教科書を開く。範囲が多すぎて全部はカバーできない。ヤマを張って、当たるかどうかは運任せ。

品質の話がリリース直前にしか出ない現場は、構造的に品質が後手に回る。「テストフェーズでなんとかする」は「試験前日になんとかする」と同じで、なんとかならない確率が高い。

しかもこのパターンは自己強化する。テストフェーズで大量のバグが見つかる → 修正で手一杯になる → テスト以前の工程を改善する余裕がない → 次のリリースも同じことが起きる。忙しいからこそ改善する時間が取れない、という悪循環だ。


### 症状4：QAチームがテスト実行チームになっている


「QAチーム」という名前がついている。でも、やっていることはテスト実行と不具合報告だけ。テスト戦略の策定。なし。プロセス改善の提案。なし。品質メトリクスの分析。なし。開発プロセスへのフィードバック。なし。

名前は「QA（品質保証）」だが、実態は「テスト実行」だ。

1-1で書いた、自分自身の経験そのものだ。名刺には「QAエンジニア」と書いてあるのに、渡されるのはテスト手順書。やっているのは手順書の消化。チーム全員がそうで、チーム全員がそれを「QA」だと思っている。新しく入った人も、半年もすればその等式に染まる。

厄介なのは、この状態が「問題」として認識されないことだ。テストをしていること自体は間違いではないし、バグを見つけて報告していること自体は価値がある。だから「仕事はちゃんとやっている」という実感がある。毎日忙しいし、バグもたくさん見つけている。成果は出ている。

でも、本来やるべきQA活動の大部分が抜け落ちている。テスト実行は氷山の一角であって、水面下にあるべき品質保証活動がごっそり欠けている。

- テスト戦略の策定
- 品質メトリクスの計測と分析
- 開発プロセスへのフィードバック
- リスクベースのテスト配分
- 品質目標の定義

これらはQAの名を冠するチームが本来担うべき活動だが、テスト実行に追われて手が回らない。あるいは、そもそもそういう活動が「QAの仕事」だと認識されていない。


### 4症状の共通点


4つの症状に共通しているのは、「テストの先がない」ことだ。

テストケースは増やしている。バグは見つけて直している。でも、テストの結果を分析して仕組みに反映する活動がない。テスト以前の工程に品質を組み込む活動がない。品質の定義すらない。

勉強のたとえでいえば、「問題を解いて、答え合わせして、間違いを直して」を繰り返してはいるが、「そもそもどう勉強すれば効率がいいか」を考えていない状態だ。一生懸命やっているのに成績が伸びない。足りないのは努力の量ではなく、方向だ。


### セルフチェック


4つの症状のうち、いくつ当てはまっただろうか。

- テストケースは増えるが品質は変わらない
- 同じパターンのバグが繰り返される
- リリース直前にしか品質の話をしない
- QAチームがテスト実行チームになっている

1つでも心当たりがあれば、「QA＝テスト」の等式がどこかに潜んでいる。3つ以上なら、かなり深く定着している。


### 症状の深刻度を測る


4つの症状がどの程度進行しているか、もう少し詳しく見てみよう。

| レベル | 状態 | 典型的なサイン |
|---|---|---|
| Lv1: 無自覚 | QA＝テストが当たり前。疑問を感じていない | 「うちのQAはちゃんと仕事してますよ」（テスト実行のことを指して） |
| Lv2: 違和感 | 何かおかしいと感じているが言語化できない | 「テストケースは増やしてるのに、なんで品質が上がらないんだろう」 |
| Lv3: 認識 | テストとQAが違うことを知っているが、行動に移せていない | 「テスト以外のQA活動が必要なのはわかる。でも時間がない」 |
| Lv4: 行動 | テスト以外のQA活動を始めている | 「先月からバグのパターン分析を始めました」 |


この本を手に取った時点で、Lv2以上にはいる。Lv2からLv3へ進むために、この本の[第1章](/books/testing-not-equals-qa/chapter1)〜[第3章](/books/testing-not-equals-qa/chapter3_1)で言葉と知識を手に入れる。Lv3からLv4へ進むために、[第4章](/books/testing-not-equals-qa/chapter4)〜[第7章](/books/testing-not-equals-qa/chapter7)で実践の道具を手に入れる。

心当たりがあっても焦らなくていい。この本は「QA＝テストをやめましょう」と説教するための本ではない。「テストの先にある世界」を一緒に見に行く本だ。

ここまでの症状は、表面に出ている兆候に過ぎない。放置するとどうなるか。この等式は組織に雪だるま式に蓄積する「構造的負債」を生む。[第2章](/books/testing-not-equals-qa/chapter2)では、その負債の正体を見ていく。


## 用語解説


:::message
**テスト（Software Testing）**
ソフトウェアが期待どおりに動くかを確認する行為。本書では「測る」と表現する。テストは品質を「測定」するが、テストだけでは品質は「改善」しない。体温計は体温を測るが、熱を下げてはくれない。テストもそれと同じだ。この違いが本書全体を貫くテーマになる。
:::


:::message
**QC（Quality Control：品質管理）**
品質の状態を評価し、基準に照らして制御する活動。本書では「診る」と表現する。「成績を分析して学力の傾向を把握する」に相当する。過去と現在を見ている活動で、品質の状態を把握し制御することに焦点を当てる。バグを直すこと自体は開発活動であり、QCではない。QCとQAは別物だ。
:::


:::message
**QA（Quality Assurance：品質保証）**
品質の良いものが生まれる仕組みをつくる活動。本書では「仕込む」と表現する。「勉強の仕方そのものを改善する」に相当する。未来を見ている活動で、テスト戦略の設計、プロセス改善、品質メトリクスの定義と計測がここに含まれる。テストやQCを「含む」上位概念であり、QA＝テストではない。
:::


:::message
**第三者検証**
開発元とは別の組織がソフトウェアのテストを行うこと。第三者の客観的な視点でテストすることで、開発者自身では気づきにくい不具合を発見できるメリットがある。日本では第三者検証を専門に行う企業が多数存在する。ただし、「第三者がやる＝品質保証」ではない点に注意。テスト実行を外部に委託しているだけの場合もある。
:::


:::message
**ISTQB（International Software Testing Qualifications Board）**
ソフトウェアテスト技術者の国際的な資格認定組織。日本ではJSTQB（Japan Software Testing Qualifications Board）が窓口となっている。Foundation Level（基礎レベル）の資格は、テストの基本概念を体系的に学ぶのにちょうどいい。本書の内容とも重なる部分が多いので、興味があればチャレンジしてみてほしい。
:::


:::message
**リグレッションテスト（回帰テスト）**
バグを修正した後や、新しい機能を追加した後に、既存の機能が壊れていないかを確認するテスト。「直したつもりが別のところを壊していた」を防ぐために行う。勉強でいえば「新しい単元を勉強した後に、前の単元を忘れていないか確認する」ようなもの。
:::


:::message
**テストケース**
テストの具体的な手順と期待結果をセットにしたもの。「ログイン画面でメールアドレスとパスワードを入力して、ログインボタンを押すと、マイページが表示される」のような形で書かれる。テスト実行の最小単位であり、テストケースの件数がテスト規模の目安として使われることが多い。ただし、件数が多い＝品質が高い、ではない点に注意。
:::


:::message
**テスタビリティ（Testability）**
ソフトウェアがテストしやすい状態にあるかどうかの度合い。テスタビリティが高いコードは、テストが書きやすく、バグも見つけやすい。逆にテスタビリティが低いと、テストを書くこと自体に膨大な時間がかかり、テストの効果も下がる。開発者がテスタビリティを意識してコードを書くことは、立派なQA活動だ。
:::


:::message
**HACCP（Hazard Analysis and Critical Control Point：危害要因分析重要管理点）**
食品の安全を工程管理で守るための国際的な仕組み。「どの工程にどんなリスクがあるか」を事前に分析し、重要な管理ポイント（CCP）を決めて監視する。出荷前の最終検査ではなく、工程そのものを管理する発想であり、ソフトウェアの品質保証と同じ構造を持つ。テスト＝最終検査、QA＝工程管理と考えると、飲食業はすでに「QA≠テスト」を実践している。
:::


:::message
**ISO 9000シリーズ**
品質マネジメントシステム（QMS）の国際規格。品質管理（QC）と品質保証（QA）を明確に区別して定義している。ISO 9000:2015では、QCは「品質要求事項を満たすことに焦点を合わせた品質マネジメントの一部」、QAは「品質要求事項が満たされるという確信を与えることに焦点を合わせた品質マネジメントの一部」と定義されている。テストとQAの区別は日本独自ではなく、この国際規格に基づく考え方だ。
:::


## テスト / QC / QA の関係図


3つの概念の関係を図にまとめた。


## コラム：「QAチーム」なのにテスト実行だけだった話


テスト、QC、QAは独立した活動ではなく、入れ子の構造になっている。


![QA/QC/テストの三層構造](/images/books/testing-not-equals-qa/diag_01_nested_layers.png)


QAはQCを含み、QCはテストを含む。テストはQAの一部であって、全部ではない。「QA＝テスト」と言ってしまうと、最も内側の円だけを指して全体を語っていることになる。

もうひとつの見方として、時間軸で整理する。


![時間軸で見るテスト/QC/QA](/images/books/testing-not-equals-qa/diag_01_timeline.png)


テストは「今」のスナップショット。QCは「見つけた問題」への対処。QAは「これから」のための仕組みづくり。視野が広がるほど、活動の範囲も時間軸も長くなる。

自分のチームの活動が、この図のどこに集中しているかを考えてみると、現在地が見えてくる。

よくある現場の状態を図にするとこうなる。


![多くの組織の現実](/images/books/testing-not-equals-qa/fig_01_reality_bar.png)


テスト実行が活動の大部分を占め、バグ修正後の確認テスト（QC）が残りを埋め、QA活動はゼロ。この配分を意識するだけでも、「何が足りないのか」が見えてくる。

目指したいのは、テスト実行を効率化してQAに使える時間を増やすこと。テストの量を減らすのではなく、テストの質を上げてQAの余白を生み出す。[第5章](/books/testing-not-equals-qa/chapter5_1)でその具体的なやり方を紹介する。


## コラム：求人票の「QAエンジニア」を読み解く


これは、よく聞く話だ。

求人票には「QAエンジニア」と書いてある。面接でも「品質保証」「テスト設計」「プロセス改善」といった言葉が飛び交う。テスト実行だけではなく、品質に幅広く関われそうだと思って入社する。

初日に渡されるのは、テスト手順書だ。

「まずはここに書いてある通りに実行してください。Pass/Failを記録して、Failだったらチケットを起票してください」

最初の1ヶ月はオンボーディングだと思う。まずは現場を知るためにテスト実行から始める。それは理解できる。製品を触らないとテスト設計もできないし、現場の文脈を知らないと改善提案もできない。

2ヶ月経つ。「いつからテスト設計の話に入れますか？」と聞くと、「まずはケースの消化をお願い」と返ってくる。消化すべきケースは無限にある。1つの機能のテストが終わると、次の機能のテスト手順書が積まれる。

3ヶ月経つ。テスト実行→バグ報告→確認テストの無限ループから抜け出せない。テスト戦略の話はない。プロセス改善の話もない。メトリクスの「メ」の字もない。品質に関する議論は「今日何件バグが出た」と「明日何件テストケースを消化する」だけだ。

週次の進捗報告では「消化率」だけが報告される。「今週の消化率は85%。来週までに100%到達予定」。テストの品質ではなく、テストの量を管理している。品質保証ではなく、テストケースの進捗管理だ。

「これ、QAじゃなくてテストでは？」

心の中でそう思っても、周りを見渡すと全員が同じことをやっている。そして全員が自分たちの仕事を「QA」と呼んでいる。チームリーダーも、プロジェクトマネージャーも、開発チームも。新しく入った自分の方がおかしいのかと、一瞬思う。

おかしいのは自分じゃない。「QA＝テスト」という等式が、チーム全体に、組織全体に、さらにはクライアントにまで浸透しているだけだ。

勉強会や懇親会でこの話をすると、「うちも同じです」「わかります」という反応がとても多い。「QAエンジニア」を名乗りながらテスト実行だけをしている人は、この業界にたくさんいる。

この状況から抜け出すには、2つのものが要る。

1つは「言葉」だ。テスト、QC、QAの違いを説明する語彙。「今やっていることはテストであってQAではない」と言語化できれば、チームの中で会話が始められる。

もう1つは「仲間」だ。同じ違和感を持っている人がチーム内にいるかもしれない。でも、お互いにその違和感を共有する機会がない。

この本を読み終わったとき、少なくとも「言葉」は手に入っている。テストとQAを区別する語彙があれば、状況は変えられる。


## ワーク：自分のチームの活動を仕分けてみよう


転職サイトで「QAエンジニア」と検索してみてほしい。

業務内容を見ると、ほとんどの求人に「テストケースの作成・実行」「バグ報告」「リグレッションテスト」と書かれている。ここまではテスト活動だ。ところが求人タイトルは「QAエンジニア」であり、職種カテゴリも「品質保証」に分類されている。

テスト実行の求人を「QA」と呼ぶ慣習が、業界全体に定着している。

この慣習が生む問題は2つある。

1つ目は「QAを知らないままQAエンジニアを名乗る人が増える」こと。テスト実行しか経験していなくても、職務経歴書には「QAエンジニア3年」と書ける。結果、QAの経験者を採用したはずが、テスト実行の経験者だったというミスマッチが起きる。

2つ目は「テスト以外のQA活動を知る機会がなくなる」こと。テスト実行の求人が「QA」と呼ばれているなら、QAとはテスト実行のことだと思うのが自然だ。プロセス改善やメトリクス分析やリスクベースドテストが「QA活動」だと知る機会がない。

求人票を見るときは、業務内容を読もう。タイトルが「QAエンジニア」でも、中身は3パターンに分かれる。

| パターン | 業務内容に含まれる言葉 | 実態 |
|---|---|---|
| テスト実行型 | テストケース実行、バグ報告、手順書作成 | テスター |
| テスト設計型 | テスト計画、テスト設計、観点整理 | テストエンジニア |
| 品質保証型 | プロセス改善、メトリクス、リスク分析、戦略 | QAエンジニア |


3つ目のパターンに出会えたら、その組織は「QA≠テスト」を理解している可能性が高い。


## FAQ


自分のチーム（あるいは自分自身）が普段やっている品質に関する活動を、テスト・QC・QAに分類してみよう。

**手順**

1. 普段やっている品質関連の活動を、思いつくだけ書き出す（5〜10個）
1. それぞれを「テスト（測る）」「QC（診る）」「QA（仕込む）」に分類する
1. 3つのバランスを確認する

**迷ったときの分類ヒント**

「この活動は何のためにやっているか？」で考えるとわかりやすい。

- 「今の状態を確認するため」→ テスト（測る）
- 「品質の状態を把握・判断するため」→ QC（診る）
- 「将来の問題を予防するため」→ QA（仕込む）

**記入例**

| 活動 | 分類 | 理由 |
|---|---|---|
| テストケースの実行 | テスト（測る） | 今の品質状態を確認する |
| バグの再現確認 | テスト（測る） | バグの発生条件を特定する |
| バグの影響度判定 | QC（診る） | バグの深刻度を評価し対処方針を決める |
| リリース判定 | QC（診る） | 品質基準に照らしてリリース可否を判断する |
| バグのパターン分析 | QA（仕込む） | 同種のバグの再発を防止する |
| テスト戦略の策定 | QA（仕込む） | 効率的なテスト配分を設計する |
| 開発プロセスの改善提案 | QA（仕込む） | バグの作り込みを予防する |


**あなたのチームの活動**

| 活動 | 分類 | 理由 |
|---|---|---|


**振り返りのポイント**

3つに分類してみて、バランスを見てほしい。

テスト（測る）だけに偏っているなら、「問題を解いているだけ」の状態だ。まずはQC（答え合わせ）を意識するところから始めよう。具体的には、バグを見つけたときに「なぜこのバグが生まれたのか」を一言だけメモする。それだけでもQCの入り口になる。

テスト＋QCまでやっているなら、次はQA（仕込む）を1つだけ足してみよう。たとえば「過去1ヶ月に出たバグのパターンを3つ挙げてみる」。それだけでも、再発防止の議論のきっかけになる。

もし「テスト」と「QC」しかなくても、それが今の現在地だ。現在地を知ること自体が、勉強法を見直す第一歩なのだから。[第3章](/books/testing-not-equals-qa/chapter3_1)で、テストの先にあるQA活動のカタログを紹介する。今はまだ、ここに何を足せばいいかわからなくても大丈夫。この本を読み進めるうちに、足したい活動が見つかるはずだ。

**チームで実施する場合（20分版）**

1人でやっても気づきはあるが、チームでやるとさらに面白い。

1. 各自が5分で品質保証活動を書き出し、テスト/QC/QAに分類する
1. 5分で全員の結果をホワイトボードに集約する
1. 10分で「QAが空っぽだ」「全員テスト実行しか書いてない」など気づきを共有する

「自分のチームは何が足りていないか」が、チーム全員の共通認識になる。その共通認識が、[第3章](/books/testing-not-equals-qa/chapter3_1)以降の活動を始めるときの土台になる。


## この章をさらに深めるなら


**Q：テスト、QC、QAの違いはわかったけど、QCとQAの境界がまだあいまいです。**

もう一度、勉強のたとえに戻ろう。テストの後に「間違えた問題を見直して、正しい解き方を覚え直す」のがQC。ここまでは「個別の問題への対処」だ。「自分はいつも計算ミスが多いから、検算の習慣をつけよう」と勉強法自体を変えるのがQA。QCは「今あるバグ」に対処する。QAは「まだ起きていないバグ」を予防する。時間軸の向きが違う。

**Q：うちにはQAチームがないんですが、この話は関係ありますか？**

大いにある。QAは「チーム」ではなく「活動」だ。QAチームがなくても、品質を良くする仕組みづくりは誰かがやる必要がある。開発者が設計レビューでバグの作り込みを防ぐ。チームでふりかえりをして開発プロセスを改善する。これらはすべてQA活動だ。QAチームがないからこそ、開発者自身が「テストの先」に目を向けることが重要になる。[第3章](/books/testing-not-equals-qa/chapter3_1)で、QAチーム以外の誰でもできるQA活動のカタログを紹介する。

**Q：QA＝テストでも、今のところ特に困ってないんですけど。**

困っていないように見えるだけかもしれない。4症状のセルフチェックに1つでも当てはまったなら、困りごとの種はすでにある。「テストケースは増えているのにバグの傾向が変わらない」「毎回同じパターンの不具合が出る」。これは困っていないのではなく、負債が見えていないだけだ。[第2章](/books/testing-not-equals-qa/chapter2)で、この等式が組織にもたらす「構造的負債」を詳しく見ていく。見えるようになると、「あれも、これも」と芋づる式に出てくるはずだ。

**Q：結局、テストが一番大事なんじゃないですか？**

テストは品質保証活動の中で最も基本的で、最も目に見えやすい活動だ。大事であることに間違いはない。テストなしにQCもQAもあり得ない。測定しなければ問題も見つからないし、改善の方向も定まらない。ただ、テスト「だけ」では品質は改善しない。問題を解くだけでは成績が上がらないのと同じだ。テストという土台の上に、QCとQAを積み重ねることで、品質は継続的に良くなっていく。本書はテストを否定しているのではなく、テストの「先」を見せたいと思っている。

**Q：「QA＝テスト」が間違いなら、正しい言い方は何ですか？**

「テストはQAの一部」が正しい。テストはQA活動を構成する重要な要素のひとつだが、すべてではない。QA＝テストが定着している現場では、まず「テスト」と「QA」を使い分けることから始めるだけでも効果がある。「今やっているのはテストだ」「これはQCだ」「この活動はQAに当たる」と意識するだけで、不足している活動が見えてくる。言葉を変えると、思考が変わる。

**Q：小さいチームでテストだけで精一杯なんですが、QA活動なんてやる余裕がありません。**

QA活動は「テストの上に積む追加の仕事」ではない。むしろ「テストを効率化して、余った時間で仕組みをつくる」という発想だ。たとえば、毎回同じパターンのバグが出ているなら、そのパターンをチェックリスト化するだけでも立派なQA活動だ。5分でできる。「余裕がないからQAができない」ではなく、「QAをしないから余裕が生まれない」のかもしれない。[第3章](/books/testing-not-equals-qa/chapter3_1)で、忙しい現場でもすぐに始められるQA活動を紹介する。

**Q：開発者なんですが、この話はQAの人だけに関係する話ですか？**

まったく逆だ。開発者にこそ関係がある。QA活動の多くは、開発プロセスの中に組み込まれるものだ。設計レビューでバグの作り込みを防ぐ。コードレビューで品質を担保する。CIパイプラインに自動テストを組み込む。テスタビリティの高いコードを書く。これらはすべてQA活動であり、開発者が担う。むしろ「QAはQAチームの仕事」と思っている方が危険だ。品質は全員で作り込むもの。[第3章](/books/testing-not-equals-qa/chapter3_1)で、開発者が日常的に取り組めるQA活動を紹介する。

**Q：他業界の品質保証と比べてソフトウェアが遅れている根本原因は何ですか？**

歴史の長さと規制の有無が大きい。製造業の品質管理は100年以上の歴史がある。航空・医療は人命に直結するため、法規制が品質の仕組み化を強制してきた。ソフトウェアは歴史が浅いうえに、多くの領域で法規制がない。「テストで見つけて直せばいい」で許される業界だったから、仕組みへの投資が後回しにされてきた。ただし、金融（FISC安全対策基準）や医療機器（IEC 62304）のように規制が入った領域では、ソフトウェアでも品質の仕組み化が進んでいる。規制がなくても仕組みで品質を守る選択は自分たちでできる。

**Q：テスト、QC、QAの使い分けをチームに広めたいんですが、どこから始めればいいですか？**

いきなり「定義を覚えてください」と言っても浸透しない。おすすめは、日常会話の中で使い分けること。ふりかえりで「この活動はテストですね。QA活動として何を足せますか？」と聞く。バグ修正の確認で「QCが終わったら、再発防止のQAもやりましょう」と言い添える。定義の共有会を開くより、実際の活動に3文字を貼り付けるほうが早く定着する。まずは1人で使い分けを始めて、隣の人が「それ何？」と聞いてくるのを待つ。

**Q：この3つの区別は日本独自の考え方ですか？海外でも通用しますか？**

テスト・QC・QAの区別はISO 9000シリーズで国際的に定義されている概念だ。日本独自ではない。ただ、海外でも「QA = Testing」と呼ぶ現場は多い。ISTQB（International Software Testing Qualifications Board）のシラバスでもテストとQAの関係が整理されているが、現場レベルでは混同されている。つまり、この混同は日本固有の問題ではなく、ソフトウェア業界全体の構造的な問題だ。

**Q：マネージャーや経営層に「QA≠テスト」をどう説明すればいい？**

「QA＝テスト」の現場で起きがちなことを3つの数字で見せると効く。(1) 同じパターンのバグが繰り返し出ている件数、(2) テストケースの増加率 vs リリース後バグの減少率、(3) テスト工程にかかっている期間の推移。「テストを増やしても品質が上がっていない」事実がデータで見えれば、「テスト以外に何かが必要だ」という認識は自然に生まれる。理屈で説得するより、自分たちのチームのデータで見せるのが最短ルートだ。[第4章](/books/testing-not-equals-qa/chapter4)の品質定義ワークショップは、マネージャーを巻き込むきっかけとしても使える。

**Q：「QA≠テスト」の考え方をすでに理解している人が、さらに上を目指すには？**

「QA≠テスト」の理解は出発点であって、到達点ではない。次のステップは、自分のチームで「テスト以外のQA活動」を1つ実践すること。理解と実践の間には大きなギャップがある。「バグのパターン分析を月1回やる」「テスト戦略をA4一枚にまとめる」「品質定義ワークショップを開く」。どれか1つ、今月中に始めてみてほしい。知識は使わなければ意味がない。[第3章](/books/testing-not-equals-qa/chapter3_1)のQA活動カタログから、自分のチームに合うものを選ぶところから。
