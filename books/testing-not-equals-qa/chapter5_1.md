## 5-1. テスト戦略 vs テスト計画


旅行の計画を立てるとき、最初に新幹線の時刻表を開く人はいない。まず「どこに行くか」を決める。京都か、北海道か、沖縄か。目的地が決まってから、交通手段と宿を手配する。

テストも同じだ。

テスト計画を先に立てるチームは、行き先を決めないまま新幹線を予約している。「のぞみ号は予約した。宿も取った。で、どこに行くんだっけ？」。笑い話のようだが、テストの現場では本当に起きている。


### 戦略と計画は別物


テスト戦略とテスト計画は別の文書だ。

|  | テスト戦略 | テスト計画 |
|---|---|---|
| 問い | Why / What | How / When / Who |
| 内容 | 何を重点的にテストするか、何をテストしないか | 誰がいつ何をどう実行するか |
| 寿命 | 長い（プロダクトの方針が変わるまで有効） | 短い（スプリントやリリースごとに更新） |
| 変更頻度 | 四半期に1回程度 | 毎スプリント |
| 前提 | 品質定義（[第4章](/books/testing-not-equals-qa/chapter4)） | テスト戦略 |


旅行のたとえに戻すとこうなる。

- **戦略** = 「京都に行く」「目的は紅葉」「予算は10万」「3泊4日」
- **計画** = 「朝9時ののぞみ」「宿は四条のホテル」「2日目に嵐山」「3日目に伏見稲荷」

戦略は方針。計画は段取り。方針がないまま段取りだけ作っても、行き先がわからない。


### テスト戦略に書くべき5項目


テスト戦略はシンプルでいい。A4用紙1枚に収まる量で十分だ。書くべきは5つの問いへの答え。

**1. 最もリスクが高い箇所はどこか**

[第3章](/books/testing-not-equals-qa/chapter3_1)のリスク分析で特定した領域。ここに最もテストリソースを集中させる。

**2. テストしない領域はどこか**

ここが重要だ。「何をテストするか」だけでなく「何をテストしないか」を明記する。テストしない理由も書く。「低リスクだから」「他テストレベルでカバー済みだから」「過去にバグが出ていないから」。

「テストしない」と決めたことと、「テストを忘れた」ことは全然違う。決めたなら記録がある。忘れたら記録がない。

**3. 品質の判断基準は何か**

[第4章](/books/testing-not-equals-qa/chapter4)で定義した品質方針と、それに紐づくテスト終了条件。

**4. 自動化する範囲はどこか**

全部を自動化する必要はない。自動化に向いている領域と、手動テストの方が効率的な領域がある。回帰テストは自動化向き。探索的テストは手動向き。

**5. テストの優先順位はどうか**

時間が半分になったら何を残すか。この問いに答えられる状態がテスト戦略のある状態だ。答えられないなら、戦略がない。


![テスト戦略がある状態 vs ない状態](/images/books/testing-not-equals-qa/fig_05_strategy_check.png)


### 戦略がないときの3つの症状


自分のチームにテスト戦略があるかどうか、3つの症状でチェックできる。

**症状1: テスト計画書を毎回ゼロから書いている**。前回の計画書をコピーして日付と担当者名だけ変えている。戦略がないから、毎回同じことを書くしかない。

**症状2: 方針がスプリントごとにブレる**。前のスプリントは「UIの使い勝手を重視」、今スプリントは「パフォーマンスを重視」。その場の空気で方針が変わる。戦略として「何を重視するか」が決まっていないからだ。

**症状3: 「何をテストしないか」が決まっていない**。「全部テストします」と答えるチーム。一見安全に聞こえるが、実は「どこが危ないかわかりません」と言っているのと同じだ。全部を同じ密度でテストする＝リスク判断を放棄している。


### テスト戦略があるチームの3つの特徴


テスト戦略がうまく機能しているチームに共通する特徴がある。

**特徴1: 「なぜこのテストが必要か」を説明できる**

テストケースの1つひとつに「なぜ」がある。「テスト戦略で決済が最優先だから、決済のテストケースを手厚くしている」。テストの意図が説明できる状態。戦略がなければ「前回もやったから」しか言えない。

**特徴2: テスト計画書が短い**

戦略で方針が決まっているから、計画書はスプリントごとの差分だけで済む。「今回の変更は認証フローに影響。テスト戦略の優先順位に従い、認証のテストを増強」。1ページで書ける。

**特徴3: リリース判定が速い**

「品質の判断基準」が戦略に書いてあるから、リリース判定で迷わない。「テスト終了条件を満たしているか」をチェックするだけ。判断基準が明確なら、判定会議は15分で終わる。曖昧なら、2時間議論しても結論が出ない。


### テスト戦略のアンチパターン


テスト戦略を作ったつもりで、実は戦略になっていないパターンがある。

**1. テスト計画書の1ページ目**

テスト計画書の冒頭に「テスト方針」という1ページがあり、「品質を担保するために網羅的にテストを実施する」と書いてある。これはテスト戦略ではない。方針が「網羅的」だけなら、何も決めていないのと同じだ。

**2. ツール選定表**

「JUnit、Playwright、Appiumを使ってテストを自動化する」。ツールの話はテスト計画の一部であって、戦略ではない。戦略は「何を重点的にテストするか」「何をテストしないか」。ツールは「どうテストするか」。

**3. カバレッジ目標だけ**

「コードカバレッジ80%以上を目標とする」。カバレッジは品質の指標の1つであって、戦略の全体ではない。カバレッジ80%でも、重要な機能のテストが薄ければ品質は守れない。カバレッジ50%でも、リスクの高い箇所に集中していれば品質は守れる。

**4. スケジュールだけ**

「テスト期間: 10/1〜10/14」。スケジュールはテスト計画。テスト戦略は「この14日間で何を優先するか」を決めるもの。スケジュールが半分に圧縮されたとき、何を残して何を切るか。この判断ができるのがテスト戦略だ。


### 5つの問いのチェック方法


テスト戦略を書いたら、以下の5つの質問でセルフチェックする。

| # | 質問 | YESなら |
|---|---|---|
| 1 | 「テストしない領域」が明記されているか | リスク判断ができている |
| 2 | 品質方針と紐づいているか | [第4章](/books/testing-not-equals-qa/chapter4)の成果が活かされている |
| 3 | 時間が半分になっても使える内容か | 優先順位が明確 |
| 4 | 新メンバーが読んで理解できるか | 暗黙知が言語化されている |
| 5 | 前回の戦略からの差分が説明できるか | 前回の学びが反映されている |


5つ全部YESなら、良いテスト戦略だ。3つ以下なら、見直す価値がある。


### テスト計画書のコピペが消える理由


テスト戦略が存在すると、テスト計画書のコピペ問題が消える。

| テスト戦略なし | テスト戦略あり |
|---|---|
| テスト計画書に「方針」を毎回書く | 方針は戦略で決まっている |
| 前回の計画書をコピペして日付を変更 | 今回の差分だけ計画書に書く |
| 計画書が長い（形式を満たすため） | 計画書が短い（差分だけだから） |
| 書くのに2日かかる | 書くのに2時間で終わる |


テスト計画書のコピペは「怠慢」ではない。「戦略の不在」が根本原因だ。計画書を毎回真面目に書かせても根本原因は解決しない。戦略を1枚作る方が効果的だ。


### テスト戦略の効用


テスト戦略があることで得られる効果を整理する。

| 効果 | 説明 |
|---|---|
| テスト計画書が短くなる | 方針は戦略に書いてあるから |
| リリース判定が速くなる | 判断基準が戦略に書いてあるから |
| スコープの議論が減る | 「テストしない領域」が戦略に書いてあるから |
| 引き継ぎが楽になる | 方針が明文化されているから |
| テストの優先順位が揃う | 「時間が半分になったら何を残すか」が決まっているから |


テスト戦略は「テストの質」を上げるだけでなく、「テストにかかる時間」も削減する。方針が明確になることで、不要な議論と不要なテストが減る。


### A4一枚の最小テスト戦略


5つの問いに答えるだけ。30分でつくれる。テンプレートはワークに掲載した。完璧を目指さなくていい。まず1枚つくってみることが大事だ。


### テスト戦略のライフサイクル


テスト戦略は書いて終わりではない。4つのフェーズで運用する。

**Phase 1: 作成（初回30分）**

ワークのテンプレートに記入する。最初は粗くて構わない。「リスクが高い箇所: たぶん決済」「テストしない領域: 思いつかない」でもいい。書くことで思考が整理される。

**Phase 2: レビュー（作成後1週間以内）**

チームで15分のレビューを行う。POに「リスクの高い箇所はここで合っているか」を確認する。Devに「自動化の範囲はこれで妥当か」を確認する。複数の視点が入ることで、戦略の精度が上がる。

**Phase 3: 運用（毎スプリント）**

テスト計画を書くとき、まずテスト戦略を参照する。「今スプリントの変更はリスクの高い箇所か」「テストしない領域に含まれるか」。戦略を判断基準として使う。使わない戦略は形骸化する。

**Phase 4: 見直し（四半期ごと）**

四半期ごとに5つの問いを見直す。「リスクの高い箇所は変わっていないか」「テストしない領域の前提は崩れていないか」。プロダクトは変化するから、戦略も変化する。ただし、見直し頻度は四半期で十分。毎スプリント変えると方針がブレる。


### テスト戦略のレビュー観点


テスト戦略をレビューするときのチェックポイント。

| レビュー観点 | 確認すること | NGの例 |
|---|---|---|
| 具体性 | 「網羅的にテストする」のような曖昧表現がないか | 「品質を担保する」 |
| 根拠 | リスク判断に根拠があるか | 「なんとなく決済が重要」 |
| 実行可能性 | 現実的なリソースで実行できるか | 全テスト自動化を前提にしている |
| 更新 | 前回からの差分が説明できるか | 3四半期連続同じ内容 |
| 接続性 | 品質方針と矛盾していないか | 品質方針は「セキュリティ重視」なのにセキュリティテストが薄い |


レビューの最重要ポイントは「テストしない領域」の妥当性だ。「テストする領域」は書きやすいが、「テストしない」と明記するのは判断が必要。その判断が正しいかをチームで確認する。


### テスト戦略と品質方針の接続


[第4章](/books/testing-not-equals-qa/chapter4)で品質方針を定義した。テスト戦略は品質方針を入力として使う。

```
品質方針（[第4章](/books/testing-not-equals-qa/chapter4)）
 「決済が正確」「5分で復旧」「初回登録3分」
 ↓
テスト戦略（[第5章](/books/testing-not-equals-qa/chapter5_1)）
 リスクの高い箇所 → 決済処理
 テストしない領域 → 管理画面の細部
 品質の判断基準 → 品質方針のテスト終了条件
 自動化範囲 → 回帰テスト
 優先順位 → 決済＞認証＞UI
 ↓
テスト計画（スプリントごと）
 今回のスプリントでの具体的なテスト作業
```


この流れが「品質方針→テスト戦略→テスト計画」の三段構造だ。品質方針がないとテスト戦略の入力がない。テスト戦略がないとテスト計画が毎回コピペになる。


### テスト戦略のケーススタディ


3つのプロダクトでテスト戦略がどう異なるか、比較してみよう。

**ケース1: ECサイト**

| 項目 | 内容 |
|---|---|
| 最もリスクが高い箇所 | 決済処理、カート計算、在庫管理 |
| テストしない領域 | 管理画面のUI細部、多言語対応（未リリース） |
| 品質の判断基準 | 決済バグ0件、カート計算一致率100% |
| 自動化範囲 | 決済フロー回帰テスト、API結合テスト |
| 優先順位 | 決済＞在庫＞検索＞UI |


**ケース2: 業務用SaaS（BtoB）**

| 項目 | 内容 |
|---|---|
| 最もリスクが高い箇所 | データ整合性、権限管理、API連携 |
| テストしない領域 | モバイル対応（PC専用）、印刷レイアウト |
| 品質の判断基準 | SLO 99.95%、データ不整合0件 |
| 自動化範囲 | API全エンドポイント、権限マトリクステスト |
| 優先順位 | データ整合性＞権限＞API＞UI |


**ケース3: モバイルアプリ**

| 項目 | 内容 |
|---|---|
| 最もリスクが高い箇所 | オフライン時のデータ同期、プッシュ通知 |
| テストしない領域 | Android 10以前（シェア3%未満） |
| 品質の判断基準 | クラッシュフリーレート99.9%、同期エラー率0.1%未満 |
| 自動化範囲 | 主要ユーザーフローのE2E、同期ロジックのUT |
| 優先順位 | 同期＞通知＞UI＞パフォーマンス |


3つのケースで共通していること: 「テストしない領域」が明記されている。テスト戦略は「やること」を決めるだけでなく「やらないこと」を決めることが本質だ。


### テスト戦略のレビュー対話例


テスト戦略をチームでレビューするとき、どんな会話になるか。ECサイトのケースで見てみよう。

```
QA：「テスト戦略のドラフトを持ってきました。
 最もリスクが高い箇所は決済処理です」

Dev：「認証フローも入れた方がいいのでは？
 先月セッション管理のバグが2件出た」

QA：「確かに。認証フローを追加します。
 リスクの高い箇所: 決済処理、認証フロー」

PO：「テストしない領域に管理画面って書いてあるけど、
 来月管理画面に新機能入るよ？」

QA：「来月はスコープ内に戻します。
 『テストしない領域』に復活条件を書いておきます。
 『管理画面: 変更がない限り。新機能追加時はスコープ内に戻す』」

Dev：「自動化範囲、回帰テストだけでいい？
 APIテストも自動化できるんだけど」

QA：「APIテストも追加します。
 自動化: 回帰テスト、APIテスト
 手動: 探索的テスト、UIの使い勝手」
```


15分の会話で、テスト戦略の精度が3段階上がった。1人で書くより、複数の視点が入る方が漏れが少ない。


### テスト戦略の「やらないリスト」の書き方


「テストしない領域」を書くのは勇気がいる。しかし、書かないと「全部やる」になり、結局どこも中途半端になる。

やらないリストの書き方のコツ:

| 書き方 | 良い例 | 悪い例 |
|---|---|---|
| 理由を添える | 「IE11: サポート終了のため」 | 「IE11」だけ |
| 復活条件を書く | 「モバイル: ユーザー比率10%超えたら再検討」 | 条件なし |
| リスク残留を認識 | 「管理画面: 低リスクだが障害時は手動確認」 | リスクに触れない |
| 具体的にする | 「多言語の中国語表示」 | 「多言語系」 |


この「やらないリスト」が説明責任の土台になる。リリース後に問題が起きたとき、「テストしない判断を記録していた」と「テストを忘れていた」では意味がまったく違う。
