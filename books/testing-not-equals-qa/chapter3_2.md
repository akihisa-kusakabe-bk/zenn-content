## 3-3. 中流で効く活動


中流の品質活動は、開発が進行している最中に品質を組み込む活動だ。授業中にノートを取り、小テストで理解度を確認するのと同じ構造。開発のサイクルの中に品質チェックポイントを埋め込む。


### #6. 品質ゲート設計


品質ゲートとは、次の工程に進んでいいかどうかを判定するチェックポイントのことだ。

品質ゲートが「テストに通ること」の1つしかない現場は珍しくない。開発が終わる→QAがテストする→通ればリリース。チェックポイントが最後に1つだけ。しかもその判断がQA担当者に集中している。負債1（門番化）の典型だ。

品質ゲートを複数の工程に分散させると、この構造が変わる。

| タイミング | ゲートの例 |
|---|---|
| PR作成時 | テスト観点の記述があるか。影響範囲が明記されているか |
| マージ前 | コードレビュー完了。自動テスト通過。静的解析クリア |
| ステージング | 主要フローの動作確認。パフォーマンス基準の充足 |
| リリース前 | リリース判定基準の全項目クリア |


ポイントは、ゲートの判定基準を明文化することだ。「誰かがOKと言えばOK」ではなく、「この条件を満たせばOK」にする。基準が明文化されれば、特定の人に判断が集中しない。

品質ゲートを設計するときの注意点が2つある。

**注意1: ゲートを厳しくしすぎない**。すべてのPRに「テスト計画書添付必須」と設定したら、開発速度が落ちて誰も守らなくなる。ゲートは「最低限これだけは確認する」のレベルに設定する。慣れてきたら少しずつ基準を上げる。

**注意2: ゲートを通過する手順を自動化する**。手動でチェックリストを確認するゲートは、人によって判断がブレる。CIで自動チェックできる項目は自動化する。人間がチェックする項目は「YES/NO」で判定できる形にする。

品質ゲートのBeforeとAfterを比較するとこうなる。

|  | Before | After |
|---|---|---|
| チェックポイント | リリース前の1回だけ | 4段階に分散 |
| 判定基準 | QA担当者の判断 | 明文化された条件 |
| 判定者 | QA担当者のみ | 開発者自身＋CI＋QA |
| 手戻りの大きさ | リリース直前に大きな手戻り | 各段階で小さな手戻り |


品質ゲートを分散させると、1回あたりの手戻りが小さくなる。リリース前に「全部ダメ」と言われるより、PR作成時に「ここ直して」と言われる方がコストが低い。

**PRテンプレートの例**


**markdown**
```
## テスト観点
- このPRで影響を受けるテスト観点: [カタログの観点IDを記入]
- 影響範囲: [変更が影響する他の機能・画面]
- 自動テスト: 追加した / 既存で十分 / 該当なし
- 手動テスト: 必要（理由: ）/ 不要
```


最初はマージ条件にしなくていい。「書く」習慣がつけば、書いていないPRが目につくようになる。自然と文化になる。

**始め方**: PRテンプレートに「テスト観点」「影響範囲」の記入欄を追加する。マージ条件にはしなくていい。書く習慣をつけるだけで効果がある。


## テスト観点


CI/CDパイプラインに品質のチェックを自動で組み込む。人が毎回手動で確認する必要がなくなる。

| 指標 | ツール例 | 閾値の目安 |
|---|---|---|
| テストカバレッジ | Jest, pytest, JaCoCo | 新規コード80%以上 |
| 静的解析 | ESLint, SonarQube | Critical/Blocker = 0 |
| セキュリティスキャン | Snyk, Dependabot | High以上 = 0 |
| ビルド時間 | CI/CD自体 | 前回比20%以上増なら警告 |


自動化された品質チェックは、門番化を防ぐ効果がある。品質の判断基準がコードとして定義され、人に依存しない。新しいメンバーが入っても、CIが同じ基準でチェックしてくれる。

CI/CDへの品質指標組み込みは、段階的に進めるのが現実的だ。

| 段階 | やること | 効果 |
|---|---|---|
| Level 1 | カバレッジの計測（閾値なし） | 数字が見えるだけで意識が変わる |
| Level 2 | 静的解析の導入（警告レベル） | コード品質の最低ラインが保証される |
| Level 3 | 閾値の設定（マージブロック） | 基準を下回るコードがマージされなくなる |
| Level 4 | セキュリティスキャンの追加 | 既知の脆弱性がリリースに含まれなくなる |


Level 1から始めて、チームが慣れたら次のレベルに進む。最初からLevel 4を目指すと「CIが邪魔」という声が上がり、元に戻される。

ただし、CI/CDに組み込めるのは機械的に判定できるものだけだ。「ユーザーにとって使いやすいか」「ビジネスロジックが正しいか」は人間が判断する必要がある。自動化できるものは自動化し、人間は人間にしかできない判断に集中する。

**始め方**: まずテストカバレッジの計測を入れる。閾値は設定せず、数字を見えるようにするだけでも意識が変わる。


### #7. CI/CDへの品質指標組み込み


テスト設計は、テスト実行の「前工程」だ。何をテストするか、なぜテストするか、どういう観点でテストするかを決める活動。

テスト実行が「問題を解く」なら、テスト設計は「どの問題集をやるか決める」にあたる。闇雲に問題を解くより、出題範囲を分析して優先度をつけた方が効率がいい。テストも同じだ。

テスト設計の詳細は[第5章](/books/testing-not-equals-qa/chapter5_1)で扱う。ここでは「テスト設計はテスト実行とは別の活動だ」ということだけ押さえておいてほしい。テスト設計とテスト実行が混同されがちだ。テストケースを書きながら実行する。設計と実行が同時に行われているから、設計の質を振り返る余裕がない。

**始め方**: テスト実行の前に30分、「今回テストで確認したい観点」を3つ書き出す。書き出すだけでいい。


### #8. テスト設計（観点の言語化）


テスト手順書に書かれていないテスト。テスターの経験と直感に基づいて、ソフトウェアを自由に操作しながらバグを探す。

手順書ベースのテストは「想定したシナリオの中でバグを見つける」活動だ。探索的テストは「想定していなかったシナリオを発見する」活動だ。

手順書を何万件実行しても、手順書に書かれていないバグは見つからない。テストケースの件数で安心する罠（負債3のテスト充足感）を打破するには、手順書の外側を探る活動が必要だ。

探索的テストにはスキルが要る。「適当に触ってみる」こととは違う。探索的テストには「チャーター」を使う。

チャーターとは、探索の目的と方向性を1〜2文で記述したガイドだ。

| チャーターの例 | 探索の方向性 |
|---|---|
| 「決済フローの異常系を30分で探索する」 | 決済途中のネットワーク切断、二重送信、タイムアウト |
| 「新規登録フローをスマホで30分探索する」 | 画面サイズ、ソフトキーボードの表示崩れ、戻るボタン |
| 「管理画面の権限周りを30分探索する」 | 権限のない操作、権限変更後の挙動、URLの直接アクセス |


チャーターがあれば、探索に方向性が生まれる。闇雲に触るのとは質がまるで違う。

**良いチャーターの書き方**

チャーターは「対象 × リスク × 制約時間」の3要素で構成する。

```
テンプレート: [対象]の[リスク観点]を[時間]で探索する
```


| 要素 | 良い例 | 悪い例 |
|---|---|---|
| 対象 | 「決済フロー」「ユーザー設定画面」 | 「全体」「アプリ」（広すぎる） |
| リスク観点 | 「異常系」「権限周り」「並行操作」 | 「バグを探す」（方向性がない） |
| 制約時間 | 「30分」「45分」 | 時間制限なし（集中が切れる） |


時間は30分を基本にする。慣れてきたら45分まで伸ばせるが、60分を超えると集中力が落ちて発見の質が下がる。

探索的テストの結果は必ず記録する。記録する内容は3つだけ。

1. **何を探索したか**: チャーターの内容
1. **何を見つけたか**: バグ、気になる挙動、仕様の曖昧さ
1. **次に何を探索すべきか**: 今回の探索で見えた新しいリスク

この記録がテスト観点カタログの素材になる。探索的テストは「手順書の外側」を発見する活動であり、その発見をカタログに還元することで品質サイクルが回る。

**探索的テストの記録テンプレート**

```
【チャーター】決済フローの異常系を30分で探索する
【日時】2026/10/01 14:00-14:30
【テスター】〇〇

【発見したこと】
1. [バグ] 決済中にブラウザの戻るボタンを押すと、
 カートの金額が2倍になる（重大度: 高）
2. [気になる] タイムアウト後のエラーメッセージが
 英語のまま。日本語化されていない
3. [仕様の曖昧さ] 決済途中でセッション切れた場合の
 振る舞いが未定義

【次に探索すべき領域】
- セッションタイムアウトまわりの全般
- 決済中の並行操作（別タブで同じカートを操作）
```


30分の探索で3つの発見。手順書ベースのテストでは見つからなかったものだ。特に「仕様の曖昧さ」の発見は、要件レビュー（活動#1）にフィードバックできる。

**探索的テストで見つかりやすいバグの傾向**

| バグの種類 | 例 | 手順書で見つかるか |
|---|---|---|
| 状態遷移の抜け | 途中離脱→再開時の不整合 | 見つかりにくい |
| 並行操作の競合 | 二重クリック、複数タブ | 見つかりにくい |
| エラーハンドリング漏れ | 想定外のHTTPステータスコード | 一部は見つかる |
| UIの不整合 | 画面遷移後の表示崩れ | デザインレビューで見つかる場合も |
| パフォーマンス劣化 | 大量データ時の応答遅延 | 負荷テストで見つかるが、探索でも気づける |


探索的テストは手順書ベースのテストを「補完」する位置づけだ。どちらかだけでは不十分で、両方を組み合わせることでテストの網が広がる。

**始め方**: スプリントの最後に30分、手順書なしでプロダクトを触る時間をつくる。チャーターだけ決めて自由に探索する。


### #9. 探索的テスト


後工程と横断の活動は、テスト実行の後工程と、タイミングを問わず常時行う活動だ。勉強でいえば、復習と勉強法の見直しにあたる。


## 3-4. 後工程＋横断で効く活動


バグを見つけて、影響度を判定して、対処方針を決める。ここまではQCだ。RCAはその先にある。「なぜこのバグが生まれたのか」を追跡する。


:::message
**RCA（Root Cause Analysis：根本原因分析）とは**
問題の表面的な原因ではなく、根本的な原因を特定する手法。「なぜ？」を繰り返し問うことで、真の原因にたどり着く。5 Whys（なぜなぜ分析）が代表的な手法。
:::


たとえば「画面に表示される金額が1円ずれている」というバグがあったとする。

- 直接原因：小数点の丸め処理が間違っていた
- なぜ？：丸め処理の仕様が明記されていなかった
- なぜ？：要件定義で金額の丸め方を定義していなかった
- 根本原因：金額計算に関する要件の記述ルールがなかった

直接原因だけ修正すると、丸め処理のバグは直る。しかし、次の機能開発でもまた金額の丸めが未定義のまま実装される。同じパターンのバグが繰り返される。

根本原因まで追跡すれば「金額計算の要件には丸め方を必ず明記する」というルールをつくれる。1件のバグ分析から、将来のバグを何件も予防できる。

もう1つ、よくあるパターンを挙げる。「ユーザー登録時にメールが届かない」というバグ。

- 直接原因：メール送信のキューが詰まっていた
- なぜ？：メール送信が同期処理になっていた
- なぜ？：非同期処理の設計方針が定義されていなかった
- 根本原因：「外部サービス連携は非同期にする」という設計ルールがなかった

直接原因だけ直すと、メールキューの詰まりは解消する。しかし根本原因まで追跡すれば「外部サービス連携は非同期にする」という設計ルールが生まれる。メール以外の外部連携（SMS、プッシュ通知、Webhook）でも同じパターンのバグを予防できる。

RCAは門番化にも効く。バグの根本原因を言語化し、チームで共有すれば、特定の人の頭の中にしかなかった品質ナレッジがチームの共有知になる。

RCAを組織に定着させるコツは「責任追及に使わない」ことだ。「誰が悪かったか」ではなく「何が起きて、なぜ起きて、どうすれば防げるか」に集中する。個人を追及するRCAは、次からバグを隠す文化を生む。プロセスを改善するRCAは、バグを報告しやすい文化を生む。

**RCAの実践テンプレート**

```
【バグ概要】
ユーザー登録画面で、全角スペースを含むメールアドレスが
登録できてしまう

【直接原因】
メールアドレスのバリデーションが半角文字のみ対象で、
全角文字を考慮していなかった

【なぜ？ × 3回】
1. なぜ全角を考慮しなかった？
 → バリデーションの仕様に「全角文字の扱い」が記載されていなかった

2. なぜ仕様に記載がなかった？
 → 入力値バリデーションの標準仕様書が存在しなかった

3. なぜ標準仕様書がなかった？
 → バリデーションルールが各機能の開発者に任されていた

【根本原因】
入力値バリデーションの共通ルールが組織にない

【再発防止策】
- 入力値バリデーションの共通ガイドラインを作成する
- メールアドレス、電話番号、住所等の共通入力項目は、
 共通バリデーション関数を使う
```


このテンプレートを使えば、30分でRCAが完了する。「なぜ？」を3回で止めるのがポイント。5回以上やると「地球が生まれたから」のような無意味な根本原因にたどり着く。3回で十分だ。

**始め方**: 次に見つけたバグ1件に対して「なぜ？」を3回繰り返す。30分あればできる。


### #10. バグ分析（RCA：根本原因分析）


品質を数字で測り、見える状態にする活動。

「テストケース10,000件実行しました」。この数字だけでは品質の実態はわからない。

品質メトリクスを設計するとは「何を測れば品質の状態がわかるか」を決めることだ。

| カテゴリ | メトリクス例 | 何がわかるか |
|---|---|---|
| バグ傾向 | バグ密度（バグ数/KLOC） | コードの品質水準 |
| バグ傾向 | バグ検出率（テスト発見/全バグ） | テストの有効性 |
| リリース品質 | リリース後バグ率 | 出荷品質の推移 |
| プロセス | 平均修正時間 | 修正プロセスの効率 |
| プロセス | 手戻り率 | 上流品質の状態 |


メトリクスは「見える化」自体が目的ではない。「次に何をするか」を判断するための材料だ。バグ密度が高い領域があれば、そこの設計を見直す。手戻り率が高ければ、要件定義の品質を疑う。数字から行動につなげて初めてメトリクスの意味がある。

メトリクスから行動への変換例を3つ示す。

| メトリクスの値 | 読み方 | 次のアクション |
|---|---|---|
| バグ密度が特定モジュールだけ高い | そのモジュールの設計かレビューに問題がある | 設計レビュー（#2）をそのモジュールに集中投入 |
| リリース後バグ率が3回連続で上昇 | テストの有効性が下がっている、または開発速度に品質が追いついていない | テスト戦略の見直し（[第5章](/books/testing-not-equals-qa/chapter5_1)） |
| 手戻り率が30%を超えている | 上流の品質が低い。要件や設計の段階で問題が作り込まれている | 要件レビュー（#1）の強化 |


大事なのは「定期的に同じ指標を記録し続けること」だ。ツールの洗練は後からでいい。

**最小品質ダッシュボード（スプレッドシートで十分）**

最初から完璧なダッシュボードを作る必要はない。スプレッドシートに4つの数字を毎リリース記録するだけで始められる。

| 指標 | v1.2 | v1.3 | v1.4 | 傾向 |
|---|---|---|---|---|
| リリース後バグ数（1ヶ月以内） | 12 | 8 | 5 | ↓改善 |
| 重大バグ数 | 2 | 1 | 0 | ↓改善 |
| テスト観点カバー率 | — | 60% | 75% | ↑改善 |
| 手戻り率 | 35% | 25% | 20% | ↓改善 |


3回分のデータが溜まれば傾向が見える。傾向が見えれば「何をすべきか」が見える。v1.2→v1.4でリリース後バグが12→5に減っていれば、品質活動が効いている証拠だ。

メトリクスの落とし穴にも触れておく。「テストケース件数」と「バグ発見件数」を目標にすると、品質が悪化する。テストケースを増やすことが目的になり、品質に貢献しないテストケースが量産される。バグ発見件数を目標にすると、軽微なバグを大量に報告して件数を稼ぐ行動が生まれる。メトリクスは「何を測るか」だけでなく「目標にしてはいけない指標は何か」も定義しておく。

**始め方**: まず1つだけ測る。おすすめは「リリース後バグ率」。リリース後1ヶ月以内に報告されたバグの件数を記録するだけ。3回分のデータが溜まれば傾向が見える。


### #11. メトリクス設計と可視化


過去のテストで使った観点を蓄積し、カタログ化する活動。

門番化の根本原因は、品質ナレッジが特定の人の頭にしかないことだ。「この機能はこのパターンでバグが出やすい」「このAPIはこういう条件で壊れる」。この知識がカタログとして共有されていれば、誰でも一定水準のテスト設計ができる。

カタログの構造は、たとえばこうなる。

| 観点カテゴリ | 観点の例 | よくあるバグパターン |
|---|---|---|
| 入力値 | 空欄、最大長、特殊文字、絵文字 | バリデーション漏れ |
| 状態遷移 | ログイン前→後、途中離脱→再開 | 状態の不整合 |
| 連携 | API呼び出し、外部サービス連携 | タイムアウト、リトライ時の二重処理 |
| 並行処理 | 同時操作、二重クリック、複数端末 | デッドロック、データ競合 |
| 境界条件 | 日付変更時、月末、閏年 | 境界値での計算ミス |


カタログは「テスト観点の辞書」だ。テスト設計のたびにゼロから観点を考えるのではなく、カタログから該当する観点を選んで、今回のテスト対象に当てはめる。

テスト観点カタログは完璧を目指さない。最初は粗くていい。過去3ヶ月のバグを分類して、「よくあるパターンTOP5」を書き出す。これだけでカタログの種ができる。カタログは品質サイクル（[第5章](/books/testing-not-equals-qa/chapter5_1)で詳述）を回すたびに育っていく。

**カタログ初版のつくり方（1時間バージョン）**

| ステップ | 所要時間 | やること |
|---|---|---|
| 1. バグチケットを開く | 5分 | 直近3ヶ月のバグチケットを一覧にする |
| 2. パターンでグルーピング | 30分 | 「入力値」「状態遷移」「連携」など、似たバグをまとめる |
| 3. TOP5を選ぶ | 10分 | 件数が多い順に5パターンを選ぶ |
| 4. 観点として言語化 | 15分 | 各パターンを「〇〇のとき、△△を確認する」の形に書く |


言語化の例を1つ挙げる。バグチケットに「全角スペースを含むメールアドレスが登録できる」「絵文字入りの名前でエラーになる」「住所欄に制御文字を入れるとDB保存でエラー」があったとする。これらをまとめると「入力値に非ASCII文字（全角スペース、絵文字、制御文字）が含まれるとき、バリデーションが正しく動作するか確認する」という1つの観点になる。

完璧でなくていい。この初版があるだけで、次のテスト設計が「ゼロから考える」から「カタログから選んで足す」に変わる。

カタログは使うたびに育てる。テスト設計のときにカタログにない観点が必要になったら、その場で追加する。探索的テストで新しいバグパターンを見つけたら、それもカタログに足す。月に2〜3個ずつ増えていけば、半年後には30個以上の観点が溜まる。チーム全員がこのカタログを入り口にしてテスト設計を始める状態になれば、「あの人がいないとテストの質が落ちる」という属人化から抜け出せる。

カタログが育つと、新しいメンバーがチームに入ったときの立ち上がりが速くなる。ベテランの頭の中にしかなかった「勘所」が言語化されているからだ。門番化を防ぐだけでなく、チームの品質力のベースラインを底上げする効果がある。

**始め方**: 過去3ヶ月のバグチケットを開いて、パターンごとにグルーピングする。1時間あればTOP5は出る。


### #12. テスト観点カタログの構築


バグの傾向、テスト観点、品質に関する気づきをチーム内で共有する活動。

特別な仕組みは要らない。週次のふりかえりで5分、「今週見つかったバグで興味深かったもの」を1件共有する。それだけで品質の知見がチーム全体に広がる。

ナレッジ共有にはいくつかの形式がある。

| 形式 | 頻度 | 内容 | 所要時間 |
|---|---|---|---|
| バグ共有会 | 週1回 | 今週の注目バグ1件を深掘り | 15分 |
| テスト観点レビュー | スプリントごと | テスト設計の観点をチームで確認 | 30分 |
| 品質ふりかえり | 月1回 | 品質メトリクスの振り返りと改善議論 | 60分 |
| バグカタログ更新 | 随時 | 新しいバグパターンをカタログに追加 | 5分/件 |


バグ共有会は特に効果が高い。「こんなバグが出ました。原因はこうでした。今後こういう観点を追加すると防げそうです」。この3文を共有するだけで、チーム全員のテスト設計力が少しずつ上がる。

門番化は「知識の偏在」が原因だ。ナレッジ共有は、知識を分散させる最も手軽な方法だ。ベテランが退職しても品質が落ちない状態をつくるには、ナレッジ共有を日常に組み込むしかない。

**バグ共有会の進め方（15分）**

| 時間 | やること |
|---|---|
| 0:00-0:03 | 今週の注目バグを1件紹介する |
| 0:03-0:08 | 「なぜ見つからなかったか」を議論する |
| 0:08-0:12 | 「今後どうすれば防げるか」を議論する |
| 0:12-0:15 | アクションを1つ決める |


15分で十分だ。バグ1件を深掘りするだけでいい。バグを3件以上紹介しようとすると、どれも浅くなって効果が薄い。1件を深く掘る方が学びが大きい。

**バグ共有会での対話例**

実際にバグ共有会でどんな会話が生まれるか、イメージしやすいように例を示す。

```
ファシリ「今週の注目バグ、何かある？」
QA 「ユーザー設定画面で、表示名を空欄にして保存できてしまう件。
 本番で3件問い合わせが来た」
Dev A 「あー、バリデーション入れてなかった。すぐ直す」
ファシリ「ちょっと待って。直すのはいいとして、
 なぜ見つけられなかったかも考えたい」
QA 「テストケースに空欄チェックはあったけど、
 設定画面は対象外だった」
Dev B 「設定画面、テスト薄いよね。他にも漏れてそう」
ファシリ「じゃあアクション。設定画面の入力値チェックを
 テスト観点カタログに追加しよう」
```


15分で1つのアクションが決まった。バグを直すだけで終わらず、「なぜ見逃したか」「次にどう防ぐか」まで踏み込む。これがバグ共有会の価値だ。

**ナレッジが分散している状態の目安**

| 指標 | 偏在（危険） | 分散（健全） |
|---|---|---|
| リリース判定 | 特定の1人がいないと判定できない | メンバーの2人以上が判定できる |
| テスト設計 | ベテラン1人が全機能の観点を持っている | カタログにまとまっていて誰でも参照可能 |
| バグの文脈理解 | 「この人に聞かないとわからない」 | RCA結果がドキュメント化されている |
| 品質ゲートの判断 | QA担当者の匙加減 | 基準が明文化されている |


左列に当てはまる項目が2つ以上あるなら、ナレッジ共有を最優先で始めるべきだ。

**始め方**: 次のふりかえりで「今週の気になるバグ」を1件共有する。5分で始められる。


### #13. ナレッジ共有


開発プロセスそのものを見直す活動。3つの負債すべてに効く。

ふりかえりの場で品質のトピックを扱うだけで、プロセス改善の入り口になる。品質に特化したふりかえりの問いを3つ用意した。

| 問い | 狙い | 効く負債 |
|---|---|---|
| 「テストフェーズで見つけたバグの中で、もっと早く防げたものは？」 | 上流活動の必要性を認識する | （上流空白） |
| 「今回のリリース判定で、QA担当以外が品質について発言したか？」 | 品質の属人化を確認する | （門番化） |
| 「テストに使った時間のうち、本当に品質向上に貢献した活動はどれか？」 | テスト工数の有効性を疑う | （テスト工数誤認） |


3つの問いのうち、1つだけ選んで次のふりかえりで使ってみる。1つで十分だ。

プロセス改善のポイントは「小さく・具体的に」。「品質意識を高める」は改善ではない。「PRテンプレートにテスト観点欄を追加する」は改善だ。次のアクションが具体的でないと実行されない。

プロセス改善は一度で完成しない。ふりかえりのたびに少しずつ変えていく。大きな改革よりも、小さな改善の積み重ねの方が定着する。3ヶ月前の自分たちと比べて「少し良くなった」と感じられれば、プロセス改善は機能している。

**プロセス改善の具体例**

品質のふりかえりから生まれた改善アクションの実例を5つ紹介する。

| ふりかえりでの発見 | 改善アクション | 効果 |
|---|---|---|
| テストフェーズで仕様の曖昧さが3件見つかった | 要件レビューに「テストできるか？」チェックを追加 | 次のスプリントで仕様起因の手戻りが0件に |
| 同じパターンのバグが3回出ている | RCAを実施し、共通バリデーション関数を作成 | 同パターンのバグが再発しなくなった |
| QAが不在だとリリース判定ができない | リリース判定基準を明文化し、誰でも判定可能に | QA不在時もリリース可能になった |
| テストケースの作成に2日かかっている | テスト観点カタログから観点を選ぶ方式に変更 | テスト設計が半日に短縮 |
| フレーキーテストの調査に毎日1時間 | フレーキーテスト撲滅スプリントを1回実施 | 調査時間が月10分に削減 |


どの改善も「小さくて具体的」だ。「品質文化を向上させる」のような大きな目標ではなく、「PRテンプレートに1項目追加する」のような具体的なアクション。小さな改善の積み重ねが、結果として品質文化を変える。

**品質ふりかえりのファシリテーション（10分版）**

通常のふりかえりに「品質パート」を10分追加するだけでいい。以下の進行例を参考にしてほしい。

```
[0:00-0:02] 今回のリリースで発見されたバグの件数と傾向を共有する
[0:02-0:05] 「もっと早く見つけられたバグ」を1件選び、
 どの工程で防げたかを議論する
[0:05-0:08] 上記の議論から、次のスプリントで試す改善案を
 1つだけ決める
[0:08-0:10] 改善案を誰がいつまでにやるか決めて終了
```


品質パートで避けるべきことが1つある。「犯人探し」だ。「誰がこのバグを作ったか」ではなく「どのプロセスがこのバグを通したか」を議論する。個人ではなくプロセスを対象にする。この原則を守れるかどうかで、品質ふりかえりが続くかどうかが決まる。

**始め方**: 次のふりかえりに上記の問いを1つ追加する。5分で始められる。
