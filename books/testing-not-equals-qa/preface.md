## 0-1. なぜこの本を書いたのか


基幹システムをウォーターフォールで作る開発エンジニアとしてキャリアを始めた。要件定義、基本設計、詳細設計に応じて単体テスト、結合テスト、総合テストを回す。テストは開発者がやるもの。そう思っていたし、もっといえば、テストをやらなくて済むようにすることに必死だった。不具合の原因は誤ったデータのインプットだ。だからDBの定義でバリデーションを仕込み、内部関数の引数にも徹底してガードをかけた。バグを出さない設計が良いエンジニアの条件だと信じていた。デシジョンテーブルも二因子網羅も知らない。テストは感覚でやるものだった。

転機は、第三者検証会社から声がかかったことだった。そのまま転職した。

入ってみて驚いた。テストに「手法」がある。デシジョンテーブル、同値分割、境界値分析。感覚でやっていたことに体系があった。そしてそれ自体がビジネスになっている。お客さまのソフトウェアを預かり、テスト設計をし、テストを実行し、バグを報告する。テストの「プロ」がいる世界。Web系の案件管理を担当するようになり、表参道あたりのクライアントを回るようになった。そこで初めて「QA」という言葉に出くわした。顧客の依頼内容を詳しく聞くと、やっていることはテストだ。なのに、なぜソフトウェア開発の現場ではテストが「QA」と呼ばれるのか。不思議だった。

気になって調べた。「QA」は Quality Assurance、品質保証。テストは品質保証と呼ばれる領域の1つの手段でしかない。JSTQBの体系を学び、製造業の品質保証の歴史を調べた。調べるほどに、ソフトウェア業界だけが「テスト＝品質保証」で止まっていることがわかってきた。製造業は60年以上前にこの等式を卒業している。なぜソフトウェアだけがここで止まっているのか。

この気づきは、実務でも裏付けられた。テストをして満足できるのは、もともと品質が良い案件だけだ。品質が悪い案件はテストをしてもクレームが来る。テストしているのになぜか。QCもQAもしないで、テストだけしているからだ。

「QAしてください」と言われても、「テストしてください」と言われても、品質分析とバグの傾向レポートは必ずつけるようにした。不要と言われない限り、不具合の傾向を分析し、足りないテスト観点を特定し、エンジニアごとの不具合パターンを洗い出し、次に何をすべきかレポートにまとめる。テストして終わりではなく、テストで見えたことを次のアクションにつなげる。「これをやってよかった、ありがとう」と言われる仕事ができるようになった。

手応えを感じる一方で、手動テストの限界も見えていた。Seleniumは2004年に生まれていたが、2020年頃まで現場に浸透しているようには見えなかった。ウォーターフォールではせいぜい3回程度の繰り返しテストしかしないから、自動化の費用対効果が出ない。しかしアジャイル開発が主流になるにつれ、自動化のリグレッションテストの需要が爆発した。SaaS型の自動化ツールが2017年前後に登場し、手動テストの終焉が見えてきた。この流れの中で、テスト自動化に特化した会社の事業立ち上げに携わった。Playwrightが2020年に勢力図を塗り替え、今やAIがテスト設計を行い自動化が実装される時代になった。

自動化でテスト実行が回り、AIでテスト設計と分析が行われる世界に変化している。人がソフトウェアのテストをする時代の幕引きだ。

今はビットキーという会社で品質戦略を担当している。テスト実行チームではなく、品質戦略室という名前のチームだ。スマートロックというハードウェアとソフトウェアが一体になったプロダクトの品質を、テスト実行ではなく仕組みで守る。なぜ「テスト」ではなく「品質戦略」なのか。その答えはこの本全体を通して伝えていく。

QAと呼ばれる職業は、ソフトウェアに限らず世界中のいろんな業種に存在する。以前、あるテレビ番組でオレンジジュースを日本に輸出するブラジルの工場が紹介されていた。その工場のQA担当者は、納品されたオレンジを洗い、選別し、何種類ものオレンジをブレンドしていた。オレンジジュースの味は糖度と酸度の比率（レシオ）で決まる。日本向けはレシオ14の甘め、ヨーロッパ向けはレシオ12の酸味寄り。国ごとの好みに合わせて数値をコントロールする。顧客の好みに味を整えるところまでが、この工場のQAの仕事だった。

番組スタッフが日本の消費者の声をそのQA担当者に届ける。「おいしい」「ありがとう」。その言葉を聞いたQAの方は、嬉し涙を浮かべていた。選別して、ブレンドして、数値を合わせて、届けた先の「おいしい」。そこまでやっていたからこそ、その涙だった。

自分たちのQA活動は、本来そういうものではないだろうか。開発者から言われたテストをこなす。それだけでいいのか。QAは開発からも、CS（カスタマーサクセス）からも、営業からも独立して、「顧客」に向き合う存在であるべきではないか。自分はそう考えている。

自分が経験した「QA＝テスト」の違和感を、言語化して整理して、同じ違和感を持つ人に届けたい。そしてもうひとつ。違和感すら感じていない人にも届けたい。「テスター」と呼ばれ、IT業界の最下層に置かれていると感じている人。あなたがやっている仕事の先には、もっと広い世界がある。それを知るだけで、見える景色が変わる。

品質を自分たちの手に取り戻す。テストを外に出して終わりにするのではなく、品質を自分たちで考え、自分たちで仕込む。顧客に届く品質を、自分たちの意志でつくる。この本を書いた動機はそこにある。


## 0-2. なぜ日本だけ「QA＝テスト」になったのか


「QA＝テスト」という等式は、世界共通の常識ではない。筆者は、日本のソフトウェア業界に特有の現象だと考えている。なぜこうなったのか。歴史を辿ると、3つの段階が見えてくる。


### ウォーターフォール時代の土壌


日本のソフトウェア開発は、長らくウォーターフォール型が主流だった。要件定義→設計→実装→テスト→リリース。工程が明確に分かれていて、最後に「テスト工程」がある。

余談だが、ウォーターフォールの原型とされるウィンストン・ロイスの1970年の論文では、この直線的なモデルは「うまくいかない例」として紹介されている。ロイス自身は反復型の開発を推奨していた。名前だけが一人歩きして、世界中に広まった。

この構造の中で「第三者検証」という業態が生まれた。開発とは別の組織がテストを実行する。客観的な目でソフトウェアを検証する。SIerが開発し、第三者検証会社がテストする。日本独特の分業モデルだ。

この時点では、呼び名は素直に「テスト」だった。テスト会社がテストをする。テスターがテストを実行する。わかりやすい。まだ混乱はなかった。


### 「アジャイル」の上陸と誤解


2000年代に入り、アジャイル開発が日本に上陸した。

アジャイルマニフェストの原文を読んだことがあるだろうか。4つの価値と12の原則が書いてある。そこには「スプリント」も「バックログ」も「デイリースクラム」も書かれていない。アジャイルマニフェストは工程管理の方法論ではなく、「ソフトウェア開発において何を大事にするか」の価値観の宣言だ。

ところが日本では、アジャイルは「ウォーターフォールの工程を短く回す方法論」として受容された。半年のウォーターフォール（WF）プロジェクトを2週間のスプリントに分割する。ミニウォーターフォールの出来上がりだ。要件→設計→実装→テストを2週間で回す。形はアジャイル。中身はWFの圧縮版。

アジャイルマニフェストがいう「動くソフトウェアを優先する」は「ドキュメントを書かなくていい」と読み替えられ、「変化に対応する」は「計画を立てなくていい」と解釈された。本質が伝わらないまま、形だけが導入された。

この誤解が、次の混乱を呼ぶ。


### 「QA」というラベルの流入


海外のアジャイルチームには「QA Engineer」というロールがあった。

スクラムチームの中にQAがいる。QAは単にテストを実行するのではなく、品質全体に責任を持つ。要件定義の段階からテスト観点を持ち込む。受け入れ基準を開発者と一緒に定義する。テスト戦略を考える。品質メトリクスを設計する。テスト実行はその活動のほんの一部だ。

日本の会社は、このロールの名前だけを輸入した。「QA Engineer」というタイトルはかっこいい。市場でのブランディングにも使える。単価も上げやすい。

しかし、中身は輸入しなかった。プロセス改善、品質戦略、メトリクス設計、要件レビューへの品質観点の持ち込み。これらの活動は持ち込まれなかった。タイトルが「テスター」から「QAエンジニア」に変わっただけで、やっていることは1ミリも変わっていない。仕様書を受け取り、テスト設計書を書いて、テストを実行し、バグを報告する。それだけだ。

第三者検証会社もこの流れに乗った。「テストサービス」を「QAサービス」にリブランドした。提案資料の表紙が変わった。営業トークが変わった。単価が少し上がった。中身のサービスは変わっていない。

採用市場でも同じことが起きた。「テスター募集」では人が来ない。「QAエンジニア募集」にすると応募が増える。実態は同じテスト実行でも、タイトルが「QA」の方が魅力的に映る。こうして、供給側も需要側も「QA＝テスト」を強化する方向に動いた。

業界全体で「テスト」が「QA」に置き換わった。ラベルだけが。


### この混乱が20年続いている


2000年代に始まったこの混乱は、2026年の今も続いている。

求人サイトで「QAエンジニア」を検索してみてほしい。業務内容を読むと、多くはテスト設計とテスト実行だ。品質戦略やプロセス改善が業務内容に含まれているものは少ない。「QAエンジニア」という肩書で採用されて、やることはテスト実行。20年前と構造が変わっていない。

海外では、品質に関わるロールはすでに次の段階に進化している。Quality Engineering（品質工学）、Quality Coach（品質コーチ）、Quality Advocate（品質推進者）。テスト実行から離れ、品質を組織全体に組み込むロールへと変わっている。テスト実行はCI/CDで自動化し、人間が判断・設計に集中する分業が進んでいる。

日本は「QA＝テスト」のまま止まっている。この停滞は、ソフトウェアの品質だけでなく、品質に関わる人のキャリアにも影響している。テスト実行しかしたことがない「QAエンジニア」が、AI時代にどう生き残るのか。[第6章](/books/testing-not-equals-qa/chapter6)で詳しく扱うが、答えの鍵は「QA＝テスト」を卒業することにある。


### なぜ「今」この本なのか


2026年、テスト実行の現場が変わり始めている。

AIがテストケースを生成する。リグレッションテストを自動で回す。探索的テストの候補を提案する。1年前まで「将来こうなるかも」だった話が、目の前で起きている。

ここで「QA＝テスト」の等式が致命傷になる。

テスト実行がAIに移るとき、「QA＝テスト」の世界にいる人は立ち位置を失う。仕事を奪われる、という単純な話ではない。テスト実行以外の品質保証活動を知らないから、「じゃあ自分は何をする人なのか」に答えられなくなる。

品質保証活動の全体像が見えている人は、この問いに答えられる。テスト実行はAIに渡して、自分はテスト戦略を設計する。品質メトリクスを組み立てる。リリース判定基準を定める。プロセスの弱点を見つけて改善案を出す。AIが「実行」を、人間が「判断」を担う。やることは明確だ。

でも「QA＝テスト」のまま止まっている人には、この分担が見えない。テスト実行以外にどんな品質保証活動があるのか、知る機会がなかったからだ。

自分がビットキーで品質戦略をやっていて、この問題を肌で感じている。組織的に、テスト戦略の立案や品質メトリクスの設計といった経験が浅い現場が多い。「うちのプロダクトの品質って何だろう」をチームで話し合ったことがない。そういう組織のほうが多い。

以前、テスト実行を長年やってきた方と話す機会があった。「QAエンジニアとして何年やっていますか」と聞くと「8年です」と返ってきた。「テスト以外にどんな品質保証活動をしていますか」と聞くと、少し考えて、「テスト設計もやっています」と答えた。テスト設計はテストだ。品質保証活動ではあるが、テストの範囲の中の話だ。8年間QAエンジニアという肩書で働いて、テストの外に出たことがない。その方が悪いのではない。テストの外に何があるのかを教えてくれる場所がなかった。

個人の責任ではない。業界が「QA＝テスト」という等式を20年間放置してきた結果だ。等式がテスト実行以外の品質保証活動を見えなくした。

変化の兆しは見え始めている。カンファレンスでは「テスト自動化」の隣に「品質戦略」「品質文化」のセッションが並ぶようになった。採用では「テスト実行ができる人」ではなく「品質を仕組める人」を求める求人が増えている。ただし、求人票の要件に書いてある「品質戦略の策定経験」「品質メトリクスの設計経験」を満たせる人材がいない。需要はあるのに供給が追いつかない。20年間テスト実行に閉じてきた業界が、品質を仕組める人材を育ててこなかったから当然だ。

だから今、この等式を覆しにいく必要がある。AIがテスト実行を塗り替えていく前に、テストの先にある世界を知ること。それが、この本を今書いた理由だ。

この本は、その卒業を手伝うために書いた。「テスト」と「QA」を正しく使い分けるところから始めて、テストの先にある品質保証活動の世界を、一緒に見に行こう。


## 0-3. この本が伝えたいこと


伝えたいことは、3つに集約される。

**QA＝テストではない。** テストは「測る」行為。QCは「診る」行為。QAは「仕込む」行為。この3つは別物だ。テストはQAの一部であって、全部ではない。

**テストの先に、広大な品質保証活動の世界がある。** テスト実行以外にも、品質に貢献する活動は20種類以上ある。テスト戦略の策定、品質メトリクスの設計、プロセス改善、リスク分析、品質定義ワークショップ。テスト実行だけに閉じていると、この世界が見えない。

**等式を卒業すると、あなたのキャリアが変わる。** 「QA＝テスト」の等式の中にいると、キャリアパスは「テスト実行→テストリーダー→テストマネージャー」の一本道しかない。等式を卒業すると、テスト設計→テスト戦略→品質戦略という別の道が開ける。AI時代にテスト実行の価値が急速に変化する中で、この違いがキャリアの分岐点になる。

この本は理論書ではない。テストの先にある世界を、たとえ話と図解と実践ワークで体験してもらうための本だ。

各章にはワークを用意した。理屈だけで理解するのは難しい。手を動かして「自分の現場に当てはめたらどうなるか」を考えることで、初めて実感がわく。読み終わったときに「明日から1つやってみよう」と思ってもらえることを目指して、各章にワークや具体例を散りばめた。


### この本で扱わないこと


範囲を明確にしておく。

この本はテスト技法の教科書ではない。同値分割や境界値分析の解説は最小限にとどめている。テスト技法を体系的に学びたい人は、各章末の推薦書籍を参照してほしい。

テスト自動化のコードも書かない。SeleniumやPlaywrightのチュートリアルは含まれていない。自動化は品質保証活動の手段の1つであり、本書の主題はその手段の上位にある「何をテストし、何をテストしないか」の判断だ。

特定のテスト管理ツールの使い方も扱わない。QaseやTestRailの操作手順ではなく、どんなツールを使っていても適用できる「テスト戦略の考え方」を伝える。

この本が扱うのは「テストの先にある品質の世界」だ。テスト技法をすでに知っている人にとっては次のステップの話。まだ知らない人にとっては「テスト技法を学ぶ動機」になる話。どちらの立場でも読めるように書いたつもりだ。


## 0-4. 対象読者と読み方ガイド


この本は、品質やテストに関わるすべての人に向けて書いた。ただし、立場によって特に読んでほしい章が違う。

**QAエンジニア・テスター**
全章を[第1章](/books/testing-not-equals-qa/chapter1)から順番に読むのがおすすめ。自分の仕事を「テスト」「QC」「QA」に仕分けるところから始めて、テストの先にある活動を具体的に学んでいく流れになっている。特に[第3章](/books/testing-not-equals-qa/chapter3_1)のQA活動カタログで「テスト以外に何をすればいいか」が具体的にわかるはずだ。

**開発リード・エンジニアリングマネージャー**
第1〜2章で「QA＝テスト」の弊害を理解し、[第4章](/books/testing-not-equals-qa/chapter4)の品質定義ワークショップをチームで試してみてほしい。「品質は誰の仕事か」という問いへの答えが変わるはずだ。[第5章](/books/testing-not-equals-qa/chapter5_1)のテスト戦略は、開発プロセスに品質保証活動を組み込む具体的な方法を扱っている。

**プロダクトマネージャー**
[第4章](/books/testing-not-equals-qa/chapter4)の品質定義と[第6章](/books/testing-not-equals-qa/chapter6)のAI時代の話が特に関係する。品質をプロダクト戦略にどう組み込むか、テスト実行の自動化が進む中でQAの予算をどう考えるか、という視点で読んでほしい。

**ソフトウェア開発に関わる初心者**
[第1章](/books/testing-not-equals-qa/chapter1)から順番に。専門用語には補足解説をつけているので、前提知識がなくても読み進められる。章末のFAQと推薦書籍も活用してほしい。


## 0-5. 本書の全体マップ


7つの章が、どういう順番で何を伝えるか。1枚の図にまとめた。


![本書の全体マップ](/images/books/testing-not-equals-qa/diag_00_book_map.png)


第1〜2章で「なぜQA＝テストが問題なのか」を理解する。[第1章](/books/testing-not-equals-qa/chapter1)で勉強のたとえを使ってテスト・QC・QAを定義し、[第2章](/books/testing-not-equals-qa/chapter2)でこの等式を放置すると組織に何が起きるかを「構造的負債」として描く。

第3〜5章は手を動かすパートだ。[第3章](/books/testing-not-equals-qa/chapter3_1)でテスト以外の品質保証活動を20種類以上カタログにし、[第4章](/books/testing-not-equals-qa/chapter4)でチームと一緒に「品質とは何か」を合意するワークショップを実践する。[第5章](/books/testing-not-equals-qa/chapter5_1)はテスト戦略の立て方。「何をテストしないか」を決めるプロセスを扱う。ここが本書で最も技術的な章になる。

各章は独立して読めるように書いてあるので、興味のある章から読んでも構わない。ただし、[第1章](/books/testing-not-equals-qa/chapter1)の「テスト＝測る、QC＝診る、QA＝仕込む」という定義は本書全体の土台になる。ここだけは先に読んでおいてほしい。

各章の末尾には補足セクションを設けた。用語解説、たとえ話・図解、あるあるコラム、やってみようワーク、FAQ、推薦書籍。本文だけだと抽象的になりがちな話を、具体例や手を動かすワークで補っている。


### 3つの読み方


この本は3通りの読み方ができる。自分のスタイルに合うものを選んでほしい。

**通読コース（7時間）**
[第1章](/books/testing-not-equals-qa/chapter1)から順番に読む。定義から始まり、構造的負債、品質保証活動カタログ、品質定義、テスト戦略、AI時代、実践事例と積み上がっていく。初読はこのコースがおすすめ。各章のワークもやると、自分の現場に引きつけて理解できる。読み終えたあとに全体マップを見返すと、章同士のつながりが見えて二度おいしい。

**つまみ食いコース（2〜3時間）**
時間がない。今すぐ使えるものがほしい。その場合は[第1章](/books/testing-not-equals-qa/chapter1)を読んだあと、[第3章](/books/testing-not-equals-qa/chapter3_1)（QA活動カタログ）と[第4章](/books/testing-not-equals-qa/chapter4)（品質定義ワークショップ）に飛んでほしい。[第3章](/books/testing-not-equals-qa/chapter3_1)で「テスト以外にやれること」の全体像をつかみ、[第4章](/books/testing-not-equals-qa/chapter4)のワークショップを来週のチームミーティングで試す。それだけで景色が変わる。手応えを感じたら[第5章](/books/testing-not-equals-qa/chapter5_1)のテスト戦略に進むと、品質保証活動を日々の開発プロセスに組み込む具体的な方法がわかる。

**キャリア設計コース（3時間）**
「自分のキャリア、このままでいいんだろうか」がモチベーションなら、[第1章](/books/testing-not-equals-qa/chapter1)→[第2章](/books/testing-not-equals-qa/chapter2)→[第6章](/books/testing-not-equals-qa/chapter6)の順で読む。QA＝テストの構造を理解し、それが組織とキャリアに与えている影響を知り、AI時代にどう動くかを考える。そのあとで[第3章](/books/testing-not-equals-qa/chapter3_1)に戻ると、次に身につけるべきスキルが具体的に見えてくる。[第7章](/books/testing-not-equals-qa/chapter7)の品質組織のつくり方は、ビットキーの事例を交えた実践編として、QA＝テストを卒業した組織がどう動いているかのリアルな参考になる。

どのコースでも、[第1章](/books/testing-not-equals-qa/chapter1)の「テスト＝測る、QC＝診る、QA＝仕込む」は必ず通る。ここが全章の共通言語だ。

各章にはワークがついている。通読コースでは全部やるのが理想だが、つまみ食いコースやキャリア設計コースでは飛ばしても大丈夫だ。ただし[第4章](/books/testing-not-equals-qa/chapter4)の品質定義ワークショップだけは、どのコースでもやってみてほしい。チームで「品質とは何か」を言語化する体験は、本を読むだけでは得られない。1回やると、品質への解像度が一段上がる。

章の途中で他の章を参照する箇所には、該当する章番号を明記してある。気になったら先にそちらを読んでもいい。途中で寄り道して、また戻ってくる。そういう読み方も歓迎だ。


## 0-6. 読前チェック：あなたの現場は？


本書を読む前に、15個の質問に答えてみてほしい。今の自分の現場の状態を確認するためのチェックリストだ。正解はない。自分の現場を素直に振り返って、「はい」か「いいえ」かを考えてみてほしい。

「はい」なら ○、「いいえ」なら × をつけてほしい。

| # | 質問 | ○/× |
|---|---|---|
| 1 | QAチームの主な仕事はテスト実行だ |  |
| 2 | 「テスト」と「QA」を意識的に使い分けていない |  |
| 3 | テスト戦略という文書がチームにない |  |
| 4 | バグの根本原因分析を定期的にやっていない |  |
| 5 | 品質の定義がチーム内で合意されていない |  |
| 6 | リリース判定に数値的な根拠がない |  |
| 7 | テストフェーズに入るまで品質の話が出ない |  |
| 8 | 同じパターンのバグが繰り返し発生している |  |
| 9 | テストケースの件数が品質の指標になっている |  |
| 10 | QAエンジニアのキャリアパスが不明確だ |  |
| 11 | QAの活動が「テスト設計→実行→バグ報告」で完結している |  |
| 12 | 品質に関する数値を定期的にチームで振り返る場がない |  |
| 13 | 開発チームにとってQAは「最後にテストする人」だ |  |
| 14 | テスト実行がAIに置き換わったらQAチームの存在意義を説明できない |  |
| 15 | 「品質を上げたい」というと最初に出るのは「テストを増やそう」だ |  |


:::message
**結果を見る（自分で考えてから開こう）**

**○が11個以上**: 「QA＝テスト」がかなり定着している。本書はまさにあなたのために書いた。[第1章](/books/testing-not-equals-qa/chapter1)から順番に読み進めてほしい。

**○が6〜10個**: テストの先を意識し始めている段階。[第3章](/books/testing-not-equals-qa/chapter3_1)のQA活動カタログが特に効くはずだ。

**○が5個以下**: すでにQA＝テストを卒業しつつある。[第5章](/books/testing-not-equals-qa/chapter5_1)のテスト戦略や[第6章](/books/testing-not-equals-qa/chapter6)のAI時代の話が参考になる。

:::

このチェックリストは、今の現在地を確認するためのものだ。○が多いからダメという話ではない。

もう1つ、自分自身への問いも置いておく。○×ではなく、自由に考えてみてほしい。

- あなたのチームで「品質」という言葉が出るのは、開発のどの段階か？
- テスト以外で品質に貢献しているといえる活動を、3つ挙げられるか？
- 「あなたのプロダクトの品質とは何ですか」と聞かれたら、30秒で答えられるか？
- 1年後、あなたの品質への関わり方をどう変えたいか？

答えはすぐに出なくていい。出なくて当然だ。この本を読み進めるうちに、少しずつ言葉になっていく。読み終わったあと、もう一度この問いに戻ってきてほしい。そのとき、自分の中で何が変わったかがわかる。

あとがきで、同じチェックリストをもう一度やる。読了後に見え方がどう変わったか、確認してみてほしい。同じ質問なのに、答えが変わっているかもしれない。あるいは、質問の意味自体が読む前と後で変わっているかもしれない。○の数が減ることもあれば、「この質問の意図がようやくわかった」と感じることもあるはずだ。

チェックリストの結果がどうであれ、この本を手に取った時点であなたは「テストの先」に目を向けている。それだけで、読む前の自分とは違う場所に立っている。

では、[第1章](/books/testing-not-equals-qa/chapter1)から始めよう。
