## コンセプト

探索的テストを「1人で黙々とやる作業」から「Claudeと壁打ちしながら進めるセッション」に変える。テストチャーターの設計から、実行中の気づきの深掘り、セッション後の分析まで、Claudeをペアテスターとして使い倒す実践記事。

## 想定読者

- 探索的テストを「なんとなく触ってバグを見つける」だと思っている人
- 1人でテストしていて、視野が固定化している自覚がある人
- テストチャーターを書いたことがない人

## キーメッセージ

- 探索的テストは「自由に触る」ではなく「仮説を持って探索する」
- 人間の「嗅覚」（ここ怪しい）× AIの「網羅性」（見落としパターン提示）
- ペアテストの相手がいない現場でも、Claudeがその役割を果たせる

## 構成案

### 導入
- 探索的テストあるある：「自由にテストして」と言われて困る
- ペアテストしたいけど、人がいない
- Claudeをペアテスター役にする発想

### Phase 1：チャーター設計（テスト前）

**Claudeに渡すもの：**
- 今回の変更内容（PRやリリースノート）
- 対象機能の仕様概要
- 「ここが気になる」という自分の直感

**Claudeと作るチャーター：**
- 探索テーマ：「認証リファクタ後のセッション管理」
- 注目ポイント：「複数デバイス同時ログイン、トークン有効期限、ログアウト後の状態」
- 時間：30分

**ポイント：**
- チャーターは「何を探索するか」の仮説。テストケースではない
- Claudeが網羅的に候補を出し、人間が「今回はここに絞る」を決める

### Phase 2：探索中の壁打ち（テスト中）

**実行中にClaudeに聞くこと：**
- 「セッションタイムアウト後にAPIを叩いたら200が返った。これ正常？」
- 「同時ログインで片方が強制ログアウトされるはずが、両方生き残ってる。関連する仕様ある？」
- 「この画面遷移、なんか遅い気がする。パフォーマンス観点で他に見るべきところは？」

**Claudeの役割：**
- 仕様の確認・解釈の壁打ち相手
- 「その現象が起きるなら、こっちも確認したほうがいい」の提案
- 類似バグパターンの提示

**人間の役割：**
- 「なんか変」という直感（AIにはない）
- 操作の順序やタイミングの工夫
- ビジネスインパクトの判断（「これはヤバい」か「許容範囲」か）

### Phase 3：セッション振り返り（テスト後）

**Claudeにやらせること：**
- セッション中のメモを構造化（バグ/気づき/疑問/次回チャーター候補）
- 発見した問題の重要度分類
- テストカバレッジの可視化（何を探索して、何を探索しなかったか）

**人間がやること：**
- 「次に探索すべきはここ」の判断
- バグレポートの優先度決定
- チームへの共有

### 実例：30分セッションのログ
- 実際のClaudeとのやり取りを時系列で見せる
- どこで人間の直感が効いたか、どこでClaudeの網羅性が効いたかを注釈

### vs 従来の探索的テスト

| | 1人で探索 | Claudeとペア探索 |
|---|---|---|
| チャーター設計 | 自分の経験頼み | 経験 + AIの網羅的候補 |
| 探索中の判断 | 自分の中で完結 | 壁打ちで深掘りできる |
| 視野の固定化 | 起きやすい | AIが別角度を提示 |
| 振り返り | メモが散らかる | 構造化を代行 |
| 再現性 | 低い（記憶頼み） | ログが残る |

### まとめ
- 探索的テストは「センス」ではなく「仮説 → 探索 → 学び」のサイクル
- Claudeはペアテスターとして3つの役割を果たす：チャーター設計の壁打ち、探索中の深掘り、振り返りの構造化
- 人間の嗅覚は代替できない。でも、嗅覚の精度をAIが上げてくれる

## メモ

- 実際にClaudeで探索的テストをやってみた録画 or スクショがあると最強
- 「ペアプログラミング」の概念を知っている読者にはアナロジーが効く
- テスト管理ツール（Qase）との連携も書けるとさらに実践的
- Phase 2の「探索中の壁打ち」が一番面白い部分。ここを厚く書く
