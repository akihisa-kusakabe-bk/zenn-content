:::message
「次のリリースのテスト計画書、前回のコピペでいいよね？」
この一言に反論できなかったことがあるなら、この記事はきっと役に立つ。
:::

**30ページのテスト計画書。中身は前回のコピペ。変えたのは日付と担当者だけ。**

心当たりはないだろうか。

テスト計画書は大事だと言われる。だから作る。でも前回と同じ内容をコピペして、「テスト期間」と「担当者」だけ差し替えて、レビューも形式的に通って終わり。誰も中身を読んでいない。でも「計画書がある」という事実だけが求められている。

:::details リスクベースドテストとは
すべてを均等にテストするのではなく、リスクの高い箇所に集中してテストする考え方。変更の影響度や過去のバグ傾向をもとに優先順位をつける。
:::

自分がやったのは、形骸化した30ページのコピペ計画書を、Claude Codeを使って**5ページのリスク分析**に作り替えることだ。計画書を「捨てろ」とは言わない。**中身の作り方を変えよう**、という話だ。

なぜコピペになるか。毎回変わるべき「今回のリスク」まで前回のコピペだからだ。

## Before / After：計画書はこう変わる

### Before：コピペ計画書

```
■テスト計画書 v2.4.0
├─ 1. はじめに（目的、範囲、定義）         ... 5ページ
├─ 2. テスト戦略（方針、種別、ツール）     ... 8ページ
├─ 3. テスト対象と観点                      ... 10ページ
│    └─ 全機能を均等にテスト（85観点）
├─ 4. スケジュール                          ... 3ページ
├─ 5. 体制と役割                            ... 2ページ
└─ 6. リスクと対策                          ... 2ページ
     └─ 「特になし。全体を網羅的にテストする」
─────────────────────────────────────────
合計 30ページ（うち25ページがコピペ）
```

### After：リスク分析ベースの計画書

```
■テスト計画書 v2.4.0
├─ 1. 今回の変更サマリ                      ... 1ページ
│    └─ 変更4件の影響分析
├─ 2. リスク分析                            ... 2ページ
│    ├─ 変更 × 過去バグの突合結果
│    ├─ リスクマトリクス
│    └─ 人間の調整（理由付き）
├─ 3. テスト方針（リスクベース）            ... 1ページ
│    ├─ カード決済：重点＋探索的テスト
│    ├─ 購入確認画面：全画面テスト
│    ├─ コンビニ決済：PayPayフロー重点
│    ├─ 注文履歴：互換性テスト
│    └─ メール通知：自動テストのみ
├─ 4. スケジュールと担当                    ... 1ページ
└─ 5. 前回の戦略からの変更点                ... なし（変更時のみ記載）
─────────────────────────────────────────
合計 5ページ（全ページが今回固有の内容）
```

変わったのはページ数だけではない。

| | Before | After |
|---|---|---|
| リスク分析 | 「特になし」 | 変更 × 過去バグの突合 |
| テスト配分 | 全機能均等（85観点） | リスクベース（高リスク領域に厚く） |
| 読む人 | いない | チーム全員（5ページなら読める） |
| 作成時間 | 2時間（コピペ＋調整） | 1時間（Claude Codeに分析させて人間が調整）※自分のチームで試した感覚 |
| 価値 | 「計画書がある」という事実 | 「何が危ないか」がわかる |

**30ページの儀式が、5ページの武器になった。**

ここからは、このAfterをどう作ったかを見せる。

## やること：変更差分 × 過去バグ = リスクの在処

考え方はシンプルだ。

1. **今回何が変わったか**（リリースノート、Git diff）
2. **過去どこで壊れたか**（バグ傾向データ）
3. この2つをClaude Codeに突合させて、**危険地帯を特定**する

必要なインプットは3つ。全部揃わなくていい。

| インプット | 内容 | ないとダメ？ |
|---|---|---|
| リリースノート / Git diff | 今回何が変わったか | 必須 |
| 過去のバグ傾向データ | 過去どこで壊れたか（Jira、Qase等から） | あると精度が上がる |
| 前回のテスト計画書 | 前回何をテストしたか | なくても可 |

もっとも重要なのはリリースノートだ。

```
【v2.4.0 リリースノート】

## 変更内容
- 決済処理のリファクタリング（カード決済モジュール分離）
- コンビニ決済に「PayPay」追加
- 購入確認画面のUIリニューアル（React移行）
- 注文履歴APIのレスポンス形式変更（v1→v2）

## 影響範囲（開発者申告）
- 決済フロー全般
- フロントエンド：購入確認画面、注文履歴画面
- API：/api/v2/orders
```

バグデータは領域ごとの件数と重大度がわかればいい。前回の計画書は形骸化していても「前回何をテストしたか」の記録として使える。

:::message alert
AIツールに社内の機密情報や個人情報を入力しないでください。バグデータや計画書をつかう場合は、固有名詞や実データをダミーに置きかえるか、社内で承認されたAIツールを利用してください。
:::

## Claude Codeにやらせること

インプットを渡して、以下の分析をClaude Codeに依頼する。

### Step 1: 変更影響 × 過去バグの突合

```
以下のリリースノートと過去バグデータを突合して、
「変更が入る × 過去にバグが多い」領域を特定してください。
危険度を最高/高/中/低で判定し、判定理由も付けてください。

【リリースノート】
（貼る）

【過去バグデータ】
（貼る）
```

Claude Codeの出力例：

| 領域 | 今回の変更 | 過去バグ | 危険度 | 判定理由 |
|---|---|---|---|---|
| カード決済処理 | モジュール分離 | 12件（高4） | **最高** | 過去バグ最多の領域にリファクタリングが入る |
| 購入確認画面 | React移行 | 7件（高2） | **高** | UI全面刷新 × 直近1カ月でバグ発生 |
| コンビニ決済 | PayPay追加 | 3件（高0） | 中 | 新規実装だが、既存部分は安定 |
| 注文履歴 | API形式変更 | 2件（高0） | 中 | 変更あるが過去バグは少ない |
| 決済完了メール | 間接的影響 | 1件（高0） | 低 | 間接的影響のみ。過去バグも少ない |

**「カード決済 × モジュール分離」がもっとも危険。** 過去にもっともバグが出ている領域に、構造的な変更が入る。ここをコピペ計画書の「均等配分」で乗り切ろうとするのは無謀だ。

### Step 2: リスクマトリクスで優先順位をつける

:::details リスクマトリクスとは
影響度と発生確率の2軸でリスクを分類する表。高影響 × 高確率の領域から優先的にテストリソースを割り当てる判断につかう。
:::

```
以下の突合結果をもとに、影響度 × 発生確率のリスクマトリクスを作成してください。
各領域をマトリクス上に配置し、テスト戦略の推奨も付けてください。
```

Claude Codeの出力例：

|  | 発生確率：高 | 発生確率：中 | 発生確率：低 |
|---|---|---|---|
| **影響度：高** | カード決済処理 | 購入確認画面 |  |
| **影響度：中** |  | コンビニ決済（PayPay） | 注文履歴 |
| **影響度：低** |  |  | 決済完了メール |

テスト戦略の推奨：

| 領域 | リスク | 推奨テスト戦略 |
|---|---|---|
| カード決済処理 | 最高 | 重点テスト＋探索的テスト。リファクタリング前後の挙動比較 |
| 購入確認画面 | 高 | UIの全画面テスト。旧画面との差分確認 |
| コンビニ決済 | 中 | PayPay固有のフローを重点テスト。既存決済は回帰テスト |
| 注文履歴 | 中 | API v1→v2の互換性テスト。表示崩れの確認 |
| 決済完了メール | 低 | 既存の自動テストで確認。手動テストは不要 |

ここまでがClaude Codeの仕事だ。ここから先が人間の出番。

### 人間の文脈でリスクを補正する

Claude Codeが出したリスクマトリクスは「たたき台」だ。人間が調整する。

Claude Codeにはわからないことがあるからだ。

- 「カード決済のリファクタリングは、設計レビュー済みで構造が単純化される方向の変更」→ リスクを1段階下げる
- 「購入確認画面のReact移行は、外部委託チームが担当。コードレビューがまだ完了していない」→ リスクを1段階上げる
- 「コンビニ決済のPayPay追加は、他の決済手段と共通基盤を使っている」→ 共通基盤の回帰テストを追加

Claude Codeは変更差分とバグデータから機械的にリスクを計算する。でも「設計レビュー済みだからリスクが下がる」「外部委託だからリスクが上がる」といった**文脈は、現場にいる人間にしかわからない**。

## 「でも、上司が30ページの計画書を求めるんです」

わかる。フォーマットが決まっている現場、計画書のボリュームが品質の証拠として扱われる現場は多い。

その場合は、**見た目は30ページの計画書、中身はリスク分析**という戦略が使える。

- 戦略部分（方針、種別、ツール）は「テスト戦略書」として別ドキュメントに分離する。計画書からは参照リンクだけ貼る
- 計画書本体は「今回のリスク分析」「今回のテスト方針」に集中させる
- ページ数が足りなければ、リスク分析の詳細（AIの分析ログ、突合結果の全件）を付録として添付する

フォーマットを変えられなくても、**中身の作り方を変えることはできる**。コピペの25ページを「戦略書への参照」に置きかえるだけで、残りの5ページに集中できる。

## まとめ

計画書の問題は、**「今回のリスク」が入っていないこと**だ。

Claude Codeを使えば、変更差分と過去バグデータの突合は数分で終わる。人間がやるべきは、その結果に文脈を加えてリスク判断を調整することだ。

| 役割 | AIの仕事 | 人間の仕事 |
|---|---|---|
| 変更影響 | 差分から影響範囲を特定 | 間接的影響の見落としを補う |
| リスク分析 | 変更 × 過去バグの突合 | 文脈（設計レビュー済み、外部委託等）で調整 |
| テスト配分 | リスクに応じた配分案 | 最終的な優先順位を決定 |

コピペ計画書のままか、リスク分析に作り替えるか。目の前の計画書はどちらだろうか。

次にテスト計画書を作るとき、まず変更差分をClaude Codeに渡すところから始めてみてほしい。「今回のリスクは何か」から始めるだけで、計画書が使えるものになる。
