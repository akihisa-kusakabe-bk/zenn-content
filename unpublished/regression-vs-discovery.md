リリースのたびに同じリグレッションテストを手動で回して、新機能のテストに着手できるのはいつもリリース直前。心当たりはないだろうか。

テストには、2つのまったく異なる仕事が混ざっている。

1つは、**壊れていないことを確認する仕事**。もう1つは、**新しい不具合を見つける仕事**。

この2つは目的もスキルも違うのに、多くの現場では区別されていない。その結果、テスターの時間は「確認作業」に追われ、「発見」に使える時間がほとんど残らない。

この記事では、この2つを分けて考えることが、なぜテストの負荷を下げ、品質を上げることにつながるのかを整理する。

## たとえ話：警備員と探偵

テストの2つの仕事は、**警備員と探偵**にたとえるとわかりやすい。

**警備員**は、毎日同じルートを巡回して、異常がないことを確認する。「昨日と同じ状態か？」が仕事だ。ルートも手順も決まっている。

**探偵**は、まだ誰も気づいていない問題を探す。「何かおかしいところはないか？」が仕事だ。経験と勘と推理力が必要になる。

この2つはまったく違う仕事なのに、テストの現場では同じ人が同じ時間にやっていることが多い。しかも、警備の巡回が忙しすぎて、探偵の仕事に使える時間がほとんどない。

## テストの2つの仕事

2つの仕事の性質を比較してみる。

| | 確認する（リグレッション） | 見つける（探索・新機能） |
|---|---|---|
| 目的 | 既存機能が壊れていないことの確認 | 未知の不具合の発見 |
| 期待値 | 明確（前回と同じ動作） | 不明確（何が起きるかわからない） |
| 実行頻度 | 毎リリース・毎スプリント | 新機能追加時・変更時 |
| 求められるスキル | 正確な再現と確認 | 直感・経験・想像力 |
| 自動化との相性 | 高い | 低い |
| たとえ | 警備員の巡回 | 探偵の捜査 |

「確認する」は、答えが決まっている問題を繰り返し解く作業だ。「見つける」は、まだ誰も気づいていない問題を探す作業だ。

この2つを同じ「テスト」として同じ人が同じ時間に行っている現場が、実は非常に多い。

:::details リグレッションテストとは？
「回帰テスト」とも呼ばれる。コードを変更した後に、既存の機能が壊れていないことを確認するテスト。前回と同じ手順で同じ結果が出ればPass。リリースのたびに繰り返し実行する。
:::

## リグレッションが現場を圧迫している

リリースのたびに、こんな光景を見かけないだろうか。

- 既存機能の確認テストだけで2〜3日かかる
- 新機能のテストに着手できるのはリリース直前
- テスターが「ずっと同じテストを回している」と感じている

ある現場では、テスト工数の**7割以上**がリグレッションテストに費やされていた。毎回同じ手順書を開いて、同じ画面を確認して、同じ期待結果と突き合わせる。

テスターの時間は有限だ。確認作業に工数を取られれば取られるほど、新しい不具合を見つけるための時間は削られていく。警備の巡回で1日が終わってしまい、探偵の仕事がまったくできない状態だ。

## 自動化すべきは「確認作業」

ここで、テスト自動化の話になる。

「テスト自動化」と聞くと、すべてのテストを自動化するイメージを持つかもしれない。しかし、自動化が本当に効果を発揮するのは**「確認する」仕事**のほうだ。

なぜなら、リグレッションテストには自動化に必要な条件が揃っているからだ。

- **期待値が明確**：前回と同じ動作をすればPass
- **手順が定型的**：同じ操作を毎回繰り返す
- **繰り返し実行する**：リリースのたびに必要

一方、「見つける」仕事は、自動化が難しい領域だ。何を探すかが事前にわからないから、スクリプトに書けない。ユーザーの気持ちになって「ここ、おかしくない？」と感じるのは、人間の仕事だ。

警備員の巡回はロボットに任せられる。でも、探偵の捜査はロボットには難しい。

### どのテストレベルで自動化するか

自動化する際に重要なのは、**どのテストレベルで行うか**だ。

| テストレベル | 自動化のROI | 理由 |
|---|---|---|
| API／結合テスト | **高い** | インターフェースが安定しているため壊れにくい。メンテコストが低い |
| コアフローのE2E | **高い** | ユーザー視点で「壊れていない」ことを保証できる。コアフローに絞れば安定する |
| ユニットテスト | 注意が必要 | 実装に密結合するため、リファクタで壊れやすい。メンテコストが高くなりがち |

よく「E2Eテストはフレイキーでメンテが大変」と言われるが、これは条件次第だ。XPathやCSSクラスに依存したセレクタ設計や、全画面を網羅しようとするアプローチでは確かに壊れやすくなる。しかし、`data-testid`のような専用属性を使い、コアフローに絞って設計すれば、E2Eは十分に安定する。Playwright・Cypressなどの現代的なツールもこの安定性を後押ししている。

API／結合テストとE2Eテストは、守る領域が異なる。API／結合はデータの整合性やビジネスロジックを、E2Eはユーザーが実際に触る画面の動作を保証する。**どちらか一方ではなく、組み合わせて使う**のが現実的だ。

:::details E2Eテストとは？
End-to-Endテスト。ユーザーが実際に操作するのと同じように、ブラウザを自動操作してテストする手法。「ログインしてダッシュボードが表示されるか」のような、ユーザー視点の動作確認に向いている。
:::

## 人間がやるべきは「発見」

確認作業を自動化で手離れさせたとき、テスターの時間が空く。その時間を使うべきなのが、「見つける」仕事だ。

- **探索的テスト**：仕様書にない使い方、ユーザーが実際にやりそうな操作を試す
- **ユーザー視点のレビュー**：「この動線、わかりにくくない？」「この文言、誤解を招かない？」
- **仕様の矛盾の発見**：機能Aと機能Bを組み合わせたときの挙動を考える
- **リスク分析**：変更の影響範囲を予測し、重点的にテストすべき箇所を特定する

これらは、経験と直感と文脈理解が求められる仕事だ。AI時代においても、人間が最も価値を発揮できる領域だ。

:::details 探索的テストとは？
事前にテストケースを用意せず、テスターの知識と経験に基づいてテスト対象を探索する手法。「テストチャーター」と呼ばれる大まかな方向性だけ決めて、テスターの判断で自由にテストする。仕様書の行間にあるバグを見つけるのに向いている。
:::

## 実践：どこから始めるか

「全部自動化しよう」と始めると、大抵うまくいかない。段階的に進めることが大事だ。

### ステップ1：スモークテストから

まずは、最も基本的な動作確認を自動化する。ログインできる、主要画面が表示される、基本的なCRUD操作ができる。APIレベルでビジネスロジックを、E2Eでユーザー操作を、それぞれ10〜20ケース程度で十分だ。これだけで「リリース前の最低限の確認」が自動化される。

:::details スモークテストとは？
「煙が出ないか確認する」が語源。システムの最も基本的な動作だけを確認する簡易テスト。ログインできるか、主要画面が表示されるか、基本操作ができるか。「まず動くか？」を最短で確認する。
:::

### ステップ2：コア機能のリグレッション

次に、ビジネス上最も重要な機能のリグレッションテストを自動化する。「これが壊れたら致命的」な機能から優先的に。全機能を網羅する必要はない。

### ステップ3：CI/CDに組み込む

自動テストをCI/CDパイプラインに組み込み、コードがマージされるたびに自動で実行されるようにする。テスターが手動で実行する必要すらなくなる。

:::details CI/CDとは？
CI（Continuous Integration）は、コードの変更を頻繁に統合して自動テストを回すこと。CD（Continuous Delivery/Deployment）は、テスト済みのコードを自動でデプロイすること。「コードを書いたら自動でチェックして届ける仕組み」くらいの理解で十分だ。
:::

### やらないこと

- すべてのテストケースを自動化しようとしない
- UIテストから始めない（壊れやすいため）
- 自動化の「カバレッジ」を目標にしない（ROIで判断する）

## まとめ

テストには「確認する」仕事と「見つける」仕事がある。

**確認する仕事は、機械に任せよう。** 機械は飽きない。同じことを正確に何百回でも繰り返せる。

**見つける仕事は、人間がやろう。** 「なんか変だな」と感じる力は、まだ人間にしかない。

リグレッションテストの自動化は、「楽をする」ためではない。**人間がやるべき仕事に集中するため**の手段だ。

テスターの時間を「確認」から「発見」にシフトする。それが、テストの負荷を下げながら品質を上げる、最も現実的な方法だ。
