:::message
「テスト戦略を作ってください」と言われて、何から手をつけていいかわからなかった経験はないだろうか。自分はある。
:::

テスト戦略と聞くと身構える。分厚いドキュメントを想像して手が止まる。

でも実際にやってみたら、**5つの問いに答えるだけ**だった。Claude Codeを壁打ち相手にして30分。A4一枚のテスト戦略ができた。

:::details テスト戦略とは
プロジェクト横断で「何を重点的にテストし、何を軽くするか」の方針を定めたもの。テスト計画が「今回どうやるか」なら、テスト戦略は「うちのチームはテストにどう向き合うか」の判断基準。詳しくは「[テスト計画書がコピペになる本当の理由](https://zenn.dev/bitkey_dev/articles/test-plan-vs-strategy)」を参照。
:::

## 完成形：A4一枚のテスト戦略

先に完成形を見せる。

```
■ テスト戦略（勤怠管理システム）

【1. 重要機能】月次集計、打刻処理、給与システム連携
【2. 既知のリスク】月末・月初の境界処理、外部API連携のエラーハンドリング
【3. テスト配分】
  重点：月次集計・打刻・給与連携（全レベルカバー、探索的テスト含む）
  標準：休暇申請・残業申請（結合テストまで）
  軽量：シフト管理画面・管理者設定（単体テストのみ）
【4. テストレベル方針】
  単体：全領域で実施。給与計算ロジックは境界値テスト必須
  結合：重点+標準領域。CI上で自動実行
  E2E：重点領域の主要シナリオ。Playwrightで自動化推進
【5. 終了条件】
  重大バグ0件 / 重点領域カバレッジ85% / 労務担当者の受入確認
```

**これだけだ。** 30ページの大作ではない。A4一枚。でもこの一枚があるのとないのでは、チームの判断基準がまったく違う。

ここから先は、この一枚がどうやって30分でできたかを見せる。

## 「戦略がない」の正体

「うちにはテスト戦略がない」。よく聞く悩みだが、じつは2つのパターンがある。

| パターン | 実態 | 対処 |
|---|---|---|
| **本当にない** | テスト方針が暗黙知。人によって判断が違う | → この記事で作る |
| **あるけど死んでる** | ドキュメントはあるが誰も読んでない | → 5つの問いで書き直す |

どちらも解決策は同じだ。**判断基準を、チームの言葉で文字にする。**

## 準備：Claude Codeに渡す3つのインプット

壁打ちを始める前に、手元に用意するものが3つある。全部揃わなくていい。あるものだけでいい。

| インプット | 具体例 | なくても大丈夫？ |
|---|---|---|
| **プロダクトの概要** | 何をしているサービスか。主要機能の一覧 | 必須。口頭説明レベルでOK |
| **直近の変更・リリース内容** | PRの一覧、リリースノート | あると精度が上がる |
| **過去に痛かったバグ** | インシデント履歴、バグ一覧 | あると重点領域が明確になる |

ポイントは「完璧なデータ」を求めないこと。**「壊れたら困るもの」がわかれば十分**だ。

:::message alert
AIツールに社内の機密情報や個人情報を入力しないでください。バグデータや機能一覧をつかう場合は、固有名詞や実データをダミーに置きかえるか、社内で承認されたAIツールを利用してください。
:::

## 実演：5つの問いをClaude Codeと埋める

架空の勤怠管理システムでClaude Codeと壁打ちしてみた。主要機能は打刻（出退勤記録）、休暇申請、残業申請、シフト管理、月次集計レポート、給与計算システムとの外部連携だ。

### 問い1：壊れたらもっとも困る機能は？

まず自分の直感で3つ挙げる。

```
自分の直感：
1. 打刻処理（出退勤の記録が狂ったら全社員に影響）
2. 月次集計（給与計算の元データ。ここがズレると給料が変わる）
3. 給与システム連携（お金に直結する外部API）
```

次にClaude Codeに聞く。

```
この勤怠管理システムで「壊れたら最も困る機能」を自分は3つ挙げた。
見落としている観点はあるか？

（プロダクト概要と上記3つを渡す）
```

Claude Codeの指摘例：

> 「休暇残日数の管理」が抜けています。有給休暇の残日数が実態と合わないと、取得できるはずの休暇が申請できない、あるいは超過取得が発生します。労基法上のリスクにも直結します。また「残業時間の上限チェック」も検討対象です。36協定の上限を超過した場合の警告が出ないと、法令違反を見逃すことになります。

自分の直感では出なかった「休暇残日数」が出てきた。採用するかは人間が判断する。

| 機能 | 自分の直感 | Claude Codeの指摘 | 最終判断 |
|---|---|---|---|
| 月次集計 | ◎ | ◎ | **最重要** |
| 打刻処理 | ◎ | ◎ | **最重要** |
| 給与システム連携 | ◎ | ◎ | **最重要** |
| 休暇残日数管理 | − | ◎ | 重要（見落としてた） |
| 残業上限チェック | − | ○ | 中程度（警告機能なので遅延許容） |

### 問い2：過去にもっとも痛かったバグは？

バグ一覧を渡すと、Claude Codeはこう返してきた。

> **集中領域**: 月次集計（8件、うち重大3件）と給与連携（5件、うち重大2件）
> **共通パターン**: 重大バグの70%が「月末・月初の境界処理」に起因。月またぎの深夜勤務、月末締め日の残業計算、有給の月次リセットなど
> **増加傾向**: 打刻まわりが直近3ヶ月で増加。モバイル打刻対応の影響と推測

じつはClaude Codeは最初「UIのレスポンシブ対応」をリスクに挙げてきた。勤怠管理システムで見た目の崩れが重大バグになることはまずない。「業務が止まるバグだけに絞ってくれ」と聞き直したら、上の分析が出てきた。こういう軌道修正は人間の仕事だ。

人間が一件ずつ見ても気づきにくい「月末・月初の境界に集中している」という傾向を、データから引き出してくれる。ここがClaude Codeの得意な仕事だ。

### 問い3：重点領域と軽量化領域は？

問い1・2の結果を渡して分類させた。

| 領域 | 分類 | 根拠 |
|---|---|---|
| 月次集計 | **重点** | 最重要機能 × バグ最多 × 月末境界リスク |
| 給与システム連携 | **重点** | 金銭直結 × 外部API依存 × 重大バグ複数 |
| 打刻処理 | **重点** | 全社員に影響 × 直近バグ増加中 |
| 休暇申請 | 標準 | 残日数管理は重要だが、直近バグは少ない |
| 残業申請 | 標準 | 上限チェックは重要だが安定している |
| シフト管理画面 | 軽量 | 管理者のみ利用。影響範囲が限定的 |
| 管理者設定 | 軽量 | 変更頻度が低い。過去バグもほぼない |

ここで人間が調整する。「シフト管理は軽量でいい」「休暇申請は標準のままでいいか？ 年度切り替え時期だけ重点に引き上げるか？」。こういう文脈依存の判断はClaude Codeにはできない。

### 問い4＋5：テストレベルの分担と完了条件

残りの2つはセットで聞いた。

| 領域 | 単体テスト | 結合テスト | E2Eテスト |
|---|---|---|---|
| 月次集計（重点） | 必須（境界値テスト） | 必須（集計→給与連携） | 必須（月次締め→レポート出力） |
| 給与連携（重点） | 必須（外部API mock） | 必須（集計→送信→確認） | 必須（主要シナリオ2本） |
| 打刻処理（重点） | 必須（時刻丸め処理） | 必須（打刻→日次集計） | 回帰テストのみ |
| 休暇申請（標準） | 既存維持 | 主要パスのみ | なし |
| 残業申請（標準） | 既存維持 | 主要パスのみ | なし |
| シフト管理（軽量） | 既存維持 | なし | なし |
| 管理者設定（軽量） | 既存維持 | なし | なし |

| 種別 | 終了条件 |
|---|---|
| **定量** | 重点領域のテストカバレッジ85%以上 |
| **定量** | 重大バグ（Sev1-2）が0件 |
| **定量** | 既知バグの修正率80%以上（Sev3以下は次スプリント持ち越し可） |
| **定性** | 労務担当者がリリース判断に合意 |
| **定性** | 重点領域の探索的テストを最低1セッション実施済み |

:::details 探索的テストとは
テストケースを事前に書かずに、テスターの知識と直感で自由にシステムを操作しながらバグを探すテスト手法。スクリプトテストでは見つからない「想定外の使い方」によるバグを発見できる。
:::

**重点領域は全レベルでカバー。軽量領域は単体テストの既存分だけ。** メリハリをつけることで、限られたリソースに集中できる。

## 30分でできた理由

| 工程 | 所要時間 | 誰がやったか |
|---|---|---|
| インプット準備（概要・バグ一覧） | 5分 | 人間 |
| 問い1〜5をClaude Codeと壁打ち | 15分 | 人間 × Claude Code |
| 人間の判断で調整・修正 | 5分 | 人間 |
| A4一枚にまとめる | 5分 | Claude Code |
| **合計** | **30分** | |

Claude Codeがやったのは**構造化と選択肢の提示**だ。判断は全部人間がした。

「壊れたら困るのは月次集計だ」と決めたのは自分。「給与連携も重点にしよう」と判断したのも自分。Claude Codeは「休暇残日数の管理を見落としていませんか？」と聞いてくれただけだ。

## 「50点の戦略」でいい

テスト戦略に完璧はない。環境も要件もチームも変わる。

大事なのは**文字にすること**だ。文字にすれば、レビューできる。レビューできれば、改善できる。頭の中にあるうちは、誰にも見えないし、誰も指摘できない。

50点の戦略を作って、スプリントごとに60点、70点にしていけばいい。0点のまま「戦略がない」と言い続けるより、50点を文字にするほうがずっといい。

次のスプリント計画で、5つの問いをClaude Codeに投げるところから始めてみてほしい。30分後には、チームの「テスト戦略」が手元にある。
