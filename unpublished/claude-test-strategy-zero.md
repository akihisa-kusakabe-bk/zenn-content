:::message
「テスト戦略を作ってください」と言われて、何から手をつけていいかわからなかった経験はないだろうか。自分はある。
:::

テスト戦略。聞くだけで身構える。分厚いドキュメントを想像して、手が止まる。

でも実際にやってみたら、**5つの問いに答えるだけ**だった。Claude Codeを壁打ち相手にして30分。A4一枚のテスト戦略ができた。この記事では、その過程をそのまま見せる。

:::details テスト戦略とは
プロジェクト横断で「何を重点的にテストし、何を軽くするか」の方針を定めたもの。テスト計画が「今回どうやるか」なら、テスト戦略は「うちのチームはテストにどう向き合うか」の判断基準。詳しくは「[テスト計画書がコピペになる本当の理由](https://zenn.dev/bitkey_dev/articles/test-plan-vs-strategy)」を参照。
:::

## 「戦略がない」の正体

「うちにはテスト戦略がない」──よく聞く悩みだが、じつは2つのパターンがある。

| パターン | 実態 | 対処 |
|---|---|---|
| **本当にない** | テスト方針が暗黙知。人によって判断が違う | → この記事で作る |
| **あるけど死ん出る** | ドキュメントはあるが誰も読んでない | → 5つの問いで書き直す |

どちらも解決策は同じだ。**判断基準を、チームの言葉で文字にする。**

## 準備：Claude Codeに渡す3つのインプット

壁打ちを始める前に、手元に用意するものが3つある。全部揃わなくていい。あるものだけでいい。

| インプット | 具体例 | なくても大丈夫？ |
|---|---|---|
| **プロダクトの概要** | 何をしているサービスか。主要機能の一覧 | 必須。口頭説明レベルでOK |
| **直近の変更・リリース内容** | PRの一覧、リリースノート | あると精度が上がる |
| **過去に痛かったバグ** | インシデント履歴、バグ一覧 | あると重点領域が明確になる |

ポイントは「完璧なデータ」を求めないこと。**「壊れたら困るもの」がわかれば十分**だ。

:::message alert
AIツールに社内の機密情報や個人情報を入力しないでください。バグデータや機能一覧をつかう場合は、固有名詞や実データをダミーに置きかえるか、社内で承認されたAIツールを利用してください。
:::

## 実演：5つの問いをClaude Codeと埋める

ここからは架空のECサイトを題材に、実際にClaude Codeと壁打ちした流れを再現する。

### 問い1：壊れたらもっとも困る機能は？

まず自分の直感で3つ挙げる。

```
自分の直感：
1. 決済処理（売上に直結）
2. ユーザー認証（ログインできないと何もできない）
3. 注文フロー（カート→購入の一連）
```

次にClaude Codeに聞く。

```
このECサイトで「壊れたら最も困る機能」を自分は3つ挙げた。
見落としている観点はあるか？

（プロダクト概要と上記3つを渡す）
```

Claude Codeの指摘例：

> 「在庫管理の同期処理」が抜けています。決済は通ったのに在庫が減らず二重販売になるケースは、金銭的損害に直結します。また「メール通知」も検討対象です。注文確認メールが届かないと問い合わせが急増します。

自分の直感では出なかった「在庫同期」が出てきた。採用するかは人間が判断する。

| 機能 | 自分の直感 | Claude Codeの指摘 | 最終判断 |
|---|---|---|---|
| 決済処理 | ◎ | ◎ | **最重要** |
| ユーザー認証 | ◎ | ○ | 重要 |
| 注文フロー | ◎ | ◎ | **最重要** |
| 在庫同期 | − | ◎ | **最重要**（見落としてた） |
| メール通知 | − | ○ | 中程度（遅延は許容できる） |

### 問い2：過去にもっとも痛かったバグは？

バグ一覧やインシデント履歴をClaude Codeに渡す。

```
過去6ヶ月のバグ一覧を渡すので、以下を分析してほしい。
- どの領域にバグが集中しているか
- 重大度「高」のバグに共通するパターンはあるか
- 直近3ヶ月で増加傾向にある領域はあるか
```

Claude Codeの分析例：

> **集中領域**: 決済処理（12件、うち重大4件）と購入確認画面（7件、うち重大2件）
> **共通パターン**: 重大バグの60%が「外部API連携」に起因。決済ゲートウェイとの通信エラーハンドリングが弱い
> **増加傾向**: フロントエンド関連が直近3ヶ月で倍増。React移行の影響と推測

パターン分析はClaude Codeが得意だ。人間が一件ずつ見ても気づきにくい「外部API連携に集中している」という傾向を、データから引き出してくれる。

### 問い3：重点領域と軽量化領域は？

問い1・2の結果を渡して、リスクベースの判断を作る。

```
問い1の重要機能と問い2のバグ傾向を踏まえて、
テスト対象を「重点」「標準」「軽量」の3段階に分類してほしい。
分類の根拠も付けて。
```

Claude Codeの出力例：

| 領域 | 分類 | 根拠 |
|---|---|---|
| 決済処理 | **重点** | 最重要機能 × バグ最多 × 外部API依存 |
| 注文フロー | **重点** | 最重要機能 × 購入確認画面でバグ増加中 |
| 在庫同期 | **重点** | 二重販売リスク × テスト実績が薄い |
| ユーザー認証 | 標準 | 重要だが安定している（直近バグ少） |
| 商品検索・一覧 | 標準 | 変更頻度は高いがビジネスインパクトは中 |
| メール通知 | 軽量 | 遅延許容可。過去バグも少ない |
| 管理画面 | 軽量 | 社内ユーザーのみ。影響範囲が限定的 |

ここで人間が調整する。「管理画面は軽量でいい」「在庫同期は本当に重点か？→ じつは最近リファクタして安定してるから標準に下げる」──こういう判断はClaude Codeにはできない。

### 問い4：テストレベルの分担は？

```
上記の重点/標準/軽量に対して、
単体テスト・結合テスト・E2Eテストの分担方針を提案してほしい。
前提：CI/CDあり、E2E自動化はPlaywrightで一部実装済み。
```

Claude Codeの出力例：

| 領域 | 単体テスト | 結合テスト | E2Eテスト |
|---|---|---|---|
| 決済処理（重点） | 必須（外部API mock） | 必須（決済フロー全体） | 必須（購入→決済→完了） |
| 注文フロー（重点） | 必須 | 必須 | 必須（主要シナリオ3本） |
| 在庫同期（重点） | 必須（排他制御） | 必須（決済×在庫の整合性） | 回帰テストのみ |
| 認証（標準） | 既存維持 | 主要パスのみ | ログイン→操作→ログアウト |
| 検索（標準） | 既存維持 | 主要パスのみ | なし |
| 通知（軽量） | 既存維持 | なし | なし |
| 管理画面（軽量） | 既存維持 | なし | なし |

**重点領域は全レベルでカバー。軽量領域は単体テストの既存分だけ。** メリハリをつけることで、限られたリソースを効果的に使える。

### 問い5：テスト完了の条件は？

```
このプロダクトのテスト終了条件を提案してほしい。
定量的な基準と、定性的な基準の両方を含めて。
```

Claude Codeの出力例：

| 種別 | 終了条件 |
|---|---|
| **定量** | 重点領域のテストカバレッジ90%以上 |
| **定量** | 重大バグ（Sev1-2）が0件 |
| **定量** | 既知バグの修正率80%以上（Sev3以下は次スプリント持ち越し可） |
| **定性** | PO（プロダクトオーナー）がリリース判断に合意 |
| **定性** | 重点領域の探索的テストを最低1セッション実施済み |

:::details 探索的テストとは
テストケースを事前に書かずに、テスターの知識と直感で自由にシステムを操作しながらバグを探すテスト手法。スクリプトテストでは見つからない「想定外の使い方」によるバグを発見できる。
:::

ここも人間が最終調整する。「カバレッジ90%は現実的か？」「探索的テストの工数は取れるか？」──数字は現場の実態に合わせて変える。

## 完成：A4一枚のテスト戦略

5つの問いに答えた結果を一枚にまとめると、こうなる。

```
■ テスト戦略（ECサイト）

【1. 重要機能】決済処理、注文フロー、在庫同期
【2. 既知のリスク】外部API連携のエラーハンドリング、React移行後のUI
【3. テスト配分】
  重点：決済・注文・在庫（全レベルカバー、探索的テスト含む）
  標準：認証・検索（結合テストまで）
  軽量：通知・管理画面（単体テストのみ）
【4. テストレベル方針】
  単体：全領域で実施。外部API依存はmock必須
  結合：重点+標準領域。CI上で自動実行
  E2E：重点領域の主要シナリオ。Playwrightで自動化推進
【5. 終了条件】
  重大バグ0件 / 重点領域カバレッジ90% / PO合意
```

**これだけだ。** 30ページの大作ではない。A4一枚。でもこの一枚があるのとないのでは、チームの判断基準がまったく違う。

## 30分でできた理由

| 工程 | 所要時間 | 誰がやったか |
|---|---|---|
| インプット準備（概要・バグ一覧） | 5分 | 人間 |
| 問い1〜5をClaude Codeと壁打ち | 15分 | 人間 × Claude Code |
| 人間の判断で調整・修正 | 5分 | 人間 |
| A4一枚にまとめる | 5分 | Claude Code |
| **合計** | **30分** | |

Claude Codeがやったのは**構造化と選択肢の提示**だ。判断は全部人間がした。

「壊れたら困るのは決済だ」と決めたのは自分。「在庫同期も重点にしよう」と判断したのも自分。Claude Codeは「在庫同期を見落としてませんか？」と聞いてくれただけだ。

## 「50点の戦略」でいい

テスト戦略に完璧はない。環境も要件もチームも変わる。

大事なのは**文字にすること**だ。文字にすれば、レビューできる。レビューできれば、改善できる。頭の中にあるうちは、誰にも見えないし、誰も指摘できない。

50点の戦略を作って、スプリントごとに60点、70点にしていけばいい。0点のまま「戦略がない」と言い続けるより、50点を文字にするほうがずっといい。

次のスプリント計画で、5つの問いをClaude Codeに投げるところから始めてみてほしい。30分後には、チームの「テスト戦略」が手元にある。
